# Auto-Session 285 P1: Trace 0x02FCB3 — Blocking Key Wait

## Context
Session 284 discovered that 0x09E017 (STAT menu event loop) enters a blocking key wait by writing A=1 to D00824 (event latch), then loops on `CALL 0x02FCB3` until nonzero. We need to understand what 0x02FCB3 does — how does it poll for keyboard input? Does it HALT? Does it read MMIO? Does it call _GetCSC?

## Task
Create a probe file `TI-84_Plus_CE/probe-phase285-02fcb3-key-wait.mjs` that:

1. **Static disassembly** of 0x02FCB3 — decode ~200 bytes starting at 0x02FCB3 from `ROM.rom` using the eZ80 decoder at `TI-84_Plus_CE/ez80-decoder.js`. Show address, hex bytes, and mnemonic for each instruction. Stop at a RET or after 200 bytes.

2. **Find all callers** — scan the ROM binary (`ROM.rom`, 4MB) for CALL 0x02FCB3 (`CD B3 FC 02` for ADL CALL) and JP 0x02FCB3 (`C3 B3 FC 02` for ADL JP). Report all sites.

3. **Dynamic trace** — boot a CPU runtime, run the transpiled ROM, and trace execution from 0x02FCB3 with:
   - Set up memory from ROM (copy ROM into a 16MB memory array)
   - IY = 0xD00080 (standard OS IY)
   - SP = 0xD1A87E
   - IX = 0xD1A860
   - Push a return sentinel (0xFEFEFE) onto stack
   - Seed D00824 = 0x01 (event latch armed, as 0x09E017 does)
   - Seed D0058E = 0x00 (no key pending)
   - PC = 0x02FCB3
   - Run up to 500 steps, log each step (PC, mnemonic, key registers)
   - Track: which addresses are read/written, any I/O port access, any HALT instructions, any sub-calls

4. **Second trace** — same setup but seed D0058E = 0x8F (a key is pending, scan code for "1")
   - Compare behavior: does it return faster? Does it read D0058E? Does it read the keyboard MMIO?

5. **Report**: What does 0x02FCB3 do? Is it:
   - A HALT-based wait (EI + HALT, ISR delivers key)?
   - An MMIO polling loop (reads 0xE00810-0xE00817)?
   - A RAM-polling loop (checks D0058E or D00824)?
   - Something else?
