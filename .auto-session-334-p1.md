# Auto-Session 334 — P1: Discover the OS Main Event Loop

## Context

This is a TI-84 Plus CE ROM transpilation project. The ROM (eZ80 machine code at `TI-84_Plus_CE/ROM.rom`) has been lifted into JavaScript. An executor (`cpu-runtime.js` + `ROM.transpiled.js`) can run lifted blocks.

After boot, ALL boot stages RET through a sentinel address (0xffffff). This means the staged boot sequence we use (KERNEL_INIT at 0x08C331, then rendering stages at 0x0A2B72/0x0A3301/0x0A29EC/0x0A2854) are INIT routines, not the main loop. The OS must have a main event loop somewhere that:
1. Polls _GetCSC (keyboard scanner)
2. Dispatches key events to app handlers
3. Refreshes the display

## Known addresses (from prior sessions)

- **0x08C331** = CoorMon (main OS coordinator/monitor) — this is the KERNEL_INIT entry
- **0x0019BE** = OS event loop entry (ISR dispatches here, runs 17 steps then hits missing block 0x00B608)
- **0x09EFDE** = CoorMon event loop (busy-waits on MMIO/LCD)
- **0x08BF22** = entry to CoorMon event loop from the home handler
- **0x015AD9** = post-boot callback found in session 49 at (0xD02AD7-9). This is described as "the IRQ event-loop entry that the OS would normally invoke after waking from HALT"
- **0x03CF7D** = _GetCSC implementation (trampoline at 0x02010C)
- **0x0159C0** = direct keyboard scanner (works correctly, returns scan code in B register)
- **0xD0058E** = key scan code handoff byte (many blocks read this and compare against scan codes)
- **0xD0058C** = kbdKey (processed key code)
- **0xD00587** = kbdScanCode (raw scan code from GetCSC)
- **0x058241** = home screen handler entry
- **0xD007CA** = cxMain (app context main handler pointer — is 0x000000 after basic boot)

## Key pipeline (from phase 129 report)

```
Physical key → GetCSC (0x03FA09) → kbdScanCode (0xD00587)
                                          ↓
                              Scan-to-keycode table (0x09F79B)
                                          ↓
                                   kbdKey (0xD0058C)
                                          ↓
                              CoorMon (0x08C331) main loop
                                          ↓
                              App handler dispatch (cxMain → JP(HL))
                                          ↓
                              Home handler (0x058241)
```

## Your task

Write a probe file `TI-84_Plus_CE/probe-phase334-event-loop.mjs` that investigates the OS event loop. The probe should:

1. **Boot normally** using the same pattern as `probe-phase99d-home-verify.mjs`:
   - Import from `./cpu-runtime.js` (createExecutor, createMemoryBus, createPeripheralBus, helpers)
   - Create memory bus, peripheral bus with `{ timerInterrupt: false }`, executor
   - Load ROM from `./ROM.rom` using `fs.readFileSync`
   - Run KERNEL_INIT at 0x08C331 in ADL mode for up to 100000 steps

2. **After boot, investigate these candidates for the event loop**:

   a. **0x015AD9** — the post-boot callback. Run it in ADL mode for up to 50000 steps. Log the termination reason, last PC, and number of steps. Also log every unique PC visited (use the executor's trace/step capabilities to record PCs).

   b. **0x0019BE** — the OS event loop entry. Same treatment: run for 50000 steps, log termination + PCs. This previously hit missing block 0x00B608 after 17 steps — check if that's still the case with current coverage.

   c. **0x08BF22** — CoorMon event loop entry. Same treatment.

   d. **0x09EFDE** — CoorMon inner event loop. Same treatment.

   e. **After KERNEL_INIT completes**, read the post-boot callback pointer at RAM addresses 0xD02AD7-0xD02AD9 (3 bytes, little-endian 24-bit pointer) and report what address it contains.

   f. **Read cxMain** at 0xD007CA (3 bytes, little-endian) after boot and report its value.

   g. **Search for HALT instructions** in the ROM. In the transpiled JS, HALT would appear as a specific pattern. Instead, search the raw ROM bytes: HALT in eZ80 is opcode 0x76. Scan ROM bytes 0x000000-0x020000 for 0x76 and report all addresses where it appears (filter to those that look like they're in code regions, not data — i.e., preceded by plausible instruction bytes).

3. **For each candidate entry point**, set up a key press BEFORE running:
   - Set `keyMatrix[6] = 0x02` (this is the ENTER key: group 6, bit 1 → SDK group 1, bit 0)
   - Also set `mem[0xD0058E] = 0x09` (ENTER scan code) and `mem[0xD00587] = 0x09`
   - This way, if the event loop tries to poll the keyboard, it'll find a key waiting

4. **Log the first 200 unique block entry PCs** for each candidate to stdout, so we can see the execution flow.

## File patterns to reference

Look at `TI-84_Plus_CE/probe-phase333-hook-iterator.mjs` for the import pattern and executor setup. The key pattern is:

```javascript
import { createExecutor, createMemoryBus, createPeripheralBus, helpers } from './cpu-runtime.js';
import fs from 'fs';
const { hex } = helpers;

const rom = fs.readFileSync(new URL('./ROM.rom', import.meta.url));
const mem = createMemoryBus(rom);
const periph = createPeripheralBus({ timerInterrupt: false });
const executor = createExecutor(mem, periph);
```

To run a block: `executor.runFrom(address, { mode: 'adl', maxSteps: N })` returns `{ steps, termination, lastPc }`.

To read memory: `mem[address]` for single bytes, or `mem[addr] | (mem[addr+1] << 8) | (mem[addr+2] << 16)` for 24-bit LE pointers.

To set keyboard matrix: `periph.keyMatrix[N] = value` (array of 8 bytes, index N = SDK group 7-N).
