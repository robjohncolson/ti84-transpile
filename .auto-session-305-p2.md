# Task: Trace SDK _GetCSC key-present path at 0x03FB9A

## Context
We are reverse-engineering the TI-84 Plus CE OS ROM. Session 304 compared the ISR _GetCSC (0x080259, trivially simple: BIT 3,(IY+1) + RET) with the SDK _GetCSC (0x02014C → JP 0x03FA09, ~112 instructions across 4 blocks). 

The SDK _GetCSC key-present path starts at 0x03FB9A. When a key IS available (scan code at 0xD00587 is non-zero), it:
- Checks 6 IY flags: IY+18, IY+9, IY+67, IY+91, IY+92, IY+40
- Can override key to 0x0F
- Returns scan code in A via POP AF
- Also handles USB activity (port 0x500C, 0xD14091, 0xD141B2, 0xD141BA)

Session 304 also found: ISR tests IY+1 bit 3 (0xD00081), SDK clears IY+0 bit 3 (0xD00080) — DIFFERENT BYTES for key-available signaling.

## What to do

Create a probe file `TI-84_Plus_CE/probe-phase305-getCSC-key-path.mjs` that:

1. **Set up a warm CPU state** with a key ready:
   - Standard boot pattern
   - Seed 0xD00587 = 0x31 (scan code for "2" key) 
   - Set IY+0 bit 3 (0xD00080 bit 3) to signal key available
   - Call SDK _GetCSC entry at 0x03FA09

2. **Trace the key-present path** for 500 steps:
   - Log every block visited
   - Track which IY flag checks (BIT instructions) are hit and their results
   - Track what value A has at RET

3. **Test the 6 IY flag overrides** — for each of IY+18, IY+9, IY+67, IY+91, IY+92, IY+40:
   - Set various bits in each and trace to see which bit causes the key override to 0x0F
   - Document what each flag check does (skip key? override key? modify key?)

4. **Trace the USB fallback path** at 0x03FA8D:
   - What conditions lead to it?
   - What does it read from port 0x500C and the D14xxx addresses?
