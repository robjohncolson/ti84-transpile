# Task: Trace token dispatch and display refresh paths

## Context
This is a TI-84 Plus CE ROM transpilation project. The ROM (eZ80 machine code) has been lifted to JavaScript. We're tracing the OS event loop to understand how keys get processed and characters appear on screen.

**Key findings from sessions 442-444**:
- The event loop entry is at 0x003A73, which is inside the error handler function at 0x003A05-0x003A8E
- 0x003A73 calls 0x003D5A (_GetCSC) to get a keyboard scan code in register A
- After _GetCSC returns, the error handler checks the result and either loops (no key) or processes it
- The scheduler at 0x001612 is the outer caller
- VRAM never changes during key processing in the workflow probe — the token dispatch / display refresh path is not being exercised

The workflow probe (probe-workflow-arithmetic.mjs) boots to the home screen, then injects keys '1', '+', '1', 'ENTER'. All 4 keys process through 200k steps each (PASS), but VRAM never changes (FAIL). The missing link is: what happens after _GetCSC returns a scan code? How does the OS convert it to a token and display it?

## Task
Write a probe script `TI-84_Plus_CE/probe-phase445-token-dispatch-trace.mjs` that:

1. Reads the ROM binary at `TI-84_Plus_CE/ROM.rom`
2. Disassembles the code AFTER the CALL 0x003D5A at 0x003A73. What happens when _GetCSC returns a non-zero scan code?
   - Disassemble 0x003A73-0x003A8E (the rest of the error handler after _GetCSC)
   - Look at what happens with the value in A after the CALL returns
3. Disassemble the CALL target at 0x003A0F (the entry called from the scheduler via JP at 0x0017CA). This is a different entry point into the same function.
   - Disassemble 0x003A0F-0x003A8E fully
4. Search for the OS home screen key handler. The TI-OS processes keys through a dispatch table. Look for:
   - Known addresses from phase410-key-handler-table-report.md (read this file first)
   - A function that takes a scan code and looks up a handler
   - A function that converts a scan code to a token (character code)
5. Search for display refresh / LCD update routines. Look for:
   - Writes to VRAM area 0xD40000-0xD52C00
   - References to LCD registers (port 0xF60000 area or mapped as low ports)
   - Known LCD-related functions
6. Disassemble 0x003D5A-0x003D80 (start of _GetCSC) to understand what it returns

Also write a report `TI-84_Plus_CE/phase445-token-dispatch-report.md` with:
- Disassembly of the post-_GetCSC code path at 0x003A73-0x003A8E
- Disassembly of 0x003A0F-0x003A8E
- Analysis of what happens after a key is detected
- Any key handler dispatch tables found
- Any display refresh functions identified
- The path from scan code → token → VRAM write (as far as traceable)
