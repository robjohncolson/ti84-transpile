# Auto-Session 608 P3 — Trace the Stack Leak in Key2 Runaway

## Goal
Create a probe `TI-84_Plus_CE/probe-phase608-stack-leak.mjs` that traces the SP register during the key2 runaway loop to find EXACTLY which instruction(s) push without matching pops, causing the ~12KB stack leak (SP goes from 0xD1A2E7 to 0xD17374 over ~450K steps).

## Background
- Session 607 found: key2 ('3') with post-paint snapshot gets stuck in a tight loop: 0x08F3DC↔0x04C973↔0x090927.
- SP decreases from ~0xD1A2E7 to ~0xD17374 (~12KB leak) over the runaway.
- The loop is 0x090917-0x090928: INC HL → CALL 0x08F3DC → RET Z → LD DE,(D0243A) → CALL 0x04C973 → POP DE → RET NZ → (loops back to 0x090917)
- The POP DE at 0x090927 should balance one PUSH, but something in the call chain pushes extra.

## Probe design
1. Boot through the standard sequence (cold boot → 0x08C331 → 0x0802B2 → 0x0019be → 0x09DD62 init → 0x058241 paint)
2. Snapshot the post-paint state
3. Press key '3' (scan code 0x91) — use the SAME scan code as probe-phase607-postwipe-snapshot.mjs keys[1]
4. Run from OUTER_LOOP (0x08C331) with maxSteps=50_000 (enough to see the leak pattern, not 500K)
5. Use onBlock to track SP at every entry to these key addresses:
   - 0x090917 (walker loop top)
   - 0x08F3DC (cursor advance — inner call)
   - 0x04C973 (compare helper)
   - 0x090927 (POP DE)
   - 0x0019B5 (halt — if reached)
   - 0x0018F8 (wipe — if reached)

For each hit, log: `step, PC (hex), SP (hex), SP delta from previous hit at same PC`

6. After the run, compute:
   - SP at first hit of 0x090917 vs last hit
   - Total SP drop
   - SP delta per iteration of the 0x090917 loop
   - Which specific addresses show SP decreasing between consecutive visits

## Key insight to find
The POP DE at 0x090927 pops 3 bytes (ADL mode), and the CALL at 0x090918/0x090923 pushes 3 bytes. So CALL+RET should balance. The leak must be:
- A PUSH inside 0x08F3DC that doesn't get POPped (because the function takes a different exit path in the loop case), OR
- The CALL 0x04C973 at 0x090923 pushing 3 bytes that the POP DE at 0x090927 only partially compensates (POP in ADL = 3 bytes, same as CALL push), OR
- Something else entirely

Track SP changes BETWEEN consecutive onBlock hits to narrow it down.
