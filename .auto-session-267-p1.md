# Auto-Session 267 — P1: Disassemble 0x08C69E-0x08C745 and trace D007D0→HL zeroing

## Context

Session 266 discovered that the "z80-mode loop" at 0x062055 was actually the cold-boot reset sequence entered via JP(HL=0) at 0x08C745. The ADL mode is correct. The real issue is:

1. Boot path reaches 0x08C69E from 0x062055→0x080151→0x06205A→0x063033→0x062060→0x08C69E
2. D007D0 is seeded with 0x06C546 (a valid code address) before boot
3. At 0x08C745, JP(HL) is executed, but HL=0x000000 — the seed was zeroed somewhere in the 0x08C69E→0x08C745 call chain
4. This causes a jump to the reset vector instead of to cxMain

## Task

Create a probe `TI-84_Plus_CE/probe-phase267-08C69E-hl-trace.mjs` that:

1. **Disassembles 0x08C69E through 0x08C745** — read the ROM bytes, decode eZ80 instructions, and list them with addresses. Use the existing decoder in `TI-84_Plus_CE/ez80-decoder.js` (import `decodeInstruction` or the decoder class).

2. **Instruments execution from 0x08C69E to 0x08C745** to track:
   - HL value at every block entry
   - Any reads from D007D0-D007D2 (3-byte pointer)
   - Any writes to HL that change it
   - Which block zeroes HL or loads 0 into it

3. **Setup**: Use the standard boot pattern from session 266:
   - Import `{ createCPU }` from `./cpu-runtime.js`
   - Import `{ createPeripheralBus }` from `./peripherals.js`  
   - `createPeripheralBus({ timerInterrupt: false })`
   - Load `ROM.transpiled.js` via dynamic import
   - Set ADL=true, D0230F=0x3F, D007D0=0x06C546 (3-byte LE: mem[0xD007D0]=0x46, mem[0xD007D1]=0xC5, mem[0xD007D2]=0x06)
   - Set B=3 (the gate value from session 266)
   - PC = 0x062055
   - Run up to 500 steps

4. **Output**: Print a table showing for each step in the 0x08C69E-0x08C745 range:
   - Step number, PC (block address), HL value (hex), whether D007D0 was read/written
   - Highlight the exact step where HL transitions from non-zero to zero
