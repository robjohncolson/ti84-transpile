# Task: Trace 0x00C9A0 (Hardware/State Reset)

## Context
You are working on a TI-84 Plus CE ROM reverse-engineering project. The ROM file is at `TI-84_Plus_CE/ROM.rom` (4MB eZ80 binary). The instruction decoder is at `TI-84_Plus_CE/ez80-decoder.js`.

Session 419 decoded 0x0098D2, the deep USB event dispatcher. During transfer-recovery (the D177BB path), it calls 0x00C9A0 for hardware/state reset. We need to understand what it resets.

## Deliverables

### 1. Probe file: `TI-84_Plus_CE/probe-phase420-trace-00C9A0.mjs`

Write a probe that:
1. Reads ROM.rom
2. Imports and uses `ez80-decoder.js` (use `await import('./ez80-decoder.js')` with `process.emitWarning = () => {}`)
3. Disassembles from 0x00C9A0 forward until finding a RET (estimate ~100-300 bytes)
4. For each instruction, prints: address, raw hex bytes, decoded mnemonic
5. Annotates CALL targets, port I/O (IN/OUT), and RAM variable accesses (D00000-D3FFFF range)
6. Tags any port writes that clear/reset registers

Use the same probe style as `TI-84_Plus_CE/probe-phase419-trace-014D48.mjs` (read it for reference).

The decoder function signature: `decodeInstruction(romBuffer, pc, 'adl')` returns `{tag, length, nextPc, ...fields}`.

### 2. Report file: `TI-84_Plus_CE/phase420-hw-reset-report.md`

After running the probe, write a report with:
- Function boundary (start/end address, byte count)
- What ports it resets (address, old→new value if determinable)
- What RAM variables (D00000-D3FFFF) it clears/reinitializes
- What CALL targets it invokes
- Relationship to USB recovery — what state does this function put the system back into?

## Constraints
- Do NOT modify any existing files except creating the two new files listed above
- Do NOT modify ROM.rom, cpu-runtime.js, peripherals.js, browser-shell.html, or transpile-ti84-rom.mjs
- Run the probe with `node TI-84_Plus_CE/probe-phase420-trace-00C9A0.mjs` and include its output in the report
