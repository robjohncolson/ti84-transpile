# Task: Trace BCALL/BJUMP Dispatch Mechanism (RST 28h / RST 30h)

## Context
The TI-84 Plus CE OS has a contiguous 2175-entry JP mega-table spanning 0x020110-0x022308. Session 317 discovered that RST 28h (B_CALL) and RST 30h (B_JUMP) use a 2-byte operand to index into this table. The formula appears to be: effective address = 0x020000 + operand → lands in table.

RST instructions in eZ80 are single-byte opcodes that CALL a fixed address:
- RST 28h → CALL 0x000028
- RST 30h → CALL 0x000030

The handler at those addresses reads the 2-byte operand from the return address on the stack (the bytes immediately after the RST instruction in the caller), computes the target, and jumps there.

## What To Do

1. Read the ROM file at `TI-84_Plus_CE/ROM.rom` (4MB binary, little-endian eZ80).

2. **Disassemble RST 28h handler at 0x000028**: Read bytes starting at ROM offset 0x000028. This is likely a short handler (maybe 10-30 bytes) that:
   - Pops or reads the return address from the stack
   - Reads the 2-byte operand at that return address
   - Computes the target address (probably 0x020000 + operand, or operand × 4 + base, etc.)
   - Jumps to the target
   - Adjusts the return address past the 2-byte operand before returning
   
   Fully disassemble until you hit a JP or RET.

3. **Disassemble RST 30h handler at 0x000030**: Same as above. B_JUMP likely uses JP instead of CALL semantics (doesn't return to caller).

4. **Verify the dispatch formula**: Take a known BCALL site in the ROM. For example, search for RST 28h (opcode 0xEF) followed by a 2-byte operand. Compute where the formula says it should go, then verify that address is a valid JP instruction in the mega-table pointing to a real function.

5. **Count BCALL/BJUMP usage**: How many RST 28h (0xEF) and RST 30h (0xF7) instructions exist in the ROM? This tells us how heavily the BCALL/BJUMP mechanism is used vs direct CALL/JP.

6. **Check for RST 28h/30h at other addresses**: The RST handler might JP to a longer implementation elsewhere. Follow all JPs.
