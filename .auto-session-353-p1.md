# Task: Diagnose Boot Steady-State Loop Structure

## Context
The TI-84 Plus CE ROM transpilation project boots the OS from address 0x000000 in z80 mode. After session 352, boot reaches 270 unique blocks with ZERO missing blocks, but then enters a steady-state loop — no new blocks are discovered after ~step 600. The boot appears to loop indefinitely in LCD init territory (0x006xxx-0x001377 area).

## What You Must Do
Create a probe `TI-84_Plus_CE/probe-phase353-loop-diagnosis.mjs` that:

1. Boots from 0x000000 in z80 mode with `{ pllDelay: 2, timerInterrupt: false }` for 2000 steps
2. Records the FULL block execution sequence (not just unique blocks — the ordered list of which block PC was visited at each step)
3. After step 600 (when the loop is stable), captures the exact block sequence for steps 600-700 
4. Identifies the LOOP CYCLE: which blocks form the repeating pattern, and how many steps per cycle
5. For each block in the loop cycle, disassembles the first 20 bytes of ROM at that address to show what instructions are executing
6. Specifically looks for: backward jumps (JR/JP with negative offset), port IN instructions (which port is being polled?), conditional branches that always go the same way
7. Reports: "The boot loop consists of N blocks repeating every M steps. The blocks are: [list]. The loop is caused by [port polling / unconditional jump / etc] at address 0xNNNNNN."

## How To Build The Probe
Use the same boilerplate as existing probes. Reference `TI-84_Plus_CE/probe-phase352-extended-boot-10k.mjs` for the boot setup pattern:

```javascript
import { execFileSync } from 'node:child_process';
import fs from 'node:fs';
import path from 'node:path';
import process from 'node:process';
import { fileURLToPath, pathToFileURL } from 'node:url';

process.emitWarning = () => {};
const __filename = fileURLToPath(import.meta.url);
const __dirname = path.dirname(__filename);

// Standard paths

const TRANSPILED_PATH = path.join(__dirname, 'ROM.transpiled.js');
const TRANSPILED_GZ_PATH = path.join(__dirname, 'ROM.transpiled.js.gz');
const CPU_RUNTIME_PATH = path.join(__dirname, 'cpu-runtime.js');
const PERIPHERALS_PATH = path.join(__dirname, 'peripherals.js');
const TRANSPILER_PATH = path.resolve(__dirname, '..', 'scripts', 'transpile-ti84-rom.mjs');
```

Boot setup: load ROM into memory at offset 0, create CPU with `new EZ80CPU(mem)`, create peripheral bus with `createPeripheralBus({ pllDelay: 2, timerInterrupt: false })`, set `cpu.portRead = peripherals.read; cpu.portWrite = peripherals.write`, set `cpu.pc = 0x000000; cpu.adl = 0` (z80 mode).

The transpiled ROM exports `blocks` — an object keyed by `"NNNNNN:mode"` strings (e.g., `"000000:z80"`). Each block is a function that takes `(cpu, mem)` and returns the next PC (or calls `cpu.missing_block(pc, mode)`).

To step: `const key = blockKey(cpu.pc, cpu.adl ? 'adl' : 'z80'); const block = blocks[key]; if (!block) { /* missing */ break; } block(cpu, mem);`

For disassembly: read raw ROM bytes at each block's PC address and decode eZ80 opcodes manually. The ROM is loaded as a Uint8Array. Key opcodes:
- 0x18 = JR d (relative jump)
- 0x20/0x28/0x30/0x38 = JR cc,d (conditional relative)
- 0xC3 = JP nn (absolute jump)  
- 0xDB = IN A,(n) (z80 port read)
- 0xED 0x38 = IN0 A,(n) (eZ80 port read from low 256)
- 0xED 0x78 = IN A,(C) (port read from BC)
- 0x10 = DJNZ d (loop)

## Constraints
- Do NOT modify peripherals.js, cpu-runtime.js, or any other existing file
- Only create the new probe file
- The probe must be runnable with `node TI-84_Plus_CE/probe-phase353-loop-diagnosis.mjs`
- Print results to stdout in a clear, structured format
- Include a `blockKey` helper: `function blockKey(pc, mode) { return (pc >>> 0).toString(16).padStart(6, '0') + ':' + mode; }`

## Success Criterion
The probe runs without errors and identifies the exact loop cycle (which blocks, how many steps per iteration, what instruction causes the backward branch).
