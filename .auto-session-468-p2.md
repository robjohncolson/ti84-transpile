## Background
- The OS scheduler at 0x0015F7 routes to event handler 0x001794 when port 0x0F bit 6 is set (key pending)
- Event handler at 0x001794: loops B=248 times with EI+HALT countdown barrier (0x001783), rotating display refresh (0x0017CE), and interrupt status checks (0x001296)
- Event handler CLEANUP at 0x0017BC: `LD (D00595),0x000000 → JP 0x003A0F`
- 0x003A0F is the ERROR HANDLER (prints "ERROR!" text, not the normal key path)
- The JP at 0x0017BC goes to 0x003A0F — but the target address 0x003A0F is loaded from... where? Is it hardcoded or computed?
- D00595 is cleared to 0x000000 at 0x0017BC. Multiple places in the codebase write D00595 with different values (e.g., 0x0AF1BC clears it, 0x0015E5-0x0015F3 writes HL=0x001900)
- In NORMAL home-screen mode, the scheduler at 0x0015E5 does: `LD A,0x0A → LD HL,0x001900 → LD (D00595),HL → CALL 0x0059C6 → RES 3,(IY+5)` — this writes D00595=0x001900 BEFORE the event handler runs

## What to investigate

### Part A: D00595 writers
Create a probe that searches the ROM binary for all instructions that write to D00595 (address 0xD00595 in little-endian = bytes 95 05 D0). Search patterns:
- `LD (D00595),HL` = ED 23 95 05 D0 (or similar eZ80 encoding)
- `LD (D00595),A` and other store variants
- Use the ROM.rom file directly: read it and search for byte pattern 0x95 0x05 0xD0 (little-endian address)
List all sites with their ROM addresses and the full instruction context (disassemble 10 bytes before and after each hit).

### Part B: Event handler JP target analysis
At 0x0017BC, the event handler does `LD (D00595),0x000000` then `JP 0x003A0F`. Check: is the JP target 0x003A0F hardcoded (opcode C3 0F 3A 00) or is it an indirect jump (JP (HL) or similar)? Read the ROM bytes at 0x0017BC and disassemble manually.

If the JP is hardcoded to 0x003A0F, then the event handler ALWAYS routes to the error handler on cleanup. This means the NORMAL key processing path must be somewhere else entirely — perhaps:
- Through the scheduler's main loop AFTER the event handler returns (not through the JP)
- Through an interrupt-driven path (timer ISR → key service → D141B5)
- Through a different mode (D00595 value changes the scheduler behavior)

### Part C: Trace D00595 usage
Search for all instructions that READ D00595 (same byte pattern 95 05 D0 in load instructions). Who reads this address? The scheduler writes 0x001900 to D00595 — who uses that value?

### Part D: What is at 0x001900?
Disassemble the code at ROM address 0x001900 (read ~50 bytes from ROM.rom starting at offset 0x1900). This is the value written to D00595 by the scheduler. Is it a function pointer? A mode indicator?
