# Auto-session 597 P2: Dynamic trace probe — keypress flow through 0x030300/0x040D11

## Context

This is a TI-84 Plus CE ROM transpilation project. We have a working boot-to-home-screen sequence:
1. Shortcut boot: fresh sp=0xD1A87E-24, push 0x0019be, write24(D008E0, sp), adl mode
2. Run 0x09DD62 (real OS init, ~84K steps) → sets VAT pointers, D007E0=0x40, D007CA=0x0585E9, D008E0=0xD1A866
3. Push 0x0019b5 as return, run 0x058241 (home repaint) → edit cursors live, 1377 black px
4. Inject keypress and run warm loop at 0x02FD8F → key consumed but dispatch to 0x099921 NEVER fires

The key reaches D0058E=0x90 (internal code for digit '2') but the dispatch chain stops at 0x030300→0x040D11. We need to trace what happens INSIDE 0x040D11 dynamically.

## Task

Build a probe that executes the full boot→init→paint→keypress sequence and traces 0x040D11's execution in detail.

### Recipe (from human session 595, probes probe-interactive-irq.mjs, probe-golden-path-keypress.mjs)

1. Read `TI-84_Plus_CE/probe-golden-path-keypress.mjs` or `TI-84_Plus_CE/probe-loop-iterate-keypress.mjs` as a template — they show the working boot+init+key injection pattern.

2. Create `TI-84_Plus_CE/probe-phase597-key-handler-trace.mjs`:

```
Phase 1: Boot
- const { createExecutor } = require('./cpu-runtime.js');
- const { createPeripheralBus } = require('./peripherals.js');
- const peripherals = createPeripheralBus({ timerInterrupt: false });
- const executor = createExecutor(peripherals);
- const { cpu, mem } = executor;
- Set sp = 0xD1A87E - 24, push24(0x0019be), write24(D008E0, sp), cpu.adl=1
- executor.runFrom(0x09DD62, { maxSteps: 300000, maxLoopIterations: 30000 })

Phase 2: Paint
- Read and log D007E0, D007CA, D008E0, D0231A, D0243A values
- Push return 0x0019b5, run 0x058241 (maxSteps 300000, maxLoopIterations 30000)
- Log edit cursor values after paint

Phase 3: Inject key
- peripherals.setMatrixKey(3, 1)  // row 3 bit 1 = '2' key
- mem[0xD00587] = 0x1A  // raw scan code
- mem[0xD0058C] = 0x1A  // pending key
- mem[0xD0058E] = 0x90  // translated internal code
- mem[0xD0058D] = 0x90
- mem[0xD00080] |= 0x08 // key pending flag

Phase 4: Arm longjmp anchor + run warm loop WITH DETAILED TRACING
- Re-seed D008E0: push24(0x0019b5), write24(D008E0, cpu.sp)
- Set up a step-by-step trace that logs every block entry for addresses in ranges:
  0x030300-0x0303FF, 0x040D00-0x040DFF, 0x099900-0x099AFF, 0x03E180-0x03E1FF
- Also check D000A8 (IY+0x28) value BEFORE running — bit 7 controls the 0x030300 vs 0x04049B branch
- Also check D0009D (IY+0x1D) value — bit 0 is the reentrancy guard in 0x030300
- Run executor.runFrom(0x02FD8F, { maxSteps: 5000, maxLoopIterations: 5000 })
- After: dump D0058C, D0058E, D007CA, D000A8, D0009D
- Check if 0x040D11 was visited. If visited, trace what it called.

Phase 5: If 0x040D11 hit but 0x099921 not hit:
- Dump the state at 0x040D11 entry: key code location, dispatch flags
- Check D000A8 bit 7 and D0009D bit 0 values — these may gate the path

### Output format
Print labeled sections for each phase with all values. Especially:
- "=== DISPATCH FLAGS ===" with D000A8, D0009D values before warm loop
- "=== BLOCK TRACE ===" listing every block in 0x0303xx, 0x040Dxx, 0x0999xx, 0x03E1xx ranges
- "=== POST-LOOP STATE ===" with all key/dispatch RAM values
```

3. Run: `node scripts/run-probe.mjs --max-time 180 TI-84_Plus_CE/probe-phase597-key-handler-trace.mjs`

### Critical constraints
- Do NOT modify any existing files
- PROBE SAFETY: run via watchdog only
- The executor's `runFrom` may need `onBlock` or similar callback for tracing — check cpu-runtime.js for the API. If no callback exists, compare PC ranges by reading cpu.pc after each step, or use the executor's step-level API.

### Success criterion
- Probe runs exit 0
- We learn whether 0x040D11 is reached and what it does
- We learn why 0x099921 is not reached
- D000A8 and D0009D values are dumped
