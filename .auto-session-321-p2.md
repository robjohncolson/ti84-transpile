# Task: Trace the Recursive dispatch_key() Mechanism

## Context
You are analyzing the TI-84 Plus CE OS ROM (eZ80, file `TI-84_Plus_CE/ROM.rom`, 4 MB). This is a 24-bit eZ80 CPU in ADL mode.

## Background
The TI-84 CE OS uses two structurally identical functions as screen-state transition engines:
- **0x00883C** — 78 callers, in low ROM (Flash bank A)
- **0x049CCA** — 166 callers, in mid ROM (Flash bank B, parallel copy)

These are `dispatch_key(key_code, state)` functions. Session 320 confirmed:
- They are recursive — state transitions call `dispatch_key(0, current_state)` for exit handlers
- State is stored at RAM address **D177B9** (14 refs, 12 reads + 2 writes, 13 states mapped)
- The _seqcase tables (session 315: 356 unique targets) route scan codes to case handlers
- Key state mapping: 0x01=Home, 0x03=??, 0x06=Window, 0x08=GRAPH, 0x10=??, 0x13=Graph screen, etc.

## Deliverables

1. **Full disassembly of 0x00883C** — decode from 0x00883C until the function returns. Show hex bytes + mnemonics. Note: the function may be substantial (dozens of instructions).
2. **Parameter passing convention** — how are key_code and state passed? (registers, stack?)
3. **Recursion mechanism** — where does it call itself? What arguments does it pass for the recursive call? Show the specific instructions.
4. **Recursion guard** — what prevents infinite recursion? Is there a depth counter, a "visited" flag, a state comparison that stops re-entry?
5. **_seqcase dispatch** — how does it invoke the _seqcase table lookup? What happens when no case matches (default/epilogue)?
6. **State transition flow** — trace a concrete example: when state=0x13 (Graph) and key=0x08 (GRAPH physical key), what sequence of dispatch_key calls occurs?

## Method

3. Look for CALL 0x00883C within the function body (recursive call)
4. Look for references to D177B9 (state read/write)
5. Look for _seqcase pattern: CALL to a _seqcase stub followed by inline data table
6. Also spot-check 0x049CCA for structural comparison
