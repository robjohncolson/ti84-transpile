# Task: Investigate Port 0x0009 (CPU Speed Control) Boot Gate

## Context
The TI-84 Plus CE ROM transpilation project boots the OS from 0x000000 in z80 mode. After session 352, boot reaches 270 unique blocks but enters a steady-state loop. Port 0x0009 is read 25 times during boot, always returning 0xFF (unhandled default). On real TI-84 CE hardware, port 0x09 is the CPU speed/frequency control register. The wrong return value may gate boot progress.

## What You Must Do
Create a probe `TI-84_Plus_CE/probe-phase353-port0009-analysis.mjs` that:

1. Boots from 0x000000 in z80 mode with `{ pllDelay: 2, timerInterrupt: false }` for 5000 steps
2. Intercepts ALL reads from port 0x0009 with their exact context: which PC address triggered the read, what step number, what value of A register before/after
3. For each unique PC that reads port 0x0009, disassembles 20 bytes starting from that PC to show what the code does with the value (e.g., BIT test, CP compare, AND mask)
4. Then does a SECOND run with port 0x0009 returning 0x00 instead of 0xFF, and a THIRD run with 0x02 (typical CPU speed register value = 6 MHz mode). Compare: does the unique block count change? Does the loop break?
5. Reports which return value (if any) causes boot to advance past 270 blocks

## Technical Details

In `peripherals.js`, the `createPeripheralBus` function has a `register(port, handler)` method. Port 0x0009 is NOT registered, so reads fall through to default 0xFF at line 198. To test alternative values, register a handler AFTER creating the bus:

```javascript
const peripherals = createPeripheralBus({ pllDelay: 2, timerInterrupt: false });
// Test different port 0x0009 values:
peripherals.register(0x09, { read() { return VALUE; }, write() {} });
```

Note: The register function takes the NORMALIZED port number (0x09, not 0x0009). Check peripherals.js — `normalizePort` does `Number(port) & 0xFFFF`.
