# Task: VRAM Address Offset Investigation

## Context
You are working on the TI-84 Plus CE ROM transpilation project at `C:/Users/rober/Downloads/Projects/school/ti84-transpile`. The ROM is a 4MB eZ80 binary at `TI-84_Plus_CE/ROM.rom`.

Session 484 found a discrepancy: "Normal Float Radian" status text renders at VRAM row 39 (0xD4618C) despite D0059C starting at 0xD40000. The golden regression places it at row 37 (which is correct per the formula: row*20+37 for row 0 → pixel row 37). The question: does the renderer always compute from D00595/D00596, or does D0059C influence rendering?

## Known facts
- VRAM formula (decoded at 0x005A75 in session 480): `addr = 0xD40000 + (row*20+37)*640 + (col*12+2)*2`
- D00595 = cursor row, D00596 = cursor column
- D0059C = VRAM pointer variable (3 bytes). Written at 0x005AB0 by the renderer itself.
- 0x005A48 converts row → pixel row: `pixel_row = row * 20 + 37`
- 0x005A53 converts col → pixel column: `pixel_col = col * 12 + 2`
- The renderer at 0x005A75 COMPUTES D0059C from D00595/D00596 on every call (session 480 confirmed this)
- In session 484, "Normal Float Radian" rendered at VRAM starting at 0xD4618C, which is:
  - Offset from 0xD40000 = 0x618C = 24972 bytes
  - 24972 / 640 = 39.01... → pixel row 39, not 37
  - The expected address for row 0, col 0 with the formula is: 0xD40000 + 37*640 + 2*2 = 0xD40000 + 23680 + 4 = 0xD45C84
  - 0xD4618C - 0xD45C84 = 0x508 = 1288 bytes = 2.0125 pixel rows difference

## Your task
Create a probe `TI-84_Plus_CE/probe-phase485-vram-offset.mjs` that:

1. Boots using the standard 3-stage boot:
   - Stage 1: z80 reset from 0x000000, 20K steps
   - Stage 2: adl from 0x08C331, 200K steps  
   - Stage 3: adl from 0x0802B2, 200K steps
2. After boot, records:
   - D00595, D00596, D0059C values (the post-boot cursor state)
   - D005A0 value (computed pixel row scratch variable)
   - D000B2 value (font mode bits)
   - D00085 value (font control: bit 3 = invert, bit 3 also affects char width 12 vs 14)
3. Sets D00595=0, D00596=0 and renders char 'A' (0x41) via 0x0059C6
4. Records where the VRAM write actually lands (first changed VRAM address)
5. Computes expected address: `0xD40000 + 37*640 + 2*2 = 0xD45C84`
6. Reports the delta between actual and expected
7. Then tests with D0059C set to different values BEFORE calling 0x0059C6 to see if D0059C influences the result or is always overwritten:
   - Test A: D0059C = 0xD40000, render 'B', record first VRAM addr
   - Test B: D0059C = 0xD4618C (the offset address), render 'C' at same D00595=0/D00596=2, record first VRAM addr
   - Test C: D0059C = 0xD50000 (way off), render 'D' at D00595=0/D00596=3, record first VRAM addr
   - If all three produce addresses matching the formula (based only on D00595/D00596), then D0059C is purely an output variable
8. Finally, check what D005A0 contains after boot but BEFORE any rendering call — if it's 39 instead of 37, then boot sets it to a non-formula value that the renderer uses as an override on the first call
