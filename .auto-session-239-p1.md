# Task: Run 0x09EFDE VRAM fill with 60K+ steps to completion

## Context
You are working on a TI-84 Plus CE ROM transpilation project. The ROM is lifted to JavaScript and run via `cpu-runtime.js` + `peripherals.js` + `ROM.transpiled.js`.

Session 238 identified that **0x09EFDE is a VRAM row-fill loop** (not FP computation). It fills VRAM rows with 16-bit pixel color (DE=0xFFFF = white). The inner loop is `LD (HL),E / INC HL / LD (HL),D / INC HL` repeated 2× per iteration with `DJNZ 0x09EFDE`. The outer loop at 0x09EFCB decrements A and adds 0x280 (640 = one VRAM row stride 320×2) to HL. Session 238 found it does NOT complete in 5000 steps — estimated ~60K+ steps needed. Only 4-5 unique blocks in 0x09Exxx range.

The call chain is: 0x04EDD0 → 0x04ECCE → 0x07F984 → 0x08BF22 → 0x09EFDE (VRAM fill).

## Task
Create a probe `TI-84_Plus_CE/probe-phase239-09efde-vram-fill-complete.mjs` that:

1. Boots the CPU (z80 boot → kernelInit → memInit as per existing probes)
2. Seeds the home-screen state (IY=0xD00080, IX=0xD1A860, D007E0=0x40, D003E0=0x00, etc.)
3. Enters at 0x04EDD0 (the shared handler that leads to VRAM fill)
4. Runs with **80,000 step budget** (should be enough for ~60K fill + post-fill code)
5. Tracks:
   - Whether the VRAM fill loop at 0x09EFDE completes (does execution leave the 0x09E000-0x09F000 range?)
   - What block executes AFTER the fill completes (where does it return to?)
   - VRAM content: count non-zero bytes in VRAM region 0xD40000-0xD65400 (320×240×2)
   - Register snapshots every 10000 steps
   - Total unique blocks visited
   - Whether execution eventually returns (hits the RETURN_SENTINEL)

Use the same boilerplate/structure as `probe-phase238-09efde-computation-loop.mjs` (read it first for the boot sequence, imports, and executor setup). The key difference: **much larger step budget** (80000 vs 5000).
