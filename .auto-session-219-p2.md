# Session 219 P2: Trace the 0x05E307 alternate insertion path (BIT 4 CLEAR)

## Context

In the TI-84 Plus CE ROM transpilation project, session 218 discovered a **surprise**: when ConvKeyToTok (0x05E630) is called with BIT 4,(IY+5) CLEAR (not in edit mode), the function STILL writes token 0x31 to the edit buffer at 0xD00A00 — but via an **alternate path**: 0x05E307→0x05E315→0x05E317→0x05E348→0x05E372→0x05E352→0x05E654, which does NOT use BufInsert (0x05E2A0).

This means BIT 4 controls WHICH insertion mechanism is used, not WHETHER insertion happens. We need to understand this alternate path:
1. Is it functionally equivalent to BufInsert?
2. Does it handle multi-byte tokens (2-byte function tokens with prefix)?
3. Does it properly advance the edit cursor?
4. What's different about how it writes vs BufInsert?

## Task

Build probe `TI-84_Plus_CE/probe-phase219-alt-insert-path.mjs` that:

### Part A: Single digit trace with BIT 4 CLEAR
After boot (z80 + kernelInit + postInit + memInit), seed edit buffer (editTop=editCursor=0xD00A00, editTail=editBtm=0xD00B00), set BIT 4 CLEAR (IY+5 = 0x00), call ConvKeyToTok at 0x05E630 with A=0x8F (scan code '1'). Trace ALL visited blocks. Record:
- What gets written to edit buffer (0xD00A00-0xD00A10)
- Edit cursor value (0xD0243A) before and after
- Which specific block does the actual byte write
- How many steps total

### Part B: Multi-digit with BIT 4 CLEAR
Same setup but call ConvKeyToTok 4 times with scan codes 0x8F, 0x90, 0x80, 0x91 ('1', '2', '+', '3'). After each call, record edit buffer contents and cursor position. Between calls, re-seed A with the next scan code and re-push the return sentinel.

### Part C: 2-byte token with BIT 4 CLEAR
Try a function token — use scan code 0x69 (which maps to SIN in 2nd mode via secondary table at 0x05C01D). Or more simply, use A=0x60 (scan code for Y=, which might be a 2-byte token). Actually, from the keytok tables (session 186): scan codes 0x60-0x67 are GRAPH through DEL — these are ≥ 0x5A so they go through the primary table differently. 

Better approach: just test with a standard 1-byte operator token (0x80 = '+', maps to token 0x70) and a letter (0x9A = 'A', maps to token 0x41) to see if the alternate path handles different token types consistently.

### Part D: Compare BIT 4 SET vs CLEAR side by side
Run the same single digit (A=0x8F) with BIT 4 SET, record the path. Then diff the two paths (Part A vs Part D) — which blocks differ, which is the divergence point.

## Boot sequence
Use the standard boot pattern: z80 boot (20000 steps) → kernelInit (100000 steps) → postInit (100 steps) → memInit (100000 steps with MEM_INIT_RET sentinel). Then resetOsState for each experiment.

## Edit buffer seeding pattern
```javascript
write24(mem, 0xD02437, 0xD00A00);  // editTop
write24(mem, 0xD0243A, 0xD00A00);  // editCursor
write24(mem, 0xD0243D, 0xD00B00);  // editTail
write24(mem, 0xD02440, 0xD00B00);  // editBtm
mem.fill(0x00, 0xD00A00, 0xD00B00);  // clear edit buffer
```
