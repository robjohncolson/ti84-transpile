# Auto-Session 203 P1: Investigate 0x09927F Internal Structure

## Context
In the TI-84 Plus CE ROM transpilation project, we're tracing the keyboard dispatch path for digit tokens. The home handler at 0x058514 does `CALL 0x09927F` which is a token validation routine. For digit tokens (type byte 0x30-0x39), this call chain goes: 0x09927F → 0x082C50 → 0x0846EA → 0x08011F (CP 0x5D) → carry set → JP C,JError. This blocks BufInsert.

**Question**: Does 0x09927F have internal branching that could bypass the 0x082C50 path for simple tokens? Maybe it checks the token type/category BEFORE calling 0x082C50 and has a fast-path return for known-good tokens like digits.

## Task
Build a probe `TI-84_Plus_CE/probe-phase203-09927f-internal.mjs` that:

1. **Static disassembly** of 0x09927F: Read ROM bytes starting at 0x09927F and decode at least 40 instructions (or until RET). Use the same disassembly pattern as existing probes (read ROM.rom, decode bytes manually). Look for:
   - CP/SUB instructions (range checks)
   - Conditional jumps BEFORE the CALL 0x082C50
   - Any table lookups or indirect jumps
   - Multiple CALL targets (not just 0x082C50)

2. **Execution traces** with different token types in OP1[1] (0xD005F9):
   - Experiment A: OP1[1] = 0x34 (digit 4, known to fail via CP 0x5D)
   - Experiment B: OP1[1] = 0x62 (known to pass CP 0x5D from session 198)
   - Experiment C: OP1[1] = 0x70 (plus operator token)
   - Experiment D: OP1[1] = 0x5D (exact boundary value for CP 0x5D)
   - For each: trace blocks visited, count steps, note if 0x082C50 is reached, note carry flag at return

3. **Output**: Structured JSON with disassembly + per-experiment results.
