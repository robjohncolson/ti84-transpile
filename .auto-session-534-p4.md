# Task: Decode 0x068640 — Type→Dimension Fallback

## Context
You are working on a TI-84 Plus CE ROM transpilation project. The ROM is at `TI-84_Plus_CE/ROM.rom` (4MB, eZ80 ADL mode). We decode ROM subroutines by writing Node.js probes that read raw bytes and disassemble them.

## Target
**0x068640** — A type→dimension fallback routine. This has been carried as an undecoded priority across sessions 531-533. It's in the 0x06xxxx region (graphing/OS utility code, separate from the main FP engine at 0x07xxxx).

Context from session 531: 0x06868A is a TYPE VALIDATION DISPATCHER (29B+22B) that dispatches based on type: CP 0x20/0x21 → 0x07CFA7, CP 0x1C → 0x07CF1A. The 0x068640 function is likely the fallback path when the type doesn't match equation/string/matrix — possibly handling list (0x1D) or real (0x00) types for dimension extraction.

## What To Do
1. Create `TI-84_Plus_CE/probe-phase534-decode-068640-type-fallback.mjs`
2. Read raw ROM bytes starting at 0x068640. Read at least 100 bytes.
3. Disassemble as **eZ80 ADL mode** (24-bit addresses = 4-byte immediates).
4. Document each instruction with address, raw bytes, mnemonic, and operands.
5. Identify: what types does it handle? Does it read OP1 type byte at 0xD005F8? What CP comparisons does it make? What are the CALL targets?
6. Also check surrounding context: what's at 0x068620-0x06863F (before) and after the routine.
7. Write findings as comments in the probe file.

## eZ80 ADL Opcode Reminders
- `LD rr, nn` uses 4-byte immediates
- `3A xx xx xx` = LD A,(nn), `FE xx` = CP n
- `CA xx xx xx` = JP Z, `C2 xx xx xx` = JP NZ
- `CD xx xx xx` = CALL nn, `C9` = RET
- `E6 xx` = AND n (used for type masking: AND 0x3F strips sign bits)

## Key Type Codes
- 0x00 = Real, 0x0C = Complex, 0x1C = Matrix, 0x1D = List
- 0x20 = Equation, 0x21 = String, 0x18 = Real variant
