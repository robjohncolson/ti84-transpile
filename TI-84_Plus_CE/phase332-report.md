# Phase 332 — Glyph Scaler Call Chain Trace

Generated by `probe-phase332-glyph-scaler.mjs`.

## 1. Function 0x053396 — glyph_add_bias

Transpiled disassembly:
```
0x053396  push ix
0x053398  ld ix, 0x000000
0x05339D  add ix, sp          ; ix = frame pointer
0x05339F  push bc
0x0533A0  dec sp
0x0533A1  dec sp              ; allocate 5 local bytes
0x0533A2  ld bc, 0x0520C3     ; hardcoded ROM constant table
0x0533A6  push bc             ; arg2 for 0x0522B2
0x0533A7  ld bc, (ix+6)       ; arg1 = caller's first argument (glyph bitmap ptr)
0x0533AA  push bc
0x0533AB  nop (ed 65)
0x0533AD  ei
0x0533AE  call 0x0522B2       ; 5-byte ADC addition
0x0533B2  pop bc  x3          ; clean stack
0x0533B5  ld hl, (ix-3)       ; return value in HL
0x0533B8  ld sp, ix
0x0533BA  pop ix
0x0533BC  ret
```

**Arguments**: (ix+6) = 24-bit glyph bitmap pointer from caller.

**What it does**: Calls 0x0522B2 to perform a 5-byte addition (with carry) of the
glyph pointer with a hardcoded bias table at ROM 0x0520C3.

**Bias table at 0x0520C3**: [0x00, 0x80, 0x00, 0x00, 0x00]
  As 5-byte LE value: 0x0000008000
  Byte[1] = 0x80 sets bit 7 of the second byte — this is an FP-style sign/exponent bias.

**Font selection**: 0x053396 does NOT select the font. The glyph bitmap pointer is
passed in by the caller as arg (ix+6). Callers include:
- 0x052569 (from PutC pipeline)
- 0x0546BD, 0x0546E3, 0x054770, 0x054796 (measurement/layout helpers)
All push HL as the glyph pointer before calling. Font selection happens upstream
in the DrawChar vtable dispatch (D005E9+3) which resolves the font table base,
then computes glyph_ptr = font_base + char_index * glyph_stride.

## 2. Function 0x0522B2 — add_5bytes_adc

Transpiled disassembly:
```
0x0522B2  push ix
0x0522B4  ld ix, 0; add ix, sp  ; frame ptr
0x0522BB  push iy
0x0522BD  ld b, 5               ; loop count = 5 bytes
0x0522BF  ld hl, (ix+9)         ; source1 ptr (0x0520C3 bias table)
0x0522C2  ld de, (ix+12)        ; source2 ptr (from upstream caller)
0x0522C5  ld ix, (ix+6)         ; dest ptr (glyph bitmap ptr)
0x0522C8  or a                  ; clear carry
loop:
0x0522C9  ld a, (de)            ; byte from source2
0x0522CA  adc a, (hl)           ; + byte from source1 + carry
0x0522CB  ld (iy+0), a          ; store result
0x0522CE  inc de
0x0522CF  inc hl
0x0522D0  inc iy
0x0522D2  djnz loop             ; repeat 5 times
0x0522D4  ld hl, (ix+6)         ; return dest in HL
0x0522D7  pop iy; pop ix; ret
```

**Purpose**: Multi-precision 5-byte addition with carry. Adds two 5-byte values
byte-by-byte and stores result. Used for FP exponent/mantissa manipulation of
glyph coordinate data.

## 3. Function 0x0533BD — scaler_validate_and_setup

This is the main scaler entry point. It allocates a 71-byte local frame on the
stack and validates glyph dimensions before entering the scale kernel.

Transpiled disassembly (key sections):
```
0x0533BD  push ix; ld ix,0; add ix,sp  ; frame
0x0533C6  push hl
0x0533C7  lea hl, ix-71                 ; allocate 71 bytes of locals
0x0533CA  ld sp, hl
0x0533CB  ld hl, (ix-3)                 ; HL = glyph pointer (from caller's frame)
0x0533CE  call 0x055191                  ; lazy_init (sets IY=D00080, checks bit 1)

  ;; Dimension validation (ix+12, ix+15, ix+21 vs 0x000E10 = 3600)
0x0533D2  ld hl, (ix+12)
0x0533D5  call 0x000138                  ; sign_test(HL) — HL - 0 → flags
0x0533D9  jp m, 0x053AD4                 ; if width < 0 → abort (return)
0x0533DD  ld hl, (ix+15)
0x0533E0  call 0x000138
0x0533E4  jp m, 0x053AD4                 ; if height < 0 → abort
0x0533E8  ld hl, (ix+21)
0x0533EB  call 0x000138
0x0533EF  jp p, 0x053405                 ; if stride >= 0 → check vs max

  ;; If stride < 0: negate and clamp
0x0533F3  ld bc,(ix+18); add hl,bc; ld (ix+18),hl  ; adjust base
0x053405  ld bc, 0x000E10                ; max = 3600
0x05340A  sbc hl, bc
0x05340C  jp m, 0x05341B                 ; if dim < 3600 → use font table lookup
  ;; else: clamp (HL = dim, BC = 3600 → use 3600)
0x053410  ld (ix-3), bc; sbc hl,hl; ld (ix+18), hl
  ;; → falls through to 0x05342C

  ;; 0x05342C: scale-level-aware glyph layout
0x05342C  ld a, (0xD005EC)              ; A = scale_level (0..3)
0x053430  add a, a                       ; A = scale_level * 2
0x053431  inc a                          ; A = scale_level * 2 + 1
0x053432  ld (ix-70), a                  ; store as "effective scale"

  ;; Adjust all 4 dimension args by effective_scale:
  ;; (ix-6)  = arg_width  - effective_scale
  ;; (ix-9)  = arg_height - effective_scale
  ;; (ix-12) = arg_hStride + 2*effective_scale
  ;; (ix-15) = arg_vStride + 2*effective_scale
```

**Arguments to 0x0533BD** (on the stack, accessed via IX):
| IX offset | Meaning |
|-----------|---------|
| (ix-3) | glyph bitmap pointer (from 0x053396 return) |
| (ix+6) | glyph pixel width |
| (ix+9) | glyph pixel height |
| (ix+12) | horizontal stride (bytes per row in output) |
| (ix+15) | vertical stride (VRAM row pitch) |
| (ix+18) | output base address (VRAM or buffer) |
| (ix+21) | secondary stride / row skip |

**Between glyph data and 0x053540**: The function validates all dimensions are
non-negative and <= 3600 (0xE10), calls lazy_init (0x055191) to ensure IY=D00080
with font state initialized, then computes scale-adjusted dimensions using
D005EC (scale_level). It stores the effective scale factor (2*level+1) at (ix-70)
and adjusted dimensions at ix-6 through ix-15, then falls through to 0x053540.

## 4. Function 0x053540/0x05354C — scale_config_load

0x053540 stores the multiplication result (from 0x000154 = 24-bit multiply at
0x053533) and zeros out working accumulators:
```
0x053540  ld (ix-51), hl       ; store multiply result
0x053543  or a; sbc hl, hl      ; HL = 0
0x053546  ld (ix-54), hl        ; zero accumulator 1
0x053549  ld (ix-48), hl        ; zero accumulator 2
  ;; falls through to 0x05354C
```

0x05354C loads the scale configuration:
```
0x05354C  ld bc, (0xD005ED)    ; BC = font-metric config (default 0x000FFF)
0x053551  ld (ix-57), bc        ; store config
0x053554  ld a, (0xD005EC)      ; A = scale_level (0..3)
0x053558  inc a                  ; A = level + 1
0x053559  ld (ix-70), a          ; store as "scale factor"
0x05355C  inc a                  ; A = level + 2
0x05355D  sra a                  ; A = (level + 2) >> 1 (arithmetic shift right)
0x05355F  ld (ix-71), a          ; store as "half scale factor"

  ;; Check if D005ED == 0x000FFF (default / identity config)
0x053562  ld hl, (ix-57)        ; reload config
0x053565  ld bc, 0x000FFF
0x05356A  sbc hl, bc
0x05356C  jr nz, 0x053573       ; if config != 0xFFF → use scale kernels
  ;; If config == 0xFFF (identity):
0x05356E  ld a, 0xFF
0x053570  ld (ix-71), a          ; set half_scale = 0xFF (sentinel for "no scaling")
  ;; falls through to 0x053573
```

**D005ED significance**: Default value 0x000FFF (loaded from ROM 0x05323F during
init at 0x0551B2). When it equals 0xFFF, the scaler uses identity/no-scale mode.
When non-0xFFF, the scale kernel table is consulted.

**D005ED default**: 0x000fff (from ROM 0x05323F)

## 5. Function 0x053573 — scale_kernel_dispatch

Loads 4 kernel pointers from the current scale record, then decides
whether to run the scale loop or skip to the output copier.
```
0x053573  push iy
0x053575  ld iy, (0xD005F0)    ; IY = scale record ptr (0x05320F + level*12)
0x05357A  ld bc, (iy+9)        ; kernel ptr 4: vertical repeat
0x05357D  ld (ix-60), bc
0x053580  ld bc, (iy+3)        ; kernel ptr 2: vertical height
0x053583  ld (ix-63), bc
0x053586  ld bc, (iy+0)        ; kernel ptr 1: horizontal width
0x053589  ld (ix-66), bc
0x05358C  ld bc, (iy+6)        ; kernel ptr 3: horizontal repeat
0x05358F  ld (ix-69), bc
0x053592  pop iy

  ;; Check if scale < 1 → skip
0x053594  ld a, (ix-70)        ; A = scale factor (level + 1)
0x053597  cp 1
0x053599  jp c, 0x0536A0       ; if scale < 1 → skip to output path
0x05359D  jp z, 0x0536A0       ; if scale == 0 → skip (Z set means equal to 1??)
  ;; Actually: cp 1 sets C if A<1 (i.e. A==0). Z if A==1.
  ;; So: scale==0 → C,skip. scale==1 → Z,skip. scale>=2 → run kernels.
```

After the skip check, 0x0535A1+ runs the actual scaling loop which iterates
through glyph rows/columns, applying the scale coefficients from the kernel
records to expand/contract the glyph bitmap into the output buffer.

## 6. Scale Record Table at 0x05320F

Each scale level has a 12-byte record containing 4 three-byte pointers to
scale kernel coefficient tables. Format: [hWidth, vHeight, hRepeat, vRepeat]

| Level | Record Addr | hWidth Kernel | vHeight Kernel | hRepeat Kernel | vRepeat Kernel |
|-------|-------------|---------------|----------------|----------------|----------------|
| 0 | 0x05320f | 0x053182 | 0x053182 | 0x053182 | 0x053182 |
| 1 | 0x05321b | 0x053183 | 0x053188 | 0x053191 | 0x053196 |
| 2 | 0x053227 | 0x05319f | 0x0531a8 | 0x0531b5 | 0x0531be |
| 3 | 0x053233 | 0x0531cb | 0x0531d8 | 0x0531ed | 0x0531fa |

### Kernel coefficient records

Each kernel record starts with a count byte N, followed by N 2-byte LE
signed coefficient pairs. These control pixel replication/interpolation.

**0x053182**: N=1, coefficients=[-253]
**0x053183**: N=3, coefficients=[255, 2, -251]
**0x053188**: N=5, coefficients=[511, -256, 2, -256, 3]
**0x053191**: N=3, coefficients=[-256, 512, 261]
**0x053196**: N=5, coefficients=[257, -256, 254, -256, -507]
**0x05319f**: N=5, coefficients=[254, 1, 3, 255, -505]
**0x0531a8**: N=7, coefficients=[510, 1, -256, 2, -256, 1, 5]
**0x0531b5**: N=5, coefficients=[-512, 256, 768, -256, 519]
**0x0531be**: N=7, coefficients=[258, 255, -256, 254, -256, 255, -761]
**0x0531cb**: N=7, coefficients=[253, 1, 1, 2, 2, 255, -757]
**0x0531d8**: N=11, coefficients=[765, 1, -256, 1, -256, 2, -256, 1, -256, 1, 7]
**0x0531ed**: N=7, coefficients=[-768, 256, 256, 512, 512, -256, 779]
**0x0531fa**: N=11, coefficients=[515, 255, -256, 255, -256, 254, -256, 255, -256, 255, 12674]

Level 0: all 4 pointers → 0x053182 (N=1, coeff=[-1]) — identity/1x scale.
Level 1: 2x scale kernels (N=3..5 coefficients per axis).
Level 2: 3x scale kernels (N=5..7).
Level 3: 4x scale kernels (N=7..11).

## 7. Glyph Bitmap Format

### Alt/small font at ROM 0x0A3AFA

The bytes at 0x0A3AFA appear to be CODE (not font data). The alt font table
is likely referenced indirectly. The first non-zero glyph-like data near this
address starts at offset +0x12:
  Bytes: 08 cd dc ff 07 cd 5b f5 05 cd be 32 08 e1 c9 0b 00 00 00 00 00 00 00 00 cf 00 ff 00 31 80 31 80

### Width table

The glyph bitmap is fixed-size (28 bytes, 16px wide), but the RENDERED width
is determined by the scaler using the dimension arguments passed to 0x0533BD.
The font-decoder.mjs renderer uses only the top 5 bits of each byte (10px
effective width) based on empirical matching with the ROM renderer output.
There is no separate per-glyph width table — all glyphs are the same fixed
width in the bitmap, with variable visual width achieved by blank padding.

## 8. Output Destination — Where Does the Scaled Glyph Go?

### Flow after 0x053573

After 0x053573 loads the 4 scale kernel pointers into IX locals:

1. **Scale check**: If scale_factor < 2 (level 0 = no scaling), jumps to 0x0536A0
2. **0x0536A0** (output loop): Processes each output row:
   ```
   0x0536A0  ld hl, (ix-51)     ; current output address
   0x0536A3  ld bc, (ix-54)      ; row counter / accumulator
   0x0536A6  or a; sbc hl, bc
   0x0536A9  call 0x000218        ; sign_extend_test
   ```
   This loops through the glyph bitmap data, calling the scale kernel
   (0x05324B via the coefficient tables) for each row/column pair, and
   writes the expanded pixels.

3. **The output address** is computed from the arguments to 0x0533BD:
   - (ix+18) = output base address
   - (ix+12) = horizontal stride (bytes between pixels)
   - (ix+15) = vertical stride (bytes between rows, typically VRAM_WIDTH * 2 = 640)

### Direct VRAM writes

The scaled output goes **directly to VRAM** at 0xD40000. There is no intermediate
buffer. The callers (in the PutC pipeline and text renderers) compute the output
address as:

```
output_addr = VRAM_BASE + (pen_y * VRAM_WIDTH + pen_x) * 2
h_stride = 2  (bytes per pixel, RGB565)
v_stride = VRAM_WIDTH * 2 = 640  (bytes per row)
```

The scale kernel uses the 0x05324B helper (which calls 0x052442) to compute
actual pixel positions with scale factors applied, then writes RGB565 pixel
values directly at the computed VRAM offsets.

### Pixel writer integration

The entire chain feeds into the pixel writer layer that Session 329 documented.
The scale kernel does NOT call a separate pixel-writer function — it IS the
pixel writer for scaled text. The alpha-blend/write logic is embedded in the
scale loop at 0x0535xx-0x0537xx, which reads glyph bits and writes 16-bit
RGB565 values to the VRAM address computed from the base + stride parameters.

## 10. Summary — Complete Call Chain

```
Caller (PutC pipeline / text renderer)
  │ pushes: glyph_ptr, width, height, h_stride, v_stride, output_base, row_skip
  ▼
0x053396 — glyph_add_bias
  │ Adds 5-byte FP bias (0x0520C3: {00,80,00,00,00}) to glyph pointer
  │ via 0x0522B2 (5-byte ADC loop)
  │ Returns: biased glyph pointer in HL
  ▼
0x0533BD — scaler_validate_and_setup
  │ Allocates 71-byte frame. Calls 0x055191 (lazy_init).
  │ Validates width, height, stride all ≥ 0 and ≤ 3600.
  │ Reads D005EC (scale_level), computes effective_scale = 2*level+1.
  │ Adjusts all 4 dimensions by effective_scale.
  ▼
0x053540 — store_multiply_result_and_zero_accumulators
  │ Stores result from 24-bit multiply (0x000154), zeros accumulators.
  ▼
0x05354C — scale_config_load
  │ Loads D005ED (font metric config, default 0xFFF).
  │ Computes scale_factor = level+1, half_scale = (level+2)>>1.
  │ If config == 0xFFF → sets half_scale = 0xFF (identity sentinel).
  ▼
0x053573 — scale_kernel_dispatch
  │ Loads IY = (D005F0) = scale record pointer.
  │ Copies 4 kernel pointers from record into IX locals:
  │   (iy+0) → (ix-66) = hWidth kernel
  │   (iy+3) → (ix-63) = vHeight kernel
  │   (iy+6) → (ix-69) = hRepeat kernel
  │   (iy+9) → (ix-60) = vRepeat kernel
  │ If scale_factor < 2: skip → 0x0536A0 (direct copy, no scaling).
  ▼
0x0535A1+ — scale_loop (for scale ≥ 2)
  │ Iterates rows × columns, applies kernel coefficients
  │ to replicate/interpolate glyph pixels.
  ▼
0x0536A0 — output_row_loop
  │ Processes output rows, writes scaled pixels.
  │ Output goes DIRECTLY to VRAM at computed address:
  │   addr = output_base + row * v_stride + col * h_stride
  │ No intermediate buffer — writes RGB565 directly to 0xD40000+ region.
  ▼
VRAM (0xD40000)
```

### Key answers

1. **Font selection**: Happens UPSTREAM of this chain. The DrawChar vtable
   dispatch (D005E9+3) selects main font (0x0040EE) or alt font, computes
   glyph_ptr = font_base + (char - 0x20) * 28, and passes it as an argument.

2. **Glyph bitmap format**: Fixed 28 bytes/glyph, 16px × 14 rows, 1 bit/pixel,
   2 bytes/row, MSB-first. No per-glyph width table.

3. **Output destination**: Directly to VRAM (0xD40000+). No intermediate buffer.
   The output address and strides are passed as arguments from the PutC pipeline.

4. **Scale behavior**: Level 0 → identity (skip scaling loop). Levels 1-3 use
   coefficient tables from the kernel records at 0x053182-0x05320E to expand
   glyphs by 2x, 3x, or 4x.
