## Summary

- ★★★★ `0x0907DB` is a token-size resolver. It calls token lookup `0x0A2B53`, gate helper `0x090992`, and token-data pointer helper `0x026024`, then returns the byte size in A.
- ★★★ `0x09091C` is not a function entry. It is the first conditional return inside the forward token-pointer walker entered at `0x090918`.
- ★★★ Dynamic keypress trace confirms the live path: `0x0907DB` hit 87x, `0x090992` hit 175x, `0x090918` hit 294x, `0x09091C` hit 783x, and the run halted cleanly at `0x0019B5`.
- ★★★ The D02A29 cursor-position accumulator advances in byte units, usually by `0x000C` chunks in this run, and is reset by the later `0x0018F8` cleanup.

The runaway seen in earlier seeded same-executor probes is therefore a caller/walker loop repeatedly re-entering this interior sequence, not a standalone routine at `0x09091C`.

## Implications

The seeded same-executor maxSteps path from session 617 is best explained as stale caller state causing repeated entry into the `0x090918` forward walker. `0x09091C` itself is only `RET Z`; it cannot be the root mechanism. The real control requirements are upstream:

- keep `(IY+0x23)` bit 3 and edit cursor/boundary pointers coherent before entering the walker;
- keep `D02A28` live only at the consumer gate if token-buffer output is desired;
- snapshot/restore transient token buffers or VRAM after the structural cleanup, as sessions 618-619 proved.
