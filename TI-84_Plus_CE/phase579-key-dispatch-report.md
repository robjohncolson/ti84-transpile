# Phase 579: Key Dispatch Cascade at 0x08C3C3

Generated by `probe-phase579-decode-key-dispatch.mjs`.

## Overview

After key input via `CALL 0x0A27DD`, the event loop at 0x08C331 dispatches based on the
internal key code in register A. The dispatch cascade at 0x08C3C3-0x08C5D7 is a series
of CP instructions that route to different handlers. These are **internal OS key codes**
(post-translation from `_GetKey`, not raw `_GetCSC` scan codes).

## Key Code Namespace

The dispatched values are NOT raw scan codes or direct translation table outputs for most
cases. They are processed "internal key codes" in the TI-OS `_GetKey` namespace:

- `0x01-0x0F`: Control codes (arrows, enter, clear, del)
- `0x28-0x29`: ASCII `(` and `)` (parentheses)
- `0x30-0x3E`: Digit/punctuation ASCII
- `0x41-0x5A`: Letter/app mode codes (A-Z range)
- `0x5B-0x75`: App/context mode codes
- `0x80-0xBF`: Function/token codes
- `0xC0-0xFF`: Special OS function codes (catalog, format, etc.)

## Detailed Flow Analysis

### Stage 1: Quit Check (0x08C3C3-0x08C3ED)

```
0x08C3C3: CP 0xB4          ; is it QUIT?
0x08C3C5: CALL Z, 0x07BF19 ; if yes, call quit handler
0x08C3C9: RES 1,(IY+40)    ; clear flags regardless
0x08C3CD: RES 2,(IY+40)
0x08C3D1: BIT 5,(IY+52)    ; test flag
0x08C3D5: JR Z, 0x08C3EE   ; skip if clear -> go to stage 2
0x08C3D7: CALL 0x02392F    ; call helper
0x08C3DB: BIT 1,(IY+40)    ; re-check flag
0x08C3DF: JP NZ, 0x08C331  ; if set -> back to event loop top
0x08C3E3: BIT 2,(IY+40)
0x08C3E7: JR Z, 0x08C3EE   ; -> stage 2
0x08C3E9: PUSH AF
0x08C3EA: JP 0x08C532      ; -> common dispatch with AF on stack
```

Notes:
- 0xB4 triggers `CALL Z` (not a jump), so the quit handler returns and
  execution continues with flag cleanup.
- IY+40 bits 1,2 and IY+52 bit 5 are context flags that gate further processing.

### Stage 2: App/Context Filter (0x08C3EE-0x08C44C)

```
0x08C3EE: CP 0x3F          ; question mark?
0x08C3F0: JR Z, 0x08C40F   ; -> stage 3 common entry
0x08C3F2: CALL 0x084989    ; "try app handler" -- tests if current app handles key
0x08C3F6: CALL C, 0x0224A3 ; if carry (app handled), call helper
0x08C3FA: JR C, 0x08C449   ; if handled -> JP 0x08C331 (back to loop)
0x08C3FC: OR A
0x08C3FD: JP Z, 0x08C543   ; if A=0, key consumed -> exit via flag check
0x08C401: CALL 0x04E0E4    ; another filter
0x08C405: JR C, 0x08C449   ; if handled -> back to loop
0x08C407: LD B, A           ; save key code
0x08C408: LD A, (0xD007E0)  ; load current mode
0x08C40C: CP 0x58           ; mode == 0x58?
0x08C40E: LD A, B           ; restore key code
0x08C40F: JP Z, 0x08C509   ; if mode == 0x58 OR key == 0x3F/0x28/0x29 -> common processing
0x08C413: CP 0x28           ; left paren?
0x08C415: JR Z, 0x08C40F
0x08C417: CP 0x29           ; right paren?
0x08C419: JR Z, 0x08C40F
0x08C41B: JR 0x08C44D      ; -> stage 4 (high-code dispatch)
```

Key insight: 0x3F, 0x28, 0x29 all route to the same place (0x08C509 common
processing). The 0x58 check at 0x08C40C is a **mode check** on D007E0, not a key
code dispatch -- if the current screen mode is 0x58, all keys go to common processing.

### Stage 3: Token Handler Loop (0x08C41D-0x08C449)

This block is only reached via `JP Z, 0x08C41D` from 0x08C53F (after common
processing returns with Z flag set).

```
0x08C41D: CALL 0x0227B5    ; "begin token insert"
0x08C421: SET 0,(IY+93)    ; set "inserting token" flag
0x08C425: LD B, 0x08        ; up to 8 characters
0x08C427: LD HL, 0xD0065A   ; token string table
0x08C42B: INC HL / LD A,(HL) / OR A / JR Z ... ; iterate
0x08C435: CALL 0x05C5B3    ; insert character
0x08C439: CALL 0x08C72F    ; update display
0x08C443: DJNZ 0x08C42B    ; loop for up to 8 chars
0x08C445: RES 0,(IY+93)    ; clear flag
0x08C449: JP 0x08C331      ; back to event loop
```

This is the **multi-character token insertion loop**. When a key maps to a
multi-char token (like "sin("), it inserts up to 8 characters from the string
table at D0065A.

### Stage 4: High-Code Dispatch (0x08C44D-0x08C4ED)

```
0x08C44D: CP 0x7F          ; >= 0x7F?
0x08C44F: JP C, 0x08C59B   ; if < 0x7F -> printable char handler
0x08C453: CP 0xFE          ; format key?
0x08C455: JP Z, 0x08C509   ; -> common processing
0x08C459: CP 0xFC          ; recall key?
0x08C45B: JP Z, 0x08C509   ; -> common processing
0x08C45F: CP 0xFA          ; catalog key?
0x08C461: JR NZ, 0x08C49F  ; if not -> check 0xFB
```

The < 0x7F boundary separates "printable" keys (digits, letters, operators) from
"function" keys (trig, catalog, format, etc.).

### Stage 5: Catalog Handler (0x08C463-0x08C49D) -- key 0xFA

```
0x08C463: LD A, (0xD0058E) ; load previous key code
0x08C467: OR A / JR Z ...  ; if no previous key -> load from D0058C
0x08C46A: CP 0x44          ; previous == 0x44 (DOWN arrow context)?
0x08C46C: JR NC, 0x08C4B2  ; if >= 0x44 -> JP 0x08C543
0x08C46E: CP 0x15          ; previous == ','?
0x08C470: LD HL, 0x027272  ; load handler address
0x08C474: JR Z, 0x08C48B   ; if comma -> LDIR 9 bytes to D0082E
0x08C476: CP 0x19          ; previous == '.'?
0x08C478: JR NZ, 0x08C49B  ; if not -> LD A,0xFA; JR 0x08C509
0x08C47A: CALL 0x027233    ; period handler
0x08C48B: LD DE, 0xD0082E  ; destination
0x08C48F: LD BC, 0x000009  ; 9 bytes
0x08C493: LDIR             ; copy handler descriptor
0x08C495: LD A, 0x58       ; set mode to 0x58
0x08C497: JP 0x08C5D7      ; -> app mode switch handler
```

This is a **context-dependent catalog handler**. It checks the previous key code
(D0058E) and sets up a 9-byte handler descriptor at D0082E.

### Stage 7: Code Remapping (0x08C4ED-0x08C507)

```
0x08C4ED: CP 0xEF         ; remap: 0xEF -> 0xA6
0x08C4F5: CP 0xF9         ; remap: >= 0xF9 -> subtract 0x14
0x08C4FD: CP 0xF3         ; remap: >= 0xF3 -> subtract 0x7C

This remaps high function codes to token indices before storing in D0058E:
- 0xEF -> 0xA6
- 0xF9-0xFF -> subtract 0x14 (0xF9->0xE5, 0xFA->0xE6, etc.)
- 0xF3-0xF8 -> subtract 0x7C (0xF3->0x77, 0xF4->0x78, etc.)

### Stage 8: Common Key Processing (0x08C509-0x08C53F)

This is the main convergence point. All "normal" keys end up here.

```
0x08C509: CP 0x69         ; menu key? -> remap to 0xFC
0x08C511: CP 0x5B         ; table key? -> remap to 0xFD
0x08C519: CP 0x28         ; left paren? -> SET 7,(IY+22), remap to 0xDA
0x08C527: CP 0x29         ; right paren? -> SET 1,(IY+29), remap to 0x7F
0x08C532: CALL 0x022331   ; **key processing subroutine** (main handler)
0x08C536: CALL 0x08C72F   ; update display
0x08C53A: RES 4,(IY+9)    ; clear flag
0x08C53E: POP AF
0x08C53F: JP Z, 0x08C41D  ; if Z -> token insert loop (stage 3)
```

Key remappings at this stage:
- 0x69 -> 0xFC (menu)
- 0x5B -> 0xFD (table)
- 0x28 -> 0xDA (left paren, with flag IY+22 bit 7)
- 0x29 -> 0x7F (right paren, with flag IY+29 bit 1)

Then CALL 0x022331 does the actual key insertion/execution.
CALL 0x08C72F does display refresh.

### Stage 10: Printable Character Handler (0x08C59B-0x08C606)

For all key codes < 0x7F (printable characters).

```
0x08C59B: LD B, A
0x08C59C: LD A, (D007E0)   ; check mode
0x08C5A0: CP 0x5B          ; mode == 0x5B? -> common processing

0x08C601: CALL 0x08C7AD    ; **app mode switch handler**
0x08C606: JP 0x08C519      ; -> common processing (stage 8)

## Summary

The key dispatch is a cascading filter with 3 major categories:

1. **Special keys** (0xB4=QUIT, 0xFA=catalog, 0xFB=2nd-function): handled inline
   with context-dependent logic.
2. **Printable characters** (< 0x7F): routed to mode-dependent handler at 0x08C59B
   that checks current app mode before inserting.
3. **Function codes** (0x7F-0xFF): remapped to token indices, stored in D0058E,
   then processed via CALL 0x022331.

All paths converge to CALL 0x022331 (main key processor) + CALL 0x08C72F (display
refresh), or directly back to the event loop at JP 0x08C331/0x08C33D.
