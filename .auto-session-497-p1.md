# Task: Decode 0x06002D — Cursor-to-VRAM Address Calculator

## Context
This is the TI-84 Plus CE ROM transpilation project. We lift eZ80 machine code from `TI-84_Plus_CE/ROM.rom` into JavaScript and run it in a browser shell.

Session 496 discovered that putchar (0x061980) calls 0x06002D between the character preprocessor (0x061434) and the pixel renderer (0x0A23E5). 0x06002D reads D00595 (cursor row) and D00596 (cursor column) and computes the VRAM write address. Understanding this function reveals the complete row/column-to-pixel mapping.

## What to do

Create a probe file `TI-84_Plus_CE/probe-phase497-decode-06002D.mjs` that:

### Part 1: Static disassembly
1. Load the ROM from `TI-84_Plus_CE/ROM.rom`
2. Disassemble 0x06002D instruction-by-instruction using the eZ80 decoder at `TI-84_Plus_CE/ez80-decoder.js`
3. Follow the code until RET, tracking all branches
4. Print each instruction with address, hex bytes, and mnemonic
5. Note all references to D00595, D00596, D008D2, D008D5 (LCD window regs), and any VRAM addresses (0xD40000+)
6. Note all CALL/JP targets

### Part 2: Dynamic tests
1. Use the executor pattern from existing probes. Here's the pattern:

```javascript
import { readFileSync } from 'fs';
import { createCPU } from './cpu-runtime.js';
import { createPeripheralBus } from './peripherals.js';

const rom = readFileSync('TI-84_Plus_CE/ROM.rom');
const peripherals = createPeripheralBus({ timerInterrupt: false });
const cpu = createCPU(peripherals);

// Load ROM
for (let i = 0; i < rom.length; i++) cpu.mem[i] = rom[i];

// Load transpiled code
const transpiledPath = 'TI-84_Plus_CE/ROM.transpiled.js';
// Check if .js exists, if not gunzip from .gz
import { existsSync, writeFileSync } from 'fs';
import { execSync } from 'child_process';
if (!existsSync(transpiledPath)) {
  execSync('gzip -dk TI-84_Plus_CE/ROM.transpiled.js.gz');
}
const transpiledCode = readFileSync(transpiledPath, 'utf-8');
new Function('cpu', transpiledCode)(cpu);
```

2. For dynamic tests, set up CPU state to call 0x06002D with different cursor positions:
   - Test A: D00595=0 (row 0), D00596=0 (col 0)
   - Test B: D00595=5 (row 5), D00596=10 (col 10)
   - Test C: D00595=9 (row 9), D00596=25 (col 25)
   
3. For each test:
   - Set IY=0xD00080 (the OS IY base)
   - Write cursor row to D00595, cursor column to D00596
   - Set PC=0x06002D, SP=0xD1A87E
   - Step until RET or 2000 steps max
   - After return, capture: all register values (especially HL, DE, BC), any values written to D008D2/D008D5, step count
   
4. Print results showing how the VRAM address changes with row/col. The goal is to determine the formula: VRAM_addr = f(row, col).

### Important constraints
- Use `import` syntax (ES modules, .mjs file)
- The ROM is 4MB, loaded into cpu.mem starting at offset 0
- IY is always 0xD00080 for TI-OS
- D00595 = IY + 0x515 relative to 0xD00000 base
- D00596 = IY + 0x516
- VRAM starts at 0xD40000 (320×240×2 = 153,600 bytes, RGB565)
- `createPeripheralBus({ timerInterrupt: false })` — always disable timer IRQ
- Run via: `node scripts/run-probe.mjs --max-time 180 TI-84_Plus_CE/probe-phase497-decode-06002D.mjs`

### Deliverables
- `TI-84_Plus_CE/probe-phase497-decode-06002D.mjs` — the probe file
- Run the probe and report results

### Success criterion
The probe runs successfully and reports:
1. Full disassembly of 0x06002D showing the VRAM address computation
2. Dynamic test results showing register values after return for each cursor position
3. The derived formula: how row/col maps to pixel coordinates and VRAM offset
