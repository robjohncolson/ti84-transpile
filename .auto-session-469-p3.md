# Task: Test 0x030078 directly — enter the real key wait loop with a key injected

## Context
This is a TI-84 Plus CE ROM transpilation project. The ROM is transpiled to JavaScript. The runtime is at `TI-84_Plus_CE/cpu-runtime.js` and peripherals at `TI-84_Plus_CE/peripherals.js`.

0x030078 is the **real key wait loop** — called from a computed jump table at 0x021AB8 (mode dispatcher). Previous sessions confirmed that 0x003A0F (the error handler) is a DEAD END for key processing. The normal path is: mode dispatcher → 0x030078 → polls for key → calls 0x03FA09 (key processor).

## What to do
Create a probe at `TI-84_Plus_CE/probe-phase469-test-030078.mjs` that:

1. Look at an existing probe to understand the boot and API patterns. Read `TI-84_Plus_CE/probe-phase466-combined-fix.mjs` or `TI-84_Plus_CE/probe-phase468-direct-0x003A0F-v2.mjs` for how to:
   - Load the transpiled ROM
   - Create CPU and peripherals
   - Boot the OS (3-stage boot to 0x021A3C)
   - Inject keys
   - Run execution with tracking

2. After the standard 3-stage boot, inject ENTER key (scan code 0x09):
   - Set `cpu.mem[0xD00587] = 0x09` (scan code for _GetCSC)
   - Set `cpu.mem[0xD00080] |= 0x08` (bit 3 = key available flag)
   - Call `peripherals.keyDown(0x10)` if the API supports it, for matrix state

3. Enter at 0x030078 and run for up to 2M steps. Use `executeTo` or whatever API the existing probes use.

4. Track and report:
   - Whether 0x03FA09 (key processor) is reached
   - Whether 0x003D5A (_GetCSC) is called
   - Whether 0x040D40 is called
   - Whether 0x003A0F (error handler) is reached — should NOT be
   - Value of D00587 and D00080 at completion
   - Where execution terminates and why
   - VRAM snapshot at 0xD40000 (first 256 bytes, hex dump)
   - Total steps taken

5. Set up address hit counting like existing probes do. Check the probe files for the pattern — typically involves patching block functions or using the executor's tracking features.
