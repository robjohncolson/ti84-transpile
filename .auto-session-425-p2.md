# Task: Decode 0x00CBE9 Secondary Descriptor Constructor

## Context
You are working on a TI-84 Plus CE ROM (eZ80) transpilation project. The ROM is at `TI-84_Plus_CE/ROM.rom` (4 MB, eZ80 machine code). The transpiler lifts ROM bytes into JavaScript. You write probes (Node.js scripts) that disassemble and trace ROM functions.

## Background
0x00CBE9 is a secondary descriptor constructor called 5× by 0x00CD7B (the 1394-byte descriptor-table builder). It is NOT called by 0x00EB31 (the single-descriptor builder). This suggests it fills additional fields that single-descriptor transfers don't need.

0x00CB7B is the primary descriptor constructor (called 6× total by both callers). 0x00CBE9 is always called AFTER 0x00CB7B by the same caller (0x00CD7B), suggesting it extends the node with additional data.

Related functions:
- 0x00CB7B: primary descriptor constructor (6 callers)
- 0x00CD7B: 1394-byte descriptor-table builder (calls both 0x00CB7B and 0x00CBE9 5× each)
- 0x00EB31: 582-byte single-descriptor builder (calls only 0x00CB7B)
- 0x00E06D: slab allocator (351 bytes)
- 0x00E1CC: slab free (287 bytes)

## What to do

1. Create a probe script `TI-84_Plus_CE/probe-phase425-trace-00CBE9.mjs` that:
   - Reads `TI-84_Plus_CE/ROM.rom` as a binary buffer
   - Disassembles bytes starting at 0x00CBE9 using eZ80 instruction decoding
   - Continue until you hit a RET (0xC9) that's not inside a conditional block
   - For each instruction, print: address, hex bytes, mnemonic, operands
   - Identify all CALL targets, RAM reads/writes, port I/O, and stack frame setup
   - Determine the function's exact byte length
   - NOTE: 0x00CB7B starts at 0x00CB7B. If 0x00CBE9 starts inside or immediately after 0x00CB7B, document whether they share code (tail-call, fall-through, etc.)

2. Create a report `TI-84_Plus_CE/phase425-trace-00CBE9-report.md` summarizing:
   - Exact address range (start-end) and byte count
   - What arguments it takes (check IX+6, IX+9, etc.)
   - What additional fields it writes beyond what 0x00CB7B writes
   - All CALL targets with their known identities
   - All RAM variables read/written
   - Relationship to 0x00CB7B (shared code? shared data structures?)

## Reference: eZ80 instruction encoding
- The eZ80 is a Z80 superset with 24-bit addressing
- Common prefixes: 0xDD=IX, 0xFD=IY, 0xED=extended, 0xCB=bit ops
- CALL nn = 0xCD followed by 3 bytes (24-bit address, little-endian)
- RET = 0xC9
- LD A,(nn) = 0x3A + 3-byte address
- LD (nn),A = 0x32 + 3-byte address
- RST 0x08 = 0xCF (debug assertion)
- Common prologue: CALL 0x00218A or CALL 0x002197 (__frameset)
