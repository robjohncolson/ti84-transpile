# Task: Test Direct RAM Injection for Keyboard Input

## Context
You are working on a TI-84 Plus CE ROM transpilation project at `C:/Users/rober/Downloads/Projects/school/ti84-transpile`.

Session 372 discovered that `_GetCSC` at 0x003D5A checks bit 3 of (IY+0) = 0xD00080 for "key available." If set, it reads the scan code from 0xD00587 and returns it in A. If not set, it calls 0x003C63 (keyboard scan), delays, repeats 52 times, then returns A=0.

Currently, keyboard matrix state has ZERO effect on the event loop — _GetCSC always returns 0 because bit 3 of 0xD00080 never gets set. We hypothesize that directly writing to 0xD00587 (scan code) and setting bit 3 of 0xD00080 will make _GetCSC return the key.

## What to do
Write a Node.js probe at `TI-84_Plus_CE/probe-phase373-direct-ram-inject.mjs` that:

1. Boots the OS through phases 1-3 using the standard 4-phase boot pattern
2. Before entering the event loop (phase 4 at 0x003A73), directly inject a key:
   ```javascript
   mem[0xD00587] = 0x09;  // ENTER scan code
   mem[0xD00080] |= 0x08; // Set bit 3 (key available flag)
   ```
3. Runs the event loop for 200,000 steps
4. Tracks:
   - Whether _GetCSC (block 0x003D5A) exits via the "key available" path at 0x003D75
   - Whether the dispatch path at 0x003A7D is reached (JR NZ after OR A check)
   - What blocks are visited after dispatch (new territory vs same loop)
   - Whether mem[0xD00587] gets cleared by _GetCSC (session 372 says it should)
   - Whether bit 3 of mem[0xD00080] gets cleared after key consumption
5. Runs a SECOND pass WITHOUT the RAM injection (control group) for comparison
6. Prints a summary: unique blocks with injection vs without, new blocks found, dispatch path reached (yes/no)


Phase 1: boot from 0x000000 for 20000 steps (timerInterrupt: false)  
Phase 2: CoorMon from 0x08C331 for 100000 steps

Phase 4 (event loop): from 0x003A73 for 200000 steps (timerInterrupt: true)

Between phases, reset SP, set IY=0xD00080, set cpu.iff1=1.
