# Task: Test kernel init with PLL fix — extended 500K+ steps

## Context

In session 338, a PLL relock bug was fixed in peripherals.js. Previously, the PLL write handler had an optimization `if (!configured || value !== lastWrite)` that skipped resetting remainingReads when the same value was written again. This caused kernel init to get stuck in an infinite loop at 0x00069A. After the fix, 0x00069A is visited only once and init proceeds to 0x0006A9.

However, kernel init was only tested with 100K steps (the standard limit). The question is: **how far does kernel init actually get with 500K+ steps?** Specifically:
- Does cxMain (address stored at 0xD007CA) get naturally populated by boot?
- Does execution reach context dispatch at 0x08C8B5?
- Does it reach CoorMon at 0x08BF22?
- What address does it get stuck at (if any)?

## Your task

Create a probe `TI-84_Plus_CE/probe-phase339-extended-kernel-init.mjs` that:

1. **Boots from 0x000000** in z80 mode (20K steps, 32 loop iterations) — standard boot.

2. **Runs kernel init from 0x08C331** in ADL mode with **750,000 steps** and **500,000 loop iterations**. Timer interrupt DISABLED.

3. **Tracks these milestones** — record first visit step number for each:
   - 0x00069A (PLL init — should be visited only once now)
   - 0x0006A9 (post-PLL)
   - 0x08C8B5 (context dispatch)
   - 0x08BF22 (CoorMon entry)
   - 0x042366 (GetCSC)
   - 0x058241 (HOME_HANDLER)
   - 0x08BF82 (cxMain dispatch area)

4. **Monitors cxMain pointer** at 0xD007CA: check its value every 50K steps. Report when/if it changes from 0x000000 to something else.

5. **Reports the final state**: last PC visited, total steps taken, total unique blocks visited, exit reason (step limit / loop limit / RETURN_SENTINEL / halt), and the values of: SP, A, HL, DE, BC, IX, IY, MBASE, cxMain pointer.

6. **Reports the top 20 most-visited blocks** (by visit count) to identify any new stuck loops.

7. **If kernel init reaches CoorMon (0x08BF22)**, report that as a MAJOR finding — it means the OS naturally boots into the event loop without manual cxMain/stack setup.

## Important: onBlock callback

The executor's `runFrom` accepts options including an `onBlock` callback that fires for every basic block:
```javascript
executor.runFrom(pc, mode, {
  maxSteps: 750000,
  maxLoopIterations: 500000,
  onBlock(blockPc, blockMeta, stepNum) {
    // blockPc = the PC of the block
    // blockMeta = metadata about the block (instructions, exits, etc.)
    // stepNum = current step number
  }
});
```

Use this to track milestones and block visit counts.
