# Task: Stub the 0x006202 delay loop in transpiled runtime

## Context
You are working on a TI-84 Plus CE ROM transpilation project at `C:/Users/rober/Downloads/Projects/school/ti84-transpile`.

Session 247 found that both 0x0003B0 (PLL configuration) and 0x0270F3 (clock switcher) stall at the delay loop at 0x006202. The loop structure:
- 0x006202: `OR A / SBC HL,DE / JR NZ,0x006202` (inner loop, HL starts ~0x8B1A, DE=1, needs ~35K iterations)
- 0x0061EF: outer loop decrements A
- Both 0x0003B0 and 0x0270F3 call into 0x0061E3 which enters this delay

This is a pure hardware settle delay (waiting for PLL lock). In the transpiled runtime, there's no real PLL, so the delay is wasted cycles. Stubbing it would unblock 0x027111/0x027123 screen-redraw tracing.

## Task

   - Traces execution from 0x0061E3 to understand the full delay structure
   - Determines the exact exit point (where execution goes after the delay completes)
   - Measures how many steps the delay takes with various initial register values
   - Tests what happens if we skip the delay (jump directly to the exit point)

2. **Then, modify the transpiler** `scripts/transpile-ti84-rom.mjs` to add a fast-path for the delay loop. Options:
   - Add a special seed/annotation that replaces the delay loop block with a no-op (set HL=0, A=0, skip to exit)
   - Or add a runtime check in the transpiled block at 0x006202 that immediately exits

3. **Verify**: After modifying the transpiler, regenerate `ROM.transpiled.js` and run the golden regression `node TI-84_Plus_CE/probe-phase99d-home-verify.mjs` to confirm 26/26 still passes.
