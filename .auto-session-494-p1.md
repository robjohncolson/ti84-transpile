# Task: Dynamic Test BCALL Table Neighbors of Cursor Erase (Entry 832)

## Context
We are transpiling the TI-84 Plus CE OS ROM (eZ80) to JavaScript. The ROM is at `TI-84_Plus_CE/ROM.rom` (4MB). We found the OS BCALL jump table at 0x020104-0x02230B with 2,178 entries (each `C3 xx xx xx` = JP instruction). Entry 832 at table offset 0x020E04 jumps to 0x061003 (confirmed cursor erase — clears screen from cursor position to bottom). The cursor DRAW function is unknown.

The neighboring entries in the bcall table are the strongest candidates for the cursor draw function:
- Entry 826 = 0x060B8D
- Entry 827 = 0x060C23
- Entry 828 = 0x060C39
- Entry 829 = 0x060EF5 (8+ callers, heavily used)
- Entry 830 = 0x060F85 (screen management)
- Entry 831 = 0x060FEA (immediately before cursor erase — #1 candidate)
- Entry 832 = 0x061003 (cursor erase — KNOWN)
- Entry 833 = 0x06118A

## Deliverable
Create `TI-84_Plus_CE/probe-phase494-bcall-neighbor-dynamic.mjs` that dynamically tests entries 826-831 and 833 (skip 832, already known).

## How to build the probe
Use the existing probe infrastructure. Read `TI-84_Plus_CE/probe-phase99d-home-verify.mjs` for the pattern of how to create a CPU, load ROM, set up peripherals, and step.

Key pattern:
```javascript
import { createCPU } from './cpu-runtime.js';
import { createPeripheralBus } from './peripherals.js';

const cpu = createCPU();
const peripherals = createPeripheralBus({ timerInterrupt: false });
cpu.attachPeripherals(peripherals);

// Load ROM
import fs from 'fs';
const rom = fs.readFileSync(new URL('./ROM.rom', import.meta.url));
cpu.loadROM(rom);
```

VRAM is at 0xD40000-0xD52C00 (320×240×2 bytes = 153,600 bytes).

For each target function (826-831, 833):
1. Boot the CPU to idle (run ~200K steps from PC=0 to reach idle state)
2. Snapshot VRAM
3. Set cursor position: D00595 = row (try 3), D00596 = col (try 10)
4. Set PC to the target address
5. Run up to 50,000 steps or until RET
6. Compare VRAM to snapshot — count changed bytes, find bounding box
7. Report: address, changed bytes count, bounding box (min/max row/col), whether position changes with cursor

Then repeat with a DIFFERENT cursor position (row=7, col=20) for entries that showed VRAM changes — if the VRAM write position moves with cursor position, it's the cursor draw.

## Output format
Print JSON results for each entry: `{ entry, address, vramChanges, boundingBox, movesWithCursor }`.

The cursor draw function will:
- Write NON-0xFF pixels (black/colored, not white) to VRAM
- Write to a ~12×16 pixel region (one character cell)
- Write position MOVES with D00595/D00596

## Important constraints
- Use `createPeripheralBus({ timerInterrupt: false })` — timer IRQ causes infinite loops
- Step limit 50,000 per function test (some functions don't return)
- IY register should be 0xD00080 (set it if needed: `cpu.registers.IY = 0xD00080`)
- Access memory via `cpu.memory[addr]` for reads, `cpu.memory[addr] = val` for writes (but only for RAM addresses >= 0xD00000)
- For VRAM comparison, check range 0xD40000 to 0xD52C00

## Success criterion
Identify which bcall table neighbor(s) write cursor-sized, position-dependent VRAM changes. Entry 831 (0x060FEA) is the #1 candidate.

## Probe safety
Run the probe ONLY via: `node scripts/run-probe.mjs --max-time 180 TI-84_Plus_CE/probe-phase494-bcall-neighbor-dynamic.mjs`
NEVER run `node TI-84_Plus_CE/probe-phase494-bcall-neighbor-dynamic.mjs` bare — it can infinite-loop.
