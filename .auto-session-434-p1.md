# Task: Trace 0x00FBD1 — Universal USB Event Callback

## Context
In the TI-84 Plus CE ROM (eZ80, file `TI-84_Plus_CE/ROM.rom`), address 0x00FBD1 is the universal USB event callback. All 13 callers of the indirect callback dispatcher at 0x01322D route here via D14026. Each caller passes a distinct power-of-two event bitmask (0x0004, 0x0008, 0x0010, 0x0020, 0x0040, 0x0080, 0x0100, 0x0200, 0x0800, 0x4000, 0x4001, 0x080001). The dispatcher reads D14026, null-checks, then dispatches via JP(IY) trampoline at 0x002288 (_indcall), forwarding the caller's stacked argument.

We know 0x00FBD1 receives the bitmask at IX+6 and applies AND 0x04 to test specific bits. But we don't know:
1. How large is 0x00FBD1? Where does it end?
2. What does it do with the bitmask argument beyond the AND 0x04 test?
3. Does it dispatch to per-event handlers, or does it accumulate bits?
4. What RAM variables does it read/write?
5. What CALL targets does it have?

## Deliverables
1. Create `TI-84_Plus_CE/probe-phase434-trace-00FBD1.mjs` — a Node.js probe that:
   - Loads the ROM from `TI-84_Plus_CE/ROM.rom`
   - Disassembles starting at 0x00FBD1 (eZ80 ADL mode, 24-bit addresses)
   - Traces all CALL targets, RAM reads/writes (0xD00000+ range), port I/O
   - Identifies the function boundary (look for RET or equivalent)
   - Outputs: function size, instruction count, CALL targets, RAM refs, port I/O, control flow summary

2. Create `TI-84_Plus_CE/phase434-00FBD1-report.md` — analysis report covering:
   - Function boundaries and size
   - What happens with the bitmask argument
   - All CALL targets with addresses
   - RAM variables accessed
   - Port I/O if any
   - Hypothesis about the function's role
