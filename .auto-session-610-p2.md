# Auto-Session 610 — P2: Trace Key1 vs Key2 Edit Buffer State

## Context

This is a TI-84 Plus CE ROM transpilation project. The lifted OS runs in JavaScript. We're investigating why keys 2-3 run away (infinite loop in the edit buffer walker) while key1 processes correctly.

Key1 processes correctly because the bulk wipe at 0x0018F8 (step ~84,825) zeroes the edit buffer and OS rebuilds it from scratch. Keys 2-3 (using the post-paint snapshot) have STALE edit buffer pointers that cause the walker at 0x090917 to loop forever.

Session 609 showed the walker's parent function (around 0x090888) loops on a degenerate edit buffer. We need to compare what the edit buffer looks like after key1's wipe vs what keys 2-3 see.

## Task

Create a probe `TI-84_Plus_CE/probe-phase610-editbuf-compare.mjs` that captures edit buffer state at key moments during key1 processing and compares with the initial (post-paint) state.

### Recipe (from prior sessions)

The standard boot + init + paint recipe:

```javascript
import { readFileSync } from 'fs';
import { createCPU } from './cpu-runtime.js';
import { createPeripheralBus } from './peripherals.js';

const rom = readFileSync('TI-84_Plus_CE/ROM.rom');
const peripherals = createPeripheralBus({ timerInterrupt: false });
const cpu = createCPU(rom, peripherals);

// Standard boot
cpu.sp = 0xD1A87E - 24;
const retAddr = 0x0019b5; // HALT idle, NOT 0x0019be (wipe trap)
cpu.mem[cpu.sp] = retAddr & 0xFF;
cpu.mem[cpu.sp + 1] = (retAddr >> 8) & 0xFF;
cpu.mem[cpu.sp + 2] = (retAddr >> 16) & 0xFF;
cpu.write24(0xD008E0, cpu.sp);
cpu.adl = 1;

// Run OS init (0x09DD62)
cpu.runFrom(0x09DD62, { maxSteps: 300000, maxLoopIterations: 30000 });

// Run home repaint (0x058241) with timer on
peripherals.setTimerEnabled(true);
cpu.mem[cpu.sp] = 0xb5; cpu.mem[cpu.sp+1] = 0x19; cpu.mem[cpu.sp+2] = 0x00;
cpu.write24(0xD008E0, cpu.sp);
cpu.runFrom(0x058241, { maxSteps: 300000, maxLoopIterations: 30000 });
```

### What to capture

Define a helper function to snapshot the edit buffer region:

```javascript
function captureEditBuf(cpu) {
  return {
    D0231A: cpu.read24(0xD0231A), // editCursor
    D0231D: cpu.read24(0xD0231D), // editBoundary  
    D02317: cpu.read24(0xD02317), // begPC
    D0243A: cpu.read24(0xD0243A), // editCursorB
    D0243D: cpu.read24(0xD0243D), // editBtm
    D02440: cpu.read24(0xD02440), // editBufStart?
    D000A3: cpu.mem[0xD000A3],    // IY+0x23 flags (bit 3 = edit buffer active)
    D007CA: cpu.read24(0xD007CA), // cxMain handler
    // Dump raw bytes D02430-D02450 (32 bytes of descriptor block)
    desc: Array.from({length: 32}, (_, i) => cpu.mem[0xD02430 + i]),
    // Dump D11100-D11160 (96 bytes)
    d111: Array.from({length: 96}, (_, i) => cpu.mem[0xD11100 + i]),
    // Dump D0231A-D02350 (54 bytes of edit cursor region)
    editRegion: Array.from({length: 54}, (_, i) => cpu.mem[0xD0231A + i]),
  };
}
```

Capture at these moments:
1. **After init** (post-0x09DD62, before paint)
2. **After paint** (post-0x058241 — this is the "post-paint snapshot" used for keys 2-3)
3. **After key1's FIRST wipe** (instrument onBlock(0x0018F8) to capture state IMMEDIATELY AFTER the wipe completes at step ~84,825)
4. **After key1's SECOND wipe** (step ~274,953)
5. **At key1 halt** (step 276,820 at 0x0019B5)

For capture #3, use onBlock to detect the wipe and capture state ~100 steps later (after the wipe's LDIR completes).

Then seed key1 ('2'/0x90) and run via the outer loop:
- Set D0058C=0x90 (key code), D0009F |= 0x20 (event flag bit 5)
- cpu.mem[cpu.sp]=0xb5; cpu.mem[cpu.sp+1]=0x19; cpu.mem[cpu.sp+2]=0x00;
- cpu.write24(0xD008E0, cpu.sp);
- cpu.runFrom(0x08C331, { maxSteps: 350000, maxLoopIterations: 30000, onBlock: ... });
