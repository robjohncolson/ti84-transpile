# Auto-Session 359 P1: RAM Trampoline for Flash Self-Test at 0xD18C22

## Context

The TI-84 Plus CE boot sequence hits a wall at step 2207: block 0x000D82 (an LDIR code-copy routine) copies 90 bytes from ROM address 0x000EBB to RAM address 0xD18C22, then executes `JP (IX)` jumping to the RAM copy. Since the transpiler only generates blocks from ROM, there's no transpiled block at 0xD18C22 → `missing_block` termination.

The copied code is a **flash erase/self-test routine** that writes unlock patterns (0xAA→0x000AAA, 0x55→0x000555, 0x80, 0x30) and polls status bits. In our emulation we don't have real flash, so this test should be **bypassed** by making execution skip the RAM copy and return "test passed."

### What the code-copy routine does (0x000D82)

```
0x000D82: PUSH AF/BC/DE/HL/IX
          POP HL (= IX on entry, points to parameter block)
          LD DE, 0xD18C7C  (RAM dest end)
          load 2-byte count from (HL) → BC = 0x005A (90)
          SBC HL,BC to compute source start
          PUSH DE (dest start)
          LDIR (copy ROM to RAM)
          LD (0xD02AD7), HL (save end source pointer)
          LD A, (0xD02AD9)
          IN0 C, (0x1F)
          INC C
          CP C
          JP NC, 0x0019B5 (only if port 0x1F gate fails)
          POP IX → JP (IX) → jumps to 0xD18C22 (RAM)
```

The caller is at 0x000E99: `CALL 0x000D7E`. Before that, 0x000E94 does `LD IX, 0x000EB9`. The parameter block at 0x000EB9 has length=0x005A, followed by the flash erase code starting at 0x000EBB.

### What "success" looks like

After the RAM code finishes the flash self-test, it does:
```
0x000F10: C1        POP BC
0x000F11: C9        RET
```
This returns to the instruction after the JP (IX) — which is actually the instruction after the CALL 0x000D7E at 0x000E99 (i.e., 0x000E9D). The code-copy routine sets up the stack so RET from the RAM code returns to the original caller.

Actually, looking more carefully: the JP (IX) REPLACES the normal return. The stack has been set up by the PUSHes in 0x000D82. The RAM code's final RET pops back through the saved registers.

## Task

Create a probe `TI-84_Plus_CE/probe-phase359-ram-trampoline.mjs` that:

1. **Adds a RAM execution trampoline** to the boot probe. When the execution engine hits `missing_block` at a RAM address in the range 0xD18C00-0xD19000, instead of terminating, it should:
   - Check if the RAM address corresponds to a known code-copy destination
   - For the flash self-test (destination 0xD18C22, source 0x000EBB), simply simulate "test passed" by:
     - Setting the CPU state as if the flash test succeeded (A=0xFF or whatever the test returns on success — the flash test polls bit 6 of the status register, so likely A has bit 6 set)
     - Adjusting PC to continue execution after the code-copy routine returns

2. **Alternative simpler approach**: Instead of a full trampoline, intercept the CALL 0x000D7E at address 0x000E99. When execution reaches block 0x000E94 (or wherever the LD IX + CALL sequence is), check if IX=0x000EB9 (flash self-test parameter block). If so, skip the call entirely and simulate a successful return.

3. **Recommended approach**: Modify the `onMissingBlock` callback in the probe's execution options. When a missing block is detected at a RAM address (addr >= 0xD00000), instead of terminating:
   - Pop the return address from the stack (this is where the code-copy routine's caller expects to resume)
   - Set PC to that return address
   - Set appropriate register state for "flash test passed"
   - Continue execution

4. **Boot the probe** with `createPeripheralBus({ timerInterrupt: false })` and run for 50,000 steps. Report:
   - Total blocks reached
   - Whether execution continues past 0xD18C22
   - What new blocks/territory are reached after the trampoline
   - Any new `missing_block` addresses encountered
