# Task: Investigate 0x00B71B Call Chain and Purpose

## Context
The TI-84 Plus CE ROM transpilation project. During boot, block 0x00B71B writes only the high byte (0x01) to address 0xD14097 but leaves 0xD14095-0xD14096 as zero, creating a bad linked-list pointer 0x010000 (ROM space). When block 0x00BC47 later follows this pointer via `LD IX, (IX-30)`, IX enters ROM space and eventually corrupts SP.

We need to understand: What IS block 0x00B71B? What calls it? Is it a memory allocator, linked-list initializer, or driver registration function?

## What to do

Write a probe script at `TI-84_Plus_CE/probe-phase365-B71B-callchain.mjs` that:

1. **Disassemble 0x00B71B** — Read ROM.rom bytes starting at 0x00B71B for ~64 bytes. Decode eZ80 ADL instructions. Also disassemble 0x00B700-0x00B71A to see if 0x00B71B is a function entry or mid-function.

2. **Find all callers of 0x00B71B** via static ROM scan:
   - Search for `CALL 0x00B71B` in the ROM. In ADL mode, CALL nn is `0xCD` followed by 3-byte little-endian address. So search for bytes `CD 1B B7 00`.
   - Also search for `JP 0x00B71B`: `0xC3 1B B7 00`.
   - Also check for conditional variants: `CALL cc, 0x00B71B` (opcodes 0xC4, 0xCC, 0xD4, 0xDC, 0xE4, 0xEC, 0xF4, 0xFC with `1B B7 00`).
   - Report all addresses where these patterns are found.

3. **Disassemble each caller** — For each CALL/JP found, disassemble 16 bytes before and 16 bytes after to understand the calling context.

4. **Dynamic trace** (optional if the above is sufficient): Run a boot for 3000 steps and log every time block 0x00B71B executes. Record the caller's PC (from the return address on stack or from the previous block in execution history), and the register state (IX, SP, BC, HL) on entry.

5. **Trace what 0x00B71B writes to 0xD14097**: Specifically, what instruction writes the 0x01 byte? Is it `LD (addr), A` where A=0x01? Or `LD (IX+d), n`? Understanding the instruction tells us whether it's intentionally writing only one byte or whether there's a missing multi-byte write.
