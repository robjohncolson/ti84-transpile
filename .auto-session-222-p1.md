# Auto-Session 222 — P1: Trace 0x05C52C Internal Branching (Key Classifier / Secondary Table Selection)

## Context

You are working on a TI-84 Plus CE ROM transpilation project. The ROM (eZ80, 4MB) has been lifted to JavaScript. Key files:

- `TI-84_Plus_CE/cpu-runtime.js` — eZ80 runtime + memory

- `scripts/transpile-ti84-rom.mjs` — transpiler

## Background

ConvKeyToTok at 0x05E630 converts scan codes to tokens. Its FIRST instruction is `CALL 0x05C52C` (the "key classifier"). The key classifier subtracts 0x5A from the scan code and indexes the primary token table at 0x05BF84 (166 entries). When the primary table entry is 0x00, secondary tables should be consulted:
- 0x05C01D (400 entries, function tokens like sin/cos)
- 0x05C1B0 (400 entries, 2nd-mode 2-byte tokens with prefix 0x61/0x5E)
- 0x05C3AA (264 entries, Alpha-mode with prefix 0xBB/0xEF)
- 0x05C4A0 (18 entries, Alpha-Lock subset)

**Problem**: Session 221 exhaustively tested 512 IY flag combinations at ConvKeyToTok entry — NEITHER BIT 4,(IY+5) at 0x05E63C nor BIT 1,(IY+42) at 0x05E65B causes secondary table selection. ALL tests write 0x00 to the edit buffer. The root cause: table selection happens INSIDE 0x05C52C itself, not via IY flags in ConvKeyToTok. 0x05C52C subtracts 0x5A and indexes the primary table — for primary=0x00, it returns 0x00 without consulting secondary tables.

## Task

Build a probe `TI-84_Plus_CE/probe-phase222-05c52c-internal-branching.mjs` that:

1. **Static disassembly**: Read ROM.rom directly (fs.readFileSync) and disassemble 0x05C52C through 0x05C600 (or until RET). Decode eZ80 instructions manually (the decoder at `TI-84_Plus_CE/ez80-decoder.js` can help, but raw byte analysis is fine). Look for:
   - CP instructions (comparisons that branch on scan code range)
   - LD HL,<table_addr> instructions that load table base addresses
   - ADD HL,DE or similar table indexing
   - Conditional JR/JP that route to different tables
   - Any reads of IY-indexed memory (mode flags)

2. **Dynamic traces**: Boot a runtime and call 0x05C52C with different A values:
   - A=0x8F (scan code for digit '1', primary table has token 0x31 — should work)
   - A=0x76 (scan code for LOG key, primary=0x00 — should trigger secondary)
   - A=0x69 (scan code for COS⁻¹, primary=0x00 — should trigger secondary)
   
   For each, trace with `maxSteps: 200` and log every block visited + register A at each step. Compare the paths to find where they diverge.

3. **Mode flag experiment**: For A=0x76 (primary=0x00), try setting mode flags BEFORE calling 0x05C52C:
   - IY+0 bit 4 (2nd mode indicator?)
   - IY+0 bit 3 (Alpha mode?)
   - IY+1 various bits
   - Direct write to any "mode" byte near 0xD00080-0xD000B0
   
   Check if any flag causes 0x05C52C to return a non-zero token for scan codes that normally return 0x00.

## How to boot the runtime

```javascript
import { readFileSync } from 'fs';
const ROM = readFileSync('TI-84_Plus_CE/ROM.rom');
const { createCPU } = await import('./TI-84_Plus_CE/cpu-runtime.js');
const { createPeripheralBus } = await import('./TI-84_Plus_CE/peripherals.js');

const peri = createPeripheralBus({ timerInterrupt: false });
const cpu = createCPU(peri);

// Load ROM
for (let i = 0; i < ROM.length; i++) cpu.mem[i] = ROM[i];

// Minimal init
cpu.mbase = 0xD0;
cpu.sp = 0xD1A87E;
cpu.iy = 0xD00080;

// Set up gap buffer for BufInsert
const mem = cpu.mem;
// editTop
mem[0xD02437] = 0x00; mem[0xD02438] = 0x0A; mem[0xD02439] = 0xD0;
// editCursor
mem[0xD0243A] = 0x00; mem[0xD0243B] = 0x0A; mem[0xD0243C] = 0xD0;
// editTail
mem[0xD0243D] = 0x00; mem[0xD0243E] = 0x0B; mem[0xD0243F] = 0xD0;
// editBtm
mem[0xD02440] = 0x00; mem[0xD02441] = 0x0B; mem[0xD02442] = 0xD0;
```
