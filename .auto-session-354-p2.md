# Auto-Session 354 — Priority 2: Investigate Port 0x000D (Interrupt Flag Register)

## Context
The TI-84 Plus CE boot reaches 270 unique blocks then loops infinitely in LCD init. Port 0x000D is read 23 times during 50K boot steps (once per ~2174-step cycle), always returning 0xFF. After reading, the code writes 0x0F to port 0x000D. On real hardware, port 0x0D is likely an interrupt mask/flag register. Reading 0xFF = "all flags set". The init code may check a flag to decide whether to continue or retry.

## Task
Create a probe `TI-84_Plus_CE/probe-phase354-port000D-test.mjs` that tests what happens when port 0x000D returns different values.

Test these return values for port 0x000D:
1. 0xFF (current default — baseline)
2. 0x00 (no flags set)
3. 0x0F (matches the write-back value)
4. 0xF0 (upper nibble only)

For each test:
1. Boot the CPU for 10,000 steps
2. Record: unique blocks reached, furthest PC, total steps executed
3. Record all reads from port 0x000D (step number, PC at read, value returned)
4. Compare with the baseline (0xFF) — did any value unlock new blocks?

## How to Override a Port Return Value
The peripheral bus has handlers for each port. To override port 0x000D's read value, you can intercept the bus's `read` method. Looking at existing probes like `probe-phase353-port0009-analysis.mjs` or `probe-phase353-portD018-analysis.mjs` for the pattern:

```javascript
const bus = createPeripheralBus({ timerInterrupt: false });
// Override port 0x000D read
const originalRead = bus.read.bind(bus);
bus.read = (port) => {
  if (port === 0x000D) return testValue;
  return originalRead(port);
};
```
