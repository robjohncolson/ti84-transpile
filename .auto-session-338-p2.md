# Task: Investigate and Fix Kernel Init Stuck Loop at 0x00069A

## Context
You are working on a TI-84 Plus CE ROM transpilation project. Session 337 found that running kernel init from 0x08C331 with 500K+ steps gets stuck in a polling loop at 0x00069A. The loop does: `IM 1`, `OUT0 (0x28),A`, `IN0 A,(0x28)`, `BIT 2,A` — polling port 0x28 bit 2 for hardware ready.

**IMPORTANT DISCOVERY**: Port 0x28 IS already registered in `peripherals.js` as the PLL handler (`createPllHandler`). The PLL handler:
- Returns 0x00 when `!state.pll.configured`
- After a write (`OUT0`), sets `configured = true`
- After `pll.delay` reads (default 2), returns 0x04 (bit 2 set)

So the handler SHOULD unblock the loop. Yet session 337 says 55,478 visits to 0x00069A in 500K steps. Something is wrong.

## Your Task
1. **Investigate** why the kernel init is stuck despite the PLL handler being registered:
   - Read `TI-84_Plus_CE/peripherals.js` — examine `createPllHandler` and how `register()` maps port reads/writes
   - Read `TI-84_Plus_CE/cpu-runtime.js` — examine how `IN0`/`OUT0` (z80 I/O instructions) dispatch to the peripheral bus. Check if there's a mode mismatch (z80 vs ADL I/O port handling)
   - Check if the `IN0 A,(0x28)` instruction at 0x00069A actually reaches the PLL handler. The issue might be:
     (a) Port address normalization issue (z80 vs ADL mode)
     (b) The polling loop writes different values each time, resetting the PLL state
     (c) The boot phase (z80 mode) handles ports differently than ADL mode
     (d) The `IN0`/`OUT0` instruction implementations don't call the peripheral bus
   - Read `TI-84_Plus_CE/ez80-decoder.js` to check how IN0/OUT0 are decoded

2. **Create a diagnostic probe** at `TI-84_Plus_CE/probe-phase338-port28-debug.mjs` that:
   - Boots normally (BOOT_ENTRY 0x000000 in z80 mode, then KERNEL_INIT_ENTRY 0x08C331 in ADL mode)
   - Instruments the peripheral bus to log every port 0x28 read and write
   - Runs kernel init for 10,000 steps (enough to see the stuck loop)
   - Reports: how many port 0x28 reads/writes occurred, what values were written, what values were returned
   - If ZERO reads/writes → the IN0/OUT0 instructions aren't reaching the peripheral bus (decoder/runtime issue)
   - If reads/writes occur but bit 2 never gets set → PLL handler logic issue

3. **Fix the root cause** — whatever you find in step 2:
   - If IN0/OUT0 don't call the peripheral bus → fix in `cpu-runtime.js` or `ez80-decoder.js`
   - If the PLL handler logic is wrong → fix in `peripherals.js`
   - If it's a boot-mode vs init-mode issue → fix the relevant dispatch
