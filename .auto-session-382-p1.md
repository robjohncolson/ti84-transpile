# Task: Resolve Scan Code Index Discrepancy (Forward vs Reversed Formula)

## Context
You are working on TI-84 Plus CE ROM transpilation in `C:/Users/rober/Downloads/Projects/school/ti84-transpile`.

The TI-84 CE OS has TWO different scan code numbering schemes:
1. **Reversed formula** `(6-group)*8+bit+1` — used by `_GetCSC` at `0x003D35-0x003D42`. The scan loop iterates keyboard ports in REVERSE ORDER (group 6 → group 0, H increments). ENTER (group 1, bit 0) = `(6-1)*8+0+1 = 0x29`.
2. **Forward formula** `group*8+bit+1` — used by the translation table at ROM `0x09F79B`. ENTER = `1*8+0+1 = 0x09`. At table[0x09]=0x05 (kEnter). At table[0x29]=0x00 (unmapped).

The translation table lookup code is at ROM `0x03010D` (documented in `TI-84_Plus_CE/scancode-translate.js` lines 7-12):
```
BIT 4,(IY+0x12) -> test alpha flag
ADD A,0x70      -> alpha offset
BIT 5,(IY+0x12) -> test 2nd flag
ADD A,0x38      -> 2nd offset
LD L,A; LD H,0; LD DE,0x09F79B; ADD HL,DE; LD A,(HL)
```

The A register at entry to 0x03010D must contain a FORWARD scan code (group*8+bit+1) for the table lookup to work. But `_GetCSC` produces REVERSED scan codes ((6-group)*8+bit+1).

**QUESTION**: Who converts between the two? There must be code between `_GetCSC` returning the scan code and `0x03010D` performing the table lookup that converts reversed→forward (or the scan code stored at `0xD00587` is already forward).

## What to investigate

3. Check if `0x03010D` is actually called in the key dispatch path (`0x003A7D → 0x001713 → ...`). If so, trace how A gets from the `_GetCSC` return value to the `0x03010D` entry.
4. An alternative theory: maybe the scan code formula ISN'T reversed — maybe `_GetCSC` at `0x003D35` computes `(H-1)*8+bit+1` where H starts at 1 for group 6, not H=7 for group 0. Re-examine: the loop at `0x003D22` increments H starting from 1, scanning ports in reverse order. H=1 for keyMatrix[6] (group 6), H=7 for keyMatrix[0] (group 0). For ENTER at keyMatrix[1]: H=6, scancode=(6-1)*8+0+1=0x29. That IS the reversed formula.
