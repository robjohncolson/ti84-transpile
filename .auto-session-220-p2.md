# Auto-Session 220 — P2: 2-Byte Token Testing via Alternate Insertion Path

## Context

Session 219 confirmed that the alternate insertion path (BIT 4 CLEAR at IY+5) is functionally equivalent to BufInsert for **single-byte tokens** (digits 0-9, letters A-Z, operators +−×÷). The two paths diverge at block index 11: CLEAR→0x05E642, SET→0x05E6A4. Both write the token to the edit buffer and advance the cursor.

However, **2-byte tokens were NOT tested**. Many TI-84 functions use 2-byte token encoding (e.g., sin = [0xBB, 0x01] in some table mappings). The ConvKeyToTok secondary tables at:
- 0x05C01D (400 entries, function tokens: sin/cos/tan/etc.)
- 0x05C1B0 (400 entries, 2nd-mode with prefix 0x61/0x5E)
- 0x05C3AA (264 entries, Alpha-mode with prefix 0xBB/0xEF)

...return 2-byte token pairs. The question is whether the alternate path handles these correctly.

## Task

Build a probe `TI-84_Plus_CE/probe-phase220-2byte-token-insert.mjs` that:

### Part A — Identify 2-byte token scan codes
1. Read ROM.rom from `TI-84_Plus_CE/ROM.rom`
2. Read the primary ConvKeyToTok table at 0x05BF84 (166 entries, 2 bytes each: scan_code→token)
3. Read the secondary table at 0x05C01D (400 entries) — this is the 2nd-function table
4. Find scan codes that produce non-zero tokens in the secondary table
5. Pick 3-4 representative 2-byte function tokens: sin (scan code for SIN key), cos, ln, and one 2-byte prefix token

The TI-84 keyboard matrix (from `TI-84_Plus_CE/keyboard-matrix.md`):
- SIN key scan code: look up in the keyboard matrix
- The scan codes for 2nd-function keys are the same physical key codes but routed through the secondary table

### Part B — Test ConvKeyToTok with secondary table entry
1. Set up runtime with full boot (z80 boot → kernelInit → postInit → memInit)
2. Initialize gap buffer: editTop(0xD02437)=0xD00A00, editCursor(0xD0243A)=0xD00A00, editTail(0xD0243D)=0xD00B00, editBtm(0xD02440)=0xD00B00
3. For each test token:
   a. Call ConvKeyToTok at 0x05E630 with the scan code in A register
   b. Record: what DE becomes (the token value), how many bytes written to edit buffer, what the edit buffer contains
   c. Check if BufInsert (0x05E2A0) is reached or the alternate path (0x05E307→0x05E654) is used
   d. Check cursor advancement (should advance by 2 for 2-byte tokens)

### Part C — Compare BIT 4 SET vs CLEAR for 2-byte tokens
1. Run the same tokens with BIT 4,(IY+5) SET (should use BufInsert path)
2. Run with BIT 4,(IY+5) CLEAR (should use alternate path)
3. Compare: do both paths produce identical edit buffer contents?
4. For 2-byte tokens specifically: does the alternate path write BOTH bytes?

### Part D — Summary
Print a comparison table:
| Token | Scan Code | BIT4=SET result | BIT4=CLEAR result | Match? |
