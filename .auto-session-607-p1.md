# Auto-Session 607 — P1: POST-WIPE STATE CAPTURE PROBE

## Goal
Build a probe that captures the full OS state AFTER key1's second wipe completes (but BEFORE key1 halts), then uses THAT post-wipe state as the snapshot for keys 2 and 3. This should fix the key2/key3 runaway problem from session 606, where keys 2-3 ran away to 500K steps because the post-PAINT snapshot was missing state the wipe rebuilds.

## Background
- Session 606's `probe-phase606-wipe-hook.mjs` used an onBlock(0x0019b5) halt-based auto-restore with a post-paint snapshot. Key1 worked (332,856 steps), but keys 2-3 ran away to 500K steps each.
- The wipe at 0x0018F8 fires TWICE during key1 processing: at block ~84,825 (wipe1) and ~274,953 (wipe2).
- After wipe2, the OS rebuilds essential state (VAT pointers, edit buffers, system flags) before halting at 0x0019B5.
- The hypothesis: if we capture state AFTER key1's wipe2 + rebuild (but before halt), keys 2-3 should have the correct starting state and not run away.

## What to Build
Create `TI-84_Plus_CE/probe-phase607-postwipe-snapshot.mjs`:

1. **Boot** the OS using the same init sequence as `probe-phase606-wipe-hook.mjs` (reference that file for the exact boot setup — read it first). Use `createPeripheralBus({ timerInterrupt: false })`.

2. **Run key1 ('2', scan code 0x9A)** with full instrumentation:
   - Use onBlock(0x0018F8) to count wipe hits
   - When the SECOND wipe hit occurs (wipeCount === 2), set a flag `captureAfterWipe2 = true`
   - Use onBlock(0x0019B5) — when `captureAfterWipe2` is true, capture the FULL state snapshot at this point:
     - D007CA: 21 bytes (context handler table)
     - D0008D: 1 byte
     - D0231A, D0243A: 3 bytes each
     - D02434: 6 bytes
     - D0009F: 1 byte
     - D0058C, D0058E: 1 byte each
     - IY flag area: 128 bytes starting at IY (0xD00080)
     - **ALSO capture**: D02587-D0259D (VAT pointers, 22 bytes), D02577 (2 bytes), D0244E (3 bytes), D0256A (3 bytes), D025A0 (3 bytes), D02317-D0231F (begPC/curPC/endPC, 9 bytes), D02440-D02448 (editBtm + surrounding, 9 bytes)
     - Save all as `postWipeSnapshot`

3. **After key1 halts**, restore `postWipeSnapshot` instead of the old post-paint snapshot.

4. **Run key2 ('3', scan code 0x91)** with the post-wipe snapshot. Monitor:
   - Step count (should be ~196K like session 605's key2, not 500K)
   - Wipe count
   - Final VRAM pixel count
   - Whether it halts at 0x0019B5

5. **Run key3 ('+', scan code 0x70)** with the same post-wipe snapshot. Same monitoring.

6. **Report**:
   - Key1: steps, wipe count, halt address, VRAM
   - Key2: steps, wipe count, halt address, VRAM (compare to 606's 500K runaway)
   - Key3: steps, wipe count, halt address, VRAM (compare to 606's 500K runaway)
   - Print SUCCESS if keys 2-3 halt normally (< 300K steps) or PARTIAL if only one works
