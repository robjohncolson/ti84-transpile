# Auto-Session 266 P1: Investigate z80-mode bug at 0x062055

## Context
Function 0x062055 is the main OS context-switching dispatcher. It reads D0230F to decide whether to call cxMain (0x058241) or graph path (0x05FE15). However, session 265 discovered that when calling 0x062055 dynamically (after full boot, with various D007D0 seeds), execution falls into a **z80-mode loop through 0x000000-0x00069A** instead of reaching the expected cxMain path. ALL 4 D007D0 seed values tested produced identical 24-block z80-mode behavior. The conclusion: CPU state/mode prerequisites beyond D007D0/D0230F are missing.

The eZ80 CPU has an ADL (Address Data Long) mode bit. When ADL=1, the CPU uses 24-bit addresses. When ADL=0, it uses 16-bit (z80-compatible) mode. If 0x062055 is called in z80 mode, PC wraps to 16-bit addresses and execution falls into low ROM (0x000000-0x00069A).

## Task
Write a probe `TI-84_Plus_CE/probe-phase266-062055-adl-mode.mjs` that:

1. **Boots the system** using the standard full-boot sequence (cold boot → kernelInit → memInit → homescreen stages 1-4) from `probe-phase99d-home-verify.mjs`.
2. After boot, **check the CPU's ADL mode** (`cpu.adl`) and **MADL** (`cpu.mbase`) before calling 0x062055.
3. **Experiment 1**: Call 0x062055 with B=3 (known to pass the 0x080151 gate), `cpu.adl = true` explicitly, D0230F=0x3F (selects cxMain path), D007D0=0x06C546 (home-screen handler from session 262). Log cpu.adl, cpu.madl/mbase at entry and trace execution for 500 steps. Record all blocks visited.
4. **Experiment 2**: Same as Experiment 1 but with `cpu.adl = false` to confirm the z80-mode loop.
5. **Experiment 3**: Call 0x062055 with B=3, cpu.adl=true, D0230F=0x00 (non-0x3F, non-0x5E → should take cxMain path with A=0x40→D007E0), D007D0=0x06C546.
6. Report: cpu.adl at each entry, blocks visited, whether 0x08C69E/0x058241 was reached, D007E0/D007D0 values after execution.
