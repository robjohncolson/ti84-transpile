# Auto-Session 195 P1: TOKEN_STAGING Pre-Seeding Experiment

## Context
In the TI-84 Plus CE ROM transpilation project, we're tracing how the OS converts key presses to tokens. The ConvKeyToTok function correctly produces E=0x34 (token for key '4') but the E→OP1 transfer never happens because execution at block 0x05E6AE jumps to address 0xD0230E (TOKEN_STAGING RAM address) — i.e., it reads TOKEN_STAGING contents and uses them as a JUMP TARGET. Since TOKEN_STAGING is empty (0x00), it jumps to 0x000000 (boot vector).

Session 187 found that TOKEN_STAGING (0xD0230E) is populated via Copy9 (OP1→TOKEN_STAGING) at two sites: 0x06214C and 0x099AF1. Direct writes: 0x05A45F writes constant 0x06, 0x06B391 clears to 0.

## Task
Build a probe file `TI-84_Plus_CE/probe-phase195-token-staging-preseed.mjs` that tests whether pre-seeding TOKEN_STAGING with valid token data allows the ConvKeyToTok → OP1 path to complete.

### Experiments

**Experiment A**: Pre-seed TOKEN_STAGING (9 bytes at 0xD0230E) with a digit token in OP1 format:
- Byte 0: type = 0x00 (real number token type)
- Byte 1: token = 0x34 (the '4' token)  
- Bytes 2-8: 0x00
Then enter at 0x05E620 with A=0x92 (key code for '4'), trace execution. Check if OP1 (0xD005F8) gets populated. Log all blocks visited, RAM writes to OP1 area (0xD005F8-0xD00600), and where execution ends.

**Experiment B**: Same setup but TOKEN_STAGING byte 0 = 0x06 (the value that 0x05A45F writes). This may be a "function token" type indicator.

**Experiment C**: Pre-seed TOKEN_STAGING with the Copy9 pattern — write the full 9-byte OP1 structure for token '4':
- `[0x00, 0x34, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00]`
Then enter at 0x05849F (the `LD HL,0xD0230E; CALL 0x07F9FB` site in the home handler) instead of 0x05E620. This bypasses ConvKeyToTok entirely and tests the Copy9→classify→BufInsert path directly. Check if BufInsert (0x05E2A0) is reached.

**Experiment D**: Same as C but enter at 0x0584A3 (the CALL 0x07F9FB itself) with HL=0xD0230E already set.
