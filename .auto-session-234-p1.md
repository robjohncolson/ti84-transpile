# Task: Trace 0x0236F9 descriptor handler (hhh)

## Context
You are working on the TI-84 Plus CE ROM transpilation project. The ROM (eZ80 machine code) has been lifted to JavaScript. We are tracing the OS key-event dispatch pipeline.

Session 233 decoded the CP 0x36/0x30 classification at 0x02FE89. For non-CLEAR/non-MODE keys, the path goes:
- 0x02FF11: LD HL,A+09F79B (table lookup)
- CALL 0x022346 → 0x022359 → 0x0236F9

**0x0236F9 is the common sink for ALL ordinary key codes after classification.** It receives a 6-byte descriptor built by 0x022359. We need to understand what it does with that descriptor.

## What to do

Create a probe file `TI-84_Plus_CE/probe-phase234-0236f9-descriptor-handler.mjs` that:

1. **Disassembles 0x0236F9-0x023800** (at least 256 bytes) using the transpiled ROM blocks. List each instruction with address, opcode bytes, and mnemonic.

2. **Traces 0x0236F9 dynamically** with a realistic descriptor. Setup:
   - Full boot: z80 boot (0x000000) → kernelInit (0x00012C via 0x020008) → memInit (0x020074 via 0x00211B) → homescreen stages 1-4 (0x082B8E with counters 0x00/0x01/0x02/0x03)
   - Disable timer IRQ: `createPeripheralBus({ timerInterrupt: false })`
   - Set IX = 0xD1A860 before each homescreen stage
   - After boot, set up a key code scenario: store a key code (e.g., 0x8F = digit '1') in A, then call 0x022346 to build the descriptor, THEN call 0x0236F9 with that descriptor in place
   - Trace for 500 steps, recording every block visited, all IY flag changes, and any CALL/JP targets

3. **Identify the function's role**: Does it dispatch to an app-specific handler? Does it call CoorMon? Does it modify the edit buffer? Does it call ConvKeyToTok? Record what RAM addresses it reads/writes.

4. **Test with 2-3 different key codes** (e.g., 0x8F digit, 0x80 operator '+', 0x9A letter 'A') to see if the handler branches differently by key type.
