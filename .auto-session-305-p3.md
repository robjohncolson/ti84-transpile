# Task: Trace 0x06868A LCD refresh inner function

## Context
We are reverse-engineering the TI-84 Plus CE OS ROM. Session 304 decoded 0x0997AE as a two-level dispatch on IY+0x53: BIT 7 = "refresh pending" gate, BIT 6 = path selector. The BIT 6 CLEAR path calls 0x05BF5C which is a thin wrapper that calls 0x06868A then JP 0x07F7D6.

0x06868A reads 0xD005F8 (OP1), checks bit 6, and calls three sub-functions:
- 0x07F7A4
- 0x07FE5A
- 0x0686A8

Then conditional JP 0x07FE28.

We need to know what each of these sub-calls does in the context of LCD/edit-line refresh.

## What to do

Create a probe file `TI-84_Plus_CE/probe-phase305-06868A-lcd-refresh.mjs` that:

1. **Disassemble 0x06868A** by executing it from a warm boot state for 300-500 steps:
   - Standard boot + home screen init
   - Set IY+0x53 appropriately (bit 7 SET to pass the gate in 0x0997AE, bit 6 CLEAR for LCD path)
   - Trace blocks, RAM reads/writes, and sub-call entry/exit

2. **Trace each sub-call individually**:
   - **0x07F7A4**: Execute for 200 steps, log what it reads/writes. Does it read VRAM? Does it modify OP1 (0xD005F8)?
   - **0x07FE5A**: Same — 200 steps, log reads/writes. Is this a VRAM updater? Font renderer? Buffer copier?
   - **0x0686A8**: Same — 200 steps. What's its role?
   - **0x07FE28**: This is reached conditionally. What condition? What does it do?

3. **Document the refresh pipeline**: What's the sequence of operations when the edit line needs a display refresh?

## Technical setup
Look at `TI-84_Plus_CE/probe-phase304-0997AE-refresh.mjs` for the exact boot pattern and IY flag setup.

Key addresses:
- 0xD005F8 = OP1 (11 bytes)
- 0xD00603 = OP2 (11 bytes)  
- 0xD40000 = VRAM base
- IY = 0xD00080
