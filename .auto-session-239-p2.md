# Task: Investigate 0x04E447 computation loop at 0x0A1A3B-0x0A1A4E

## Context
You are working on a TI-84 Plus CE ROM transpilation project. The ROM is lifted to JavaScript and run via `cpu-runtime.js` + `peripherals.js` + `ROM.transpiled.js`.

Session 238 found that **0x04E447 is a deep computation path** that doesn't return within 500 steps. It gets stuck in a loop at 0x0A1A3B-0x0A1A4E (132 visits in 500 steps). SP drops 6+ frames, IX→0xD005B8 (OP area). Reaches flash page/memory management code. No VRAM writes.

0x04E447 is reached from 0x04EDD0 when D003E0 has specific bits set (NOT on the default home screen where D003E0=0x00).

## Task
Create a probe `TI-84_Plus_CE/probe-phase239-04e447-deep-trace.mjs` that:

1. Boots the CPU (z80 boot → kernelInit → memInit as per existing probes)
2. Seeds home-screen state BUT with D003E0 set to activate the 0x04E447 branch. Based on session 238, the gate at 0x04EDD0 tests D003E0 bits — try D003E0=0x08 (bit 3 set, which session 219 identified as the gate bit)
3. Enters at 0x04E447 DIRECTLY (skip the 0x04EDD0 routing, just go straight to the target)
4. Runs with **3000 step budget** 
5. Tracks:
   - Block visit counts (especially 0x0A1A3B-0x0A1A4E loop iterations)
   - Whether execution eventually exits the loop (does it leave the 0x0A1xxx range?)
   - Register snapshots every 500 steps (A, BC, DE, HL, IX, IY, SP, PC)
   - RAM changes: watch OP1-OP6 region (0xD005F8-0xD00628), D003E0, D007E0
   - Stack depth tracking (log SP changes)
   - Whether it returns (hits sentinel)

Also run a SECOND experiment with **10,000 steps** to see if the loop eventually terminates.

Use the same boilerplate as `probe-phase238-0850d1-04e447-branches.mjs` (read it for structure).
