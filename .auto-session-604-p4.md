# Auto-session 604 P4: Peak-VRAM capture strategy — capture display at step ~264,500 before second wipe

## Context

In the TI-84 Plus CE ROM transpilation project, the OS has a structural bulk RAM wipe at 0x0018F8 that fires TWICE during key processing:
- **Hit #1** at step ~84,825: mid-processing, VRAM = 1,466 px
- **Hit #2** at step ~274,953: destroys the peak display (VRAM was 3,337 px — the real rendered state with typed character '2')

The peak VRAM state at ~step 264,500 IS the correct display. After the second wipe, VRAM goes to 0 (blank screen). Session 603 confirmed that restoring D007CA enables multi-key dispatch but the wipe recurs structurally.

**Strategy question**: Can we capture VRAM at peak and use it as the display state, instead of waiting for the wipe to destroy it? This would be a WORKAROUND, not a fix — but it may be the pragmatic path for the browser-shell.

## Task

Create a probe that:

1. **Captures VRAM at the peak** (~step 264,500, before the second wipe at ~step 274,953). Use the same boot + key-seed sequence as `probe-phase603-callchain-to-wipe.mjs` (cold boot → kernel init → mem init → paint → seed key 0x90 → outer loop).

2. **Identifies the exact step range of the peak plateau**. Session 602 said VRAM recovers to peak 3,364 px by block ~264,500. Track VRAM non-zero pixel count every 1000 steps from step 250,000 to step 280,000 to find the exact plateau boundaries.

3. **Identifies the last block PC before the second wipe begins dropping VRAM**. What block address is executing when VRAM starts declining from peak? This is the "capture point" — if we can snapshot VRAM when this block fires, we have the real display.

4. **Tests whether intercepting at the capture point is feasible**. Specifically: if we stop execution at the capture-point block, is the VRAM valid? Count non-zero pixels in the VRAM region (0xD40000–0xD52BFF for 320x240 at 16bpp). Export the VRAM snapshot to a file for verification.

## Boot sequence (copy from probe-phase603-callchain-to-wipe.mjs)

```javascript
// Phase 0: Cold boot
executor.runFrom(0x000000, 'z80', { maxSteps: 20000, maxLoopIterations: 32 });
cpu.halted = false; cpu.iff1 = 0; cpu.iff2 = 0;
cpu.sp = 0xD1A87E - 3; mem.fill(0xFF, cpu.sp, cpu.sp + 3);
executor.runFrom(0x08C331, 'adl', { maxSteps: 100000, maxLoopIterations: 10000 });
cpu.mbase = 0xD0; cpu._iy = 0xD00080; cpu._hl = 0;
cpu.halted = false; cpu.iff1 = 0; cpu.iff2 = 0;
cpu.sp = 0xD1A87E - 3; mem.fill(0xFF, cpu.sp, cpu.sp + 3);
executor.runFrom(0x0802B2, 'adl', { maxSteps: 100, maxLoopIterations: 32 });
cpu.halted = false; cpu.iff1 = 1; cpu.iff2 = 1;
cpu._iy = 0xD00080; cpu.mbase = 0xD0;
cpu.sp = 0xD1A87E - 12; mem.fill(0xFF, cpu.sp, cpu.sp + 12);
executor.runFrom(0x0019be, 'adl', { maxSteps: 1_500_000, maxLoopIterations: 100000 });

// Phase 1: Launch-init
peripherals.setTimerEnabled(false);
cpu.halted = false; cpu.iff1 = 1; cpu.iff2 = 1;
cpu._iy = 0xD00080; cpu.mbase = 0xD0;
const launchSp = 0xD1A87E - 24;
cpu.sp = launchSp;
write24(mem, launchSp, 0x0019be);
write24(mem, 0xD008E0, launchSp);
executor.runFrom(0x09DD62, 'adl', { maxSteps: 300000, maxLoopIterations: 30000 });

// Phase 2: Paint
peripherals.setTimerEnabled(true);
cpu.halted = false; cpu.iff1 = 1; cpu.iff2 = 1;
cpu._iy = 0xD00080; cpu.mbase = 0xD0;
if ((cpu.sp & 0xFFFFFF) < 0x400000) cpu.sp = 0xD1A87E - 24;
cpu.sp = (cpu.sp - 3) & 0xFFFFFF;
write24(mem, cpu.sp, 0x0019b5);
executor.runFrom(0x058241, 'adl', { maxSteps: 300000, maxLoopIterations: 30000 });

// Phase 3: Seed key
mem[0xD0058C] = 0x90;
mem[0xD0058E] = 0x90;
mem[0xD0009F] |= 0x20;
// Re-arm longjmp, set up SP, etc. (see probe-phase603 for details)
```

## VRAM layout

- VRAM starts at **0xD40000**
- Resolution: 320×240 at 16bpp = 153,600 bytes (0x25800)
- VRAM end: 0xD40000 + 0x25800 = 0xD65800 (but use 0xD52BFF based on session 600 which used 0xD52C00)
- Non-zero pixel = any 16-bit value != 0x0000
