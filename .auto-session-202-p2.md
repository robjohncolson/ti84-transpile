# Auto-Session 202 P2: STAT LDDR BC=0xEAF5 Stack Corruption — Trace the Push Chain

## Context
In the TI-84 Plus CE ROM transpilation project, the STAT 1-Var Stats handler reaches block 0x092263 which starts with an LDDR instruction. The BC register at LDDR entry is 0xEAF5 (or 0x2FEAF5 in 24-bit), which causes a massive 60K+ byte copy that corrupts memory.

Session 196 corrected session 195's hypothesis: the BC value comes from `POP BC` at 0x092260 (inside parent block `09224b:adl`), not from uninitialized RAM. The POP BC pops whatever was pushed earlier by the upstream caller chain.

Session 194 showed that with seeded list data (L1={1.0,2.0,3.0} at 0xD10000 + VAT entry at 0xD1A800), the block count tripled to 264 unique blocks at 5000 steps. But BC was still 0xEAF5 at the LDDR.

Session 201 decoded the STAT structure formula: size = BC + 18, where BC at 0xD008F0 is the column count (5 = default). Block 0x091F12 writes BC=5 during STAT init.

## Task
Build a probe `TI-84_Plus_CE/probe-phase202-stat-bc-stack-trace.mjs` that:

1. **Trace the stack around 0x092263**: Set up the STAT handler with seeded list data (same setup as probe-phase194-stat-seeded-lists.mjs — L1={1.0,2.0,3.0} at 0xD10000, VAT entry at 0xD1A800). Entry via 0x058BA9 (cxErrorEP from the home context structure). Run for 5000 steps. At EVERY PUSH instruction, log: block address, instruction, what was pushed, SP before/after. At EVERY POP instruction, log the same. Build a complete push/pop ledger.

2. **Identify what pushed the value that becomes BC=0xEAF5**: From the push/pop ledger, trace backward from the POP BC at block 0x09224b (around byte offset 0x092260). What PUSH instruction put 0xEAF5 on the stack? Was it a PUSH HL, PUSH BC, PUSH DE, or PUSH AF? What block was it in? What was the register value at push time?

3. **Test with different list sizes**: Run experiments with L1 having 1, 3, and 5 elements. Does BC at the LDDR change? (Session 194 said low bytes 0xEAF5 same in all cases, but let's verify the full push chain.)

4. **Check if BC=0xEAF5 comes from the STAT structure itself**: Since session 201 showed the STAT structure has size=BC+18 and BC=5 (column count), check if 0xEAF5 could be a pointer into the STAT area or a computed offset. Read memory at 0xD008E6 (the STAT structure base) and surrounding area at the moment the POP BC fires.
