# Auto-Session 355 — P3: Investigate 0x001768 Stub + Jump Table at 0x000080

## Context
TI-84 Plus CE ROM transpilation project. Boot loops in a 2203-step cycle through 270 blocks. The cycle path includes: 0x00D7BE → ... → 0x00D33B → 0x000038 (RST 38h) → 0x000080 (JP 0x001768) → 0x001768 (LD A,5; LD B,6; RET) → 0x000000 (RESET VECTOR) → boot init re-entry.

The jump table at 0x000080 has entries:
- JP 0x001768
- JP 0x001775
- JP 0x003C59
- JP 0x00176D
- JP 0x001770

These look like mode/phase indicators. The stub at 0x001768 returns A=5, B=6. If A=5 means "phase 5" or "still initializing", a different return value might signal "init complete, proceed".

## Task
Create a probe that:
1. **Disassembles the jump table at 0x000080-0x0000A0** (32 bytes). Show each JP target and its offset from 0x000080.
2. **Disassembles all 5 stub targets**: 0x001768, 0x001775, 0x003C59, 0x00176D, 0x001770. For each, disassemble 20 bytes and identify what value they load into A and B.
3. **Tests 4 different return values for the 0x001768 stub** by patching RAM at 0x001768+1 (the immediate value loaded into A):
   - Test 1: A=5 (baseline, current behavior)
   - Test 2: A=0 (might signal "done")
   - Test 3: A=1
   - Test 4: A=6
   For each test, boot from PC=0 for 5000 steps with `createPeripheralBus({ timerInterrupt: false })`. Record: unique blocks visited, furthest PC reached, whether the 2203-step cycle still repeats, and any new blocks not seen in baseline.
4. **Traces who reads the A value** returned by 0x001768. After the RET from 0x001768, what instruction uses A? Log the first 10 instructions after 0x001768 returns (the caller's continuation).

## Technical Details
- ROM file: `TI-84_Plus_CE/ROM.rom` (4MB)
- Runtime:
```js
const { createCPU } = await import('./cpu-runtime.js');
const { createPeripheralBus } = await import('./peripherals.js');
import fs from 'fs';
const rom = new Uint8Array(fs.readFileSync('TI-84_Plus_CE/ROM.rom'));
const mem = new Uint8Array(0x1000000);
mem.set(rom);
const bus = createPeripheralBus({ timerInterrupt: false });
const cpu = createCPU(mem, bus);
const transpiled = await import('./ROM.transpiled.js');
```
- `cpu.step()` executes one instruction. `cpu.pc`, `cpu.a`, `cpu.f`, `cpu.sp`, etc.
- **IMPORTANT**: ROM addresses < 0x400000 are write-protected in cpu-runtime.js. To patch ROM for testing, you must write to `mem[addr]` BEFORE loading the transpiled blocks, or use a different approach: write a RAM-based trampoline. Actually, `mem` is a flat Uint8Array — writes to it work fine. The write-protection is only in `cpu.write8()`. So `mem[0x001769] = newValue` works for patching the immediate operand.
- BUT: the transpiled blocks are pre-compiled JavaScript functions. Patching mem bytes won't affect already-compiled block functions. To test different return values, you'd need to either:
  (a) Hook the execution after 0x001768 returns and manually set cpu.a, OR
  (b) Create a custom block function that replaces the one at 0x001768
- Approach (a) is simpler: run normally, but add a step hook that checks if PC was just at 0x001768 and the current instruction is RET, then override cpu.a.
