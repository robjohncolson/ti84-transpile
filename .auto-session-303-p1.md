# Auto-session 303 P1: Trace 0x0800A8 — Real Scan Code → Class Conversion

## Context
This is a TI-84 Plus CE OS ROM (eZ80) reverse-engineering project. The ROM is at `TI-84_Plus_CE/ROM.rom` (4 MB). The instruction decoder is at `TI-84_Plus_CE/ez80-decoder.js` — import `decodeInstruction` from it.

In session 302, we discovered that **0x058EC6 is NOT a scan-code-to-class converter** — it's just a 20-byte flag-clearing stub (RES 5,(IY+0x53), BIT 7,(IY+0x53), RET Z, PUSH AF, CALL 0x0997ED, POP AF, RES 7,(IY+0x53), RET). The scan code in register A passes through it unchanged.

0x058EC6 is called as the first instruction of **0x058D54** (key class lookup — a CP cascade that checks scan code classes). The next call in the 0x058D54 chain after 0x058EC6 returns is likely **0x0800A8**. This is the most likely location of the actual scan-code-to-class translation — the function that takes a raw scan code byte and returns a class value (0x09, 0x0A, 0x0B, etc.).

## Task
Create a probe file `TI-84_Plus_CE/probe-phase303-0800A8-class-conv.mjs` that:

1. **Disassembles 0x0800A8** through ~0x000900 (or until the function clearly ends with RET/JP). Use `ez80-decoder.js` — `decodeInstruction(rom, pc)` returns `{mnemonic, operands, length}`.
2. **Identifies the algorithm**: Is it a lookup table? CP cascade? Computed jump table? CPIR search?
3. **If a table is found**, dump the table entries and map scan codes to classes.
4. **Searches ROM for all callers** of 0x0800A8: scan for `CALL 0x0800A8` bytes (pattern: 0xCD 0xA8 0x00 0x08 in little-endian 24-bit = `CD A8 00 08` — but eZ80 uses 3-byte addresses so CALL is `CD` followed by 3 bytes LE: `CD A8 00 08`).
5. **Also check what 0x058D54 does right after calling 0x058EC6** — disassemble 0x058D54 from the beginning (~20-30 instructions) to see how it calls 0x0800A8 and what it does with the result.
6. **Prints a clear summary** with the algorithm, any table data, and all callers.
