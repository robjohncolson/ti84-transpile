# Task: Investigate H register state and block boundaries in keyboard scan 0x003C63-0x003D2E

## Context
The TI-84 Plus CE keyboard scan routine at 0x003C63 scans 8 keyboard groups. The algorithm:
1. Writes group-select bitmask to port 0xA000 (cascading: 0x01, 0x03, 0x07, etc.)
2. Reads key state from port 0xA008+offset
3. Uses H register as both key-count and group-iteration tracker
4. At 0x003D2E: `INC H; JR NZ,0x003D47` — if H ≠ 0 after increment, jumps to error/multi-key path

**The bug**: After the first group scan finds a key (ENTER in group 1), H becomes 0x07 (group iteration count). The second `INC H` at 0x003D2E makes H=0x08, which is NZ → triggers false multi-key detection → error path → scan returns 0xFF.

The hypothesis is that transpiled block boundaries may be splitting the scan algorithm mid-loop, causing H register state to leak between iterations incorrectly.

## Deliverable
Create `TI-84_Plus_CE/probe-phase375-h-register-scan.mjs` that:

1. **Maps all transpiled block boundaries within 0x003C63-0x003D60**:
   - Load ROM.transpiled.js
   - List every block whose start address falls in the range 0x003C63-0x003D60
   - For each block, report its start address, end address (or number of instructions), and where it transfers control (JP/JR/CALL/RET targets)

2. **Traces H register value at every block transition during a dynamic keyboard scan**:
   - Boot through phases 1→2→3 (standard boot)
   - Set ENTER key in group 1: use `peripherals.setMatrixKey(1, 1, true)` or the equivalent — write to the keyboard matrix so group 1, bit 1 = pressed
   - Enter event loop at 0x003A73 for 100,000 steps
   - At every block transition within the 0x003C63-0x003D60 range, log: block address, H register value, A register value, F register flags (Z, C, N)
   - Focus on the first 5 scan iterations (first 5 calls to 0x003C63)

3. **Identifies the specific transition where H gets the wrong value**:
   - Compare H at entry to 0x003D2E across scan iterations
   - Identify whether H is being preserved across a block boundary where it shouldn't be, or whether the scan loop itself sets H to the wrong value

4. Reports:
   - All block boundaries in the scan region
   - H register trace through the first 5 scans
   - Diagnosis: is this a block-boundary issue (H preserved incorrectly across blocks) or a loop-logic issue (the algorithm itself sets H incorrectly)?
   - If it's a block-boundary issue, which specific seed addresses would fix it

## Template
Base on `TI-84_Plus_CE/probe-phase374-keyboard-groups.mjs`. It already sets up ENTER in group 1 and traces the scan. Reuse its boot sequence, keyboard matrix setup, and block-tracking infrastructure.

## Key addresses

- 0x003D47: error/multi-key jump target
- 0x003D4B: key store (LD (0xD00587),A)
- 0x003CAF: error exit path
- Port 0xA000: keyboard group select (write)
- Port 0xA008-0xA014: keyboard data read
