# Auto-Session 275 P1: Classify LD HL,0xD3FFFF Sites as Registration vs Reader

## Context
The TI-84 Plus CE OS uses a dispatch table at D3FFFF (growing downward) with 9-byte entries. Session 274 proved that ZERO direct stores to D3F000-D3FFFF exist in ROM — all writes happen via HL-indirect (`LD (HL),r` after `LD HL,0xD3FFFF`). 23 ROM sites load HL with 0xD3FFFF. We need to classify each as REGISTRATION (writes entries into the table) vs READER (scans/iterates the table).

## Known LD HL,0xD3FFFF sites (from session 274 probe)
0x028AEF, 0x029E23, 0x03F20E, 0x04A574, 0x06B728, 0x06F4FC, 0x08270A, 0x083268, 0x0833B9, 0x08391C, 0x08470A, 0x09DEF4, 0x0A5F91, 0x0A5FA3, 0x0A65F6, 0x0B7CC0, 0x0B7CF2, 0x0B7ECA, 0x0B8D60, 0x0B9068, 0x0B9212 (+ 2 more from the probe)

## Key insight from session 274
- 0x0846EA is the dispatch table SCANNER — walks top slot downward looking for match, returns handler address in DE
- Table entries are 9 bytes: likely {mode_byte, handler_addr(3), ...}
- 0x09DEF4 loads HL=D3FFFF and stores to D0259A — likely table init/reset

## Task
Create a probe `TI-84_Plus_CE/probe-phase275-d3ffff-site-classify.mjs` that:

1. For the first 10 key candidate sites (prioritize 0x028AEF, 0x029E23, 0x03F20E, 0x04A574, 0x06B728, 0x06F4FC, 0x09DEF4, 0x0A5F91, 0x0B7CC0, 0x0B7CF2):
   - Disassemble 16 bytes starting at each address using raw ROM byte reading
   - Look at the instruction AFTER `LD HL,0xD3FFFF` — if it's a store (`LD (HL),r`, `LD (HL),n`, `LDIR`, `PUSH HL` followed by stores) → REGISTRATION
   - If it's a load (`LD r,(HL)`, `LD A,(HL)`, `CP (HL)`, comparisons) → READER
   - Run each site dynamically for 50 steps from the LD HL instruction to see what happens

2. Classify each site as: REGISTRATION, READER, POINTER-LOAD, or UNKNOWN

## Reference files
- `TI-84_Plus_CE/cpu-runtime.js` — CPU runtime with createCPU/createPeripheralBus
- `TI-84_Plus_CE/ROM.rom` — raw ROM binary (4MB)
- `TI-84_Plus_CE/probe-phase274-d3ffff-rom-scan.mjs` — previous probe that found these sites

## Probe template
```javascript
import { readFileSync } from 'fs';
import { createCPU, createPeripheralBus } from './cpu-runtime.js';

const rom = readFileSync(new URL('./ROM.rom', import.meta.url));
// Read raw bytes at each site to decode the instruction following LD HL,0xD3FFFF
// LD HL,nn in ADL mode = 0x21 nn nn nn (4 bytes)
// So instruction after LD HL starts at site + 4

const sites = [0x028AEF, 0x029E23, 0x03F20E, 0x04A574, 0x06B728, 0x06F4FC, 0x09DEF4, 0x0A5F91, 0x0B7CC0, 0x0B7CF2];

for (const addr of sites) {
    const nextInstr = addr + 4; // skip LD HL,nn (4 bytes in ADL)
    const opcode = rom[nextInstr];
    // Decode opcode to classify
    // 0x77 = LD (HL),A → REGISTRATION
    // 0x70-0x75 = LD (HL),r → REGISTRATION  
    // 0x36 = LD (HL),n → REGISTRATION
    // 0x7E = LD A,(HL) → READER
    // 0x46/0x4E/0x56/0x5E/0x66/0x6E = LD r,(HL) → READER
    // 0xBE = CP (HL) → READER
    // 0xE5 = PUSH HL → POINTER-LOAD (saves for later use)
    // 0xED 0xB0 = LDIR → could be either
    console.log(`0x${addr.toString(16).padStart(6,'0')}: next opcode = 0x${opcode.toString(16).padStart(2,'0')} + 8 bytes: ${Array.from(rom.slice(nextInstr, nextInstr+8)).map(b=>'0x'+b.toString(16).padStart(2,'0')).join(' ')}`);
}
```

Then for sites classified as REGISTRATION, run a dynamic trace to see what gets written to the D3FFFF region.
