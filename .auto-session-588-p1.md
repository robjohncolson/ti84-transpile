# Task: Decode 0x0021C2 — System Vector 0 Target

## Context
0x0021C2 is the target of jump table entry 0 at ROM address 0x000138 (JP 0x0021C2). The OS system jump table at 0x000138 has 50 entries × 4 bytes. When 0x0229C5 (event helper) does `CALL 0x000138`, it's calling vector 0 which jumps to 0x0021C2.

Session 568 already decoded 0x0021C2 as a "syscall null-check" (12B). Session 569 decoded the 0x0021xx cluster as ~182B. We need DEEPER analysis: what does 0x0021C2 actually DO beyond the initial null-check? Trace its full control flow.

## Deliverable
Create `TI-84_Plus_CE/probe-phase588-decode-0021C2.mjs` that:
1. Reads `TI-84_Plus_CE/ROM.rom` (path relative to repo root)
2. Disassembles starting at 0x0021C2 for up to 300 bytes
3. Follows all branch/call targets within the function
4. Identifies all RAM references (0xD00000-0xD3FFFF range), IY-relative refs, port I/O
5. Cross-references all CALL targets and JP targets
6. Prints a formatted disassembly with hex addresses, raw bytes, and mnemonics
7. Prints a summary: function boundaries, purpose hypothesis, all call targets, all RAM refs

## Decoder API
Use a HAND-ROLLED inline decoder. Do NOT import from ez80-decoder.js. The working pattern from recent probes:
- `const rom = fs.readFileSync('TI-84_Plus_CE/ROM.rom');`
- Read bytes directly: `rom[offset]`, `rom[offset] | (rom[offset+1] << 8)` for 16-bit, add `| (rom[offset+2] << 16)` for 24-bit
- Handle eZ80 prefixes: 0xDD=IX, 0xFD=IY, 0xED=extended, 0xCB=bit ops
- Handle .SIS prefix 0x40 (forces 16-bit operands in ADL mode)
- Key opcodes to handle correctly:
  - 0xFE = CP n (immediate compare), NOT a prefix
  - 0xCD = CALL nn (3-byte address in ADL mode)
  - 0xC3 = JP nn, 0x18 = JR d, 0x20/0x28/0x30/0x38 = JR cc,d
  - 0xC9 = RET
  - 0x3E = LD A,n
  - 0xCB prefix for BIT/RES/SET ops
  - 0xED prefix for block ops (LDIR=0xB0, CPIR=0xB1, etc.) and IN/OUT
