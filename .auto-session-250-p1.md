# Session 250 P1: Trace 0x02FFAE dispatch path — why converted key never reaches cxMain

## Context
This is a TI-84 Plus CE ROM transpilation project. The ROM is lifted to JavaScript blocks. We run probes that execute these blocks to trace OS behavior.

Session 249 discovered that when key "2" (scan code 0x8F) is injected into the event loop at D0058E, the key IS picked up (step 12, A=0x8F via stub at 0x03FA09), enters normal dispatch at 0x02FFAE (step 34), key is converted from 0x8F→0x9C at 0x0302EB, but then A=0x40 at step 36 (from D007E0 mode flags), and the path goes through 0x022346→0x000578→0x0158A6 and loops back to 0x02FD99 WITHOUT ever reaching cxMain at 0x0585D3/0x0585E9 or any key handler.

## Task
Write a probe `TI-84_Plus_CE/probe-phase250-dispatch-branch-trace.mjs` that:

1. Boots the OS (same pattern as `probe-phase249-event-loop-digit-trace.mjs` — copy its boot sequence exactly)
2. Reaches the idle HALT at 0x040D40
3. Injects key "2" (D0058E = 0x8F)
4. Runs with DETAILED per-step tracing through the dispatch path, specifically:
   - Log EVERY block visited from the moment A=0x8F is loaded (step ~12) through when execution returns to 0x02FD99
   - For each block, log: PC, A register, F register (flags), the block's first few bytes (read from ROM), and any memory reads from D007E0, D003E0, D0058E, D0059F
   - Pay special attention to blocks at/near 0x02FFAE, 0x022346, 0x000578, 0x0158A6 — log what branch decision is made
5. After the trace, dump:
   - D007E0 value and what it means (which bits are set)
   - IY register value and IY+offset flags that were tested (check IY+0 through IY+100 for any non-zero bytes)
   - D003E0, D0059F, D003DD values
   - The exact block sequence from key pickup to loop-back

- Stages: 0x0A2B72, 0x0A3301, 0x0A29EC, 0x0A2854
- DISPATCHER_ENTRY = 0x02FD8F, EVENT_LOOP_REENTRY = 0x02FD99

- D00000 must be 0xCC for HALT gate
- Timer interrupt MUST be disabled: `createPeripheralBus({ timerInterrupt: false })`
