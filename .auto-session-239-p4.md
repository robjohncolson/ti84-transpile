# Task: Trace APD RAM-based counter that 0x03030E reads

## Context
You are working on a TI-84 Plus CE ROM transpilation project. The ROM is lifted to JavaScript and run via `cpu-runtime.js` + `peripherals.js` + `ROM.transpiled.js`.

Session 237 decoded the housekeeping block at **0x03030E** as an APD (Auto Power Down) timer check. It compares HL against threshold values 0xFFFF/0xFFFE/0xFFFD for idle timeout stages. Session 238 confirmed that ALL 4 HL values (0xFFFF/0xFFFE/0xFFFD/0x0000) take identical paths — the comparisons read from a **RAM-based APD counter**, NOT from the register HL value passed in.

The question is: **which RAM address does 0x03030E actually read to get the APD counter value?**

## Task
Create a probe `TI-84_Plus_CE/probe-phase239-apd-counter-address.mjs` that:

1. Boots the CPU (z80 boot → kernelInit → memInit)
2. Disassembles the block at 0x03030E from the ROM binary to find:
   - What instructions load the counter value (LD HL,(addr)? LD A,(addr)? LD BC,(addr)?)
   - The exact RAM address being read
   - How the comparison chain works (CP? SBC? SUB?)
3. Runs 0x03030E dynamically with different RAM values seeded at the identified counter address:
   - Experiment A: counter = 0x0000 (fresh boot)
   - Experiment B: counter = 0x7FFF (mid-range)
   - Experiment C: counter = 0xFFFD (near threshold)
   - Experiment D: counter = 0xFFFF (at max threshold)
4. For each experiment, track:
   - Which blocks are visited (do different counter values take different paths?)
   - Which RAM addresses are READ during execution (use read watchpoints on D000xx-D003xx range)
   - IY flag changes
   - Whether any of the APD subroutines fire (0x07F9FB, 0x08383D, 0x03E141)

The key insight from session 238 is that the threshold comparison reads from RAM, not from the HL register. So we need to find which specific RAM address contains the APD idle counter.

Also disassemble 10-15 instructions starting at 0x03030E from the ROM binary to see the actual instruction sequence.
