# Task: Investigate What Sets IX=0xD140B3 Before 0x00BC47

## Context
In the TI-84 CE ROM transpilation project, the SP corruption root cause is fully understood:
- Block 0x00BC47 at instruction 0x00BC4D does `LD IX, (IX-30)` to follow a linked-list pointer
- When IX=0xD140B3 (an array/table base with 27 ROM references), (IX-30)=0xD14095 contains garbage flag bytes (0x01,0x00,0x00) that get interpreted as a ROM pointer 0x010000
- Block 0x00BC72 then does `LD SP, IX` → SP=0x010000 (ROM space) → crash

The question: **What code calls 0x00BC47 (or its parent block 0x00BC31) with IX=0xD140B3?** Is it a specific init routine, or is 0xD140B3 a parameter passed from the event loop?

## Your task
Create `TI-84_Plus_CE/probe-phase367-ix-caller.mjs` that:

1. Uses the standard multi-phase boot pattern (copy from below)
2. After coldBoot, runs the event loop for ~10,000 steps with an **instruction-level trace** that logs every block where IX changes value
3. Specifically tracks:
   - Every block that modifies IX (LD IX, PUSH/POP IX, LEA IX, ADD IX, etc.)
   - The block that sets IX to 0xD140B3 specifically
   - The CALL/JP chain leading to 0x00BC31/0x00BC47
   - What value IX has when entering 0x00BC31

4. Reports:
   - The full call chain: which block sets IX=0xD140B3, which block calls 0x00BC31
   - Whether 0xD140B3 is loaded from a RAM address (and which one)
   - Whether IX=0xD140B3 is always the value at 0x00BC47 entry, or if it varies

## Multi-phase boot pattern (REQUIRED)
```javascript
#!/usr/bin/env node
import fs from 'node:fs';
import path from 'node:path';
import { fileURLToPath, pathToFileURL } from 'node:url';
import { createExecutor } from './cpu-runtime.js';
import { createPeripheralBus } from './peripherals.js';

const __dirname = path.dirname(fileURLToPath(import.meta.url));
const romBytes = fs.readFileSync(path.join(__dirname, 'ROM.rom'));
const romModule = await import(pathToFileURL(path.join(__dirname, 'ROM.transpiled.js')).href);
const BLOCKS = romModule.PRELIFTED_BLOCKS;

const STACK_RESET_TOP = 0xD1A87E;

const peripherals = createPeripheralBus({ timerInterrupt: false });
const executor = createExecutor(BLOCKS, peripherals, romBytes);
const { cpu, mem } = executor;

// Phase 1: Z80 cold boot
executor.runFrom(0x000000, 'z80', { maxSteps: 20000, maxLoopIterations: 32 });

// Reset CPU state between phases
cpu.halted = false;
cpu.iff1 = 0;
cpu.iff2 = 0;
cpu.sp = STACK_RESET_TOP - 3;
mem.fill(0xFF, cpu.sp, cpu.sp + 3);

// Phase 2: Kernel init (ADL)
executor.runFrom(0x08C331, 'adl', { maxSteps: 100000, maxLoopIterations: 10000 });

// Set OS state
cpu.mbase = 0xD0;
cpu._iy = 0xD00080;
cpu._hl = 0;
cpu.halted = false;
cpu.iff1 = 0;
cpu.iff2 = 0;
cpu.sp = STACK_RESET_TOP - 3;
mem.fill(0xFF, cpu.sp, cpu.sp + 3);

// Phase 3: Post-init
executor.runFrom(0x0802B2, 'adl', { maxSteps: 100, maxLoopIterations: 32 });
```

After coldBoot, to trace IX changes you'll need to use a stepping approach. The `executor.runFrom()` with `maxSteps: 1` per iteration is one way, though slow. A better approach: use `onBlock` callback if available, or run with maxSteps=10000 and use `executor.runFrom()` with a custom block visitor.

Alternatively, use a simpler approach: instrument a SHORT run (1000 steps) looking specifically for blocks 0x00BC31 and 0x00BC47. Use the `executor` object's `onBlock` or similar callback mechanism. Check `cpu-runtime.js` for available hooks.

If no hook mechanism exists, use the ROM disassembly approach instead:
- Statically scan ROM bytes for CALL/JP instructions targeting 0x00BC31 or 0x00BC47
- Report all callers found in ROM
- For each caller, disassemble the surrounding context to determine what IX value it establishes

## Key addresses
- 0x00BC31: Parent block (loop entry)
- 0x00BC47: The LD IX,(IX-30) instruction that corrupts IX
- 0x00BC72: The LD SP,IX that crashes
- 0xD140B3: The array/table base loaded into IX (27 ROM references)
- 0xD14095: (IX-30) when IX=0xD140B3 — contains flag bytes, not a pointer
