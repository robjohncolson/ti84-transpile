# Auto-Session 222 — P3: Trace ISR Key Code Delivery Chain (0x000038 → 0x02F68A)

## Context

You are working on a TI-84 Plus CE ROM transpilation project. The ROM (eZ80, 4MB) has been lifted to JavaScript. Key files:
- `TI-84_Plus_CE/ROM.rom` — raw ROM binary
- `TI-84_Plus_CE/cpu-runtime.js` — eZ80 runtime + memory
- `TI-84_Plus_CE/peripherals.js` — LCD/keyboard/timer MMIO
- `scripts/transpile-ti84-rom.mjs` — transpiler

## Background

Session 221 discovered that **_GetKey (0x04AB5D) is interrupt-driven** — it HALTs at 0x0019B5 and waits for the ISR to deliver a key code via memory location 0x02F68A. The ISR chain is:
- 0x000038 (RST 38h / maskable interrupt vector)
- → 0x0006F3 
- → 0x001713 (known ISR dispatch gate)

The scan-to-keycode conversion happens INSIDE this ISR chain, not in a static lookup table near _GetKey. The direct keyboard scanner at 0x0159C0 correctly reads raw scan codes (e.g., 0x21, 0x31, 0x42, 0x60, 0x64), but these raw scan codes (0x00-0x67) are NOT the same as key codes (0x5A-0xFF range used by ConvKeyToTok).

The question: **How does the ISR convert raw scan codes to key codes, and where is the conversion table?**

## Task

Build a probe `TI-84_Plus_CE/probe-phase222-isr-keycode-chain.mjs` that:

1. **Disassemble the ISR chain statically**: Read ROM.rom and disassemble:
   - 0x000038-0x000060 (RST 38h handler)
   - 0x0006F3-0x000750 (next link in chain)
   - 0x001713-0x001780 (ISR dispatch gate — already known from timer IRQ work)
   - Look for CALL/JP instructions that lead to keyboard-specific ISR handlers
   - Follow the chain until you find code that reads keyboard port registers (port 0xA00F for key group, port 0xA010-0xA017 for scan data) or references 0x0159C0 (direct scanner)

2. **Find the scan-to-keycode conversion table**: The conversion from scan codes (0x00-0x67) to key codes must use a lookup table somewhere in ROM. Search ROM.rom for a 104-byte (or 112-byte or 128-byte) region near the ISR code that could be this table. Heuristic: look for a region where:
   - Bytes in range 0x00-0xFF that could be key codes
   - Position 0x8F (scan code for '1') should contain the key code for '1'
   - Position 0x8E should contain the key code for '0'
   - The table is indexed by scan code and returns key code
   
   Alternative: the table might be indexed differently. Scan codes are `(row << 4) | bit` format, so the table might be organized as 7 rows × 8 columns.

3. **Trace the ISR dynamically with a key pre-loaded**: 
   - Set up a minimal runtime with keyboard port register primed to indicate key '1' is pressed:
     - Key '1' is at scan code 0x8F = row 8 (group 0xFF - keyboard row), bit 7 (or similar)
     - Actually, scan code 0x8F: row = 0x8F >> 4 = 8, bit = 0x8F & 0x0F = 15. Hmm, scan codes in the TI-84 are different from this.
     - From session 220: scan codes 0x00-0x67 across 7 rows. Digit '1' has scan code 0x8F in ConvKeyToTok terms but that's the KEY CODE, not the scan code.
     - Actually, per session 220: _GetCSC returns scan codes 0x00-0x67 (49 active). ConvKeyToTok accepts values ≥ 0x5A (key codes). The mapping from GetCSC scan codes to GetKey key codes is what we're looking for.
   - Try: enter the ISR at 0x000038 with keyboard port data pre-loaded, trace up to 500 steps, log every block and any writes to 0x02F68A or nearby key storage.

4. **Cross-reference with known mappings**: Session 220 mapped 49 scan codes. Session 186 mapped the ConvKeyToTok primary table (key codes 0x5A-0xFF → tokens). Find where scan code X maps to key code Y by finding the table that bridges these two numbering systems.

## How to boot the runtime

```javascript
import { readFileSync } from 'fs';
const ROM = readFileSync('TI-84_Plus_CE/ROM.rom');
const { createCPU } = await import('./TI-84_Plus_CE/cpu-runtime.js');
const { createPeripheralBus } = await import('./TI-84_Plus_CE/peripherals.js');

const peri = createPeripheralBus({ timerInterrupt: false });
const cpu = createCPU(peri);

// Load ROM
for (let i = 0; i < ROM.length; i++) cpu.mem[i] = ROM[i];

// Minimal init
cpu.mbase = 0xD0;
cpu.sp = 0xD1A87E;
cpu.iy = 0xD00080;
```
