# Task: Trace 0x005A75 Font Rendering — Full VRAM Write Logic

## Context
You are working on a TI-84 Plus CE ROM transpiler project. The ROM file is at `TI-84_Plus_CE/ROM.rom` (4MB eZ80 binary, little-endian).

Session 477 partially decoded the character renderer at `0x005A75`:
- DI; PUSH all registers
- If A ≥ 0xFA → clamp to 0xD0
- LD H,0x1C; LD L,A → font table at 0x1C00 + charcode
- Computes VRAM address from D0059C
- Writes 16 pixel rows

But we need the FULL VRAM write logic to understand:
1. **Pixel format**: 8bpp? 16bpp? (The TI-84 CE LCD is 320×240 at 16bpp = 153,600 bytes total VRAM)
2. **Row stride**: How many bytes between each pixel row (320 pixels × 2 bytes = 640 bytes per row)
3. **Character dimensions**: How many pixels wide × 16 tall?
4. **Font data format**: What's at 0x1C00+charcode? A pointer? Direct bitmap?

## What to do

Create: `TI-84_Plus_CE/probe-phase478-font-render-decode.mjs`

### Part 1: Hex dump the font renderer function
Read and hex-dump ROM bytes from `0x005A75` to `0x005B00` (approximately — dump 140 bytes to be safe). Print each byte as hex, 16 per line, with the starting address.

### Part 2: Hex dump font table entries
The font table is at `0x1C00 + charcode`. For characters:
- 0x48 ('H'), 0x41 ('A'), 0x30 ('0'), 0x20 (space), 0xE1 (cursor glyph 1)

For each: read 16 bytes at `0x1C00 + charcode` (if it's direct bitmap data) AND read 16 bytes at the address pointed to by `0x1C00 + charcode` (if it's a pointer table). Show both interpretations.

Actually, the instruction is `LD H,0x1C; LD L,A` which makes `HL = 0x1C00 | charcode`. In eZ80 ADL mode, HL is 24-bit, so this is `HL = 0x001C00 + A`. But the font data might be an 8-byte or 16-byte bitmap at that address. With 256 possible characters × 16 bytes each = 4096 bytes, the font table would span 0x1C00-0x2BFF.

Wait — `LD H,0x1C; LD L,A` sets HL to `0x1C00 | A` (not + A). So for A=0x48: HL = 0x1C48. For A=0x41: HL = 0x1C41. Each character gets exactly 1 byte of address space, which can't hold a bitmap. So 0x1C00+charcode must be a POINTER TABLE (each entry is a 2 or 3 byte pointer to the actual glyph data).

Hex dump 0x1C00-0x1CFF (256 bytes = full pointer table for characters 0x00-0xFF).

### Part 3: Disassemble the VRAM write loop
The key question: after the font data address is computed, how does the function write to VRAM? Look for:
- `LD (DE),A` or `LD (HL),A` — byte writes to VRAM
- `LD (DE),HL` or `LDIR` — block copy
- ADD/offset instructions that compute VRAM row stride (likely adding 640 = 0x280 per row)
- The loop counter (DJNZ or DEC B/JR NZ for 16 rows)

### Part 4: Verify VRAM layout
The VRAM is 320×240×2 = 153,600 bytes at 0xD40000-0xD65800. Session 477 found VRAM writes at 0xD40742-0xD40755 and 0xD409C2+ (spaced 0x280 = 640 bytes apart = one LCD row). This confirms 16bpp and 640-byte row stride. But what's the character width in pixels? If 6 pixels wide × 2 bytes = 12 bytes per character per row, that means 53 characters per 320-pixel line (close to the 26 chars per "line" at 0x0059C6 — but 26 is for a text column, not pixel column).

### Template
Use simple ROM file reading (no executor needed):

```javascript
#!/usr/bin/env node
import fs from 'fs';
import path from 'path';
import { fileURLToPath } from 'url';

const __filename = fileURLToPath(import.meta.url);
const __dirname = path.dirname(__filename);

const rom = fs.readFileSync(path.join(__dirname, 'ROM.rom'));

function hex(v, w = 2) { return '0x' + (v >>> 0).toString(16).toUpperCase().padStart(w, '0'); }

function hexDump(start, length, label) {
  console.log(`\n=== ${label} (${hex(start, 6)} - ${hex(start + length - 1, 6)}) ===`);
  for (let i = 0; i < length; i += 16) {
    const addr = start + i;
    const bytes = [];
    const ascii = [];
    for (let j = 0; j < 16 && (i + j) < length; j++) {
      const b = rom[addr + j];
      bytes.push(b.toString(16).padStart(2, '0'));
      ascii.push(b >= 0x20 && b < 0x7F ? String.fromCharCode(b) : '.');
    }
    console.log(`  ${hex(addr, 6)}: ${bytes.join(' ').padEnd(48)} ${ascii.join('')}`);
  }
}
```
