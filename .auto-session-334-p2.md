# Auto-Session 334 — P2: Investigate Missing Block 0xFB65ED

## Context

This is a TI-84 Plus CE ROM transpilation project. The ROM is 4MB (0x000000-0x3FFFFF). The transpiler lifts eZ80 machine code to JavaScript blocks. Session 333 traced the no-scale glyph renderer path and found it terminates at a **missing block at 0xFB65ED**.

The address 0xFB65ED is OUTSIDE the ROM range (ROM ends at 0x3FFFFF). This means it's either:
1. A computed jump target (JP (HL) or CALL (addr) where the address was loaded dynamically)
2. A RAM address (RAM is at 0xD00000-0xD65800)
3. A garbage/uninitialized value that got loaded into a register and jumped to

## Your task

Write a probe file `TI-84_Plus_CE/probe-phase334-missing-block.mjs` that investigates what 0xFB65ED actually is.

### Investigation steps

1. **Boot normally**:
   ```javascript
   import { createExecutor, createMemoryBus, createPeripheralBus, helpers } from './cpu-runtime.js';
   import fs from 'fs';
   const { hex } = helpers;
   const rom = fs.readFileSync(new URL('./ROM.rom', import.meta.url));
   const mem = createMemoryBus(rom);
   const periph = createPeripheralBus({ timerInterrupt: false });
   const executor = createExecutor(mem, periph);
   ```
   Run KERNEL_INIT: `executor.runFrom(0x08C331, { mode: 'adl', maxSteps: 100000 })`

2. **Check what's at 0xFB65ED in memory after boot**:
   - Read bytes at 0xFB65ED..0xFB65F5 (8 bytes) and log them
   - This address is way above RAM (0xD65800 is the end), so it's likely unmapped

3. **Trace the glyph renderer path to find HOW we arrive at 0xFB65ED**:
   The no-scale glyph renderer flows through these blocks (from session 333):
   ```
   053573 → 05359D → 0536A0 → 000218(sign test) → 0536AD → 0536B1 → 0536D2 → 0536D8 → 05324B(kernel helper) → 052442 → 05246E → 052483 → 053342 → 05248E → 052508 → MISSING BLOCK 0xFB65ED
   ```
   
   The last known block before the missing one is **0x052508**. Disassemble the raw ROM bytes at 0x052508 to find what instruction produces the jump to 0xFB65ED. Read 32 bytes of ROM starting at 0x052508 and decode them as eZ80 instructions (or at least identify the JP/CALL/RET instruction that exits the block).

4. **Check if 0xFB65ED could be a JP (HL) target**:
   - After boot, read registers HL, IX, IY from the executor state after running block 0x052508
   - Actually: set up the glyph rendering state as session 333 did:
     - Set fg color: `mem[0xD02688] = 0x00; mem[0xD02689] = 0x00;` (black)
     - Set bg color: `mem[0xD0268A] = 0xFF; mem[0xD0268B] = 0xFF;` (white)
     - Run from 0x053573 for up to 50000 steps and log the termination reason + lastPc
     - If it terminates at missing_block with lastPc near 0xFB65ED, that confirms the path

5. **Disassemble the exit instruction at 0x052508**:
   Read raw ROM bytes at 0x052508 for 48 bytes. Log them as hex. Look for:
   - `0xE9` = JP (HL) 
   - `0xC3 xx xx xx` = JP addr (in ADL mode, 3-byte address)
   - `0xCD xx xx xx` = CALL addr
   - `0xC9` = RET
   - `0xED 0x49` = JP (HL) in some eZ80 prefix modes
   
   Report what the exit instruction is and what register/address it uses.

6. **Also check the block at 0x05248E** (the block before 0x052508):
   Read 48 bytes at 0x05248E and log them. This may set up the register that 0x052508 uses for its jump.
