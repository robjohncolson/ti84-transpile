# Auto-Session 283 P3: Trace 0x0A1B5B glyph renderer — byte to pixels in VRAM

## Context
This is a TI-84 Plus CE ROM transpilation project. We lift eZ80 machine code into JavaScript and trace OS internals.

Session 282 traced the string renderer 0x09E11B and found it calls 0x0A1B5B for each character byte. The rendering chain is: 0x0A1B5B → 0x0A1799 → 0x07BF3E (palette) → 0x0A2D4C → 0x00038C. We need to understand 0x0A1B5B itself — how does it convert a character code (in A or a register) into pixels written to VRAM (D5xxxx)?

## Task
Write a probe file `TI-84_Plus_CE/probe-phase283-0a1b5b-glyph-renderer.mjs` that:

1. **Static disassembly of 0x0A1B5B** — decode 60+ bytes of instructions. Continue until RET or unconditional JP. Identify:
   - What register holds the character code on entry (likely A)
   - Where it looks up font/glyph data (likely a table pointer)
   - How it calculates VRAM destination address
   - What it passes to 0x0A1799

2. **Static disassembly of 0x0A1799** — decode 40+ bytes. This is the next stage in the chain. What does it do with the glyph data?

3. **Find the font table** — 0x0A1B5B likely indexes into a font bitmap table. Look for:
   - A multiply or shift by character width (e.g., multiply A by glyph height like 12 or 14)
   - A base address load (LD HL, <font-table-addr>)
   - ADD HL,DE or similar indexing

4. **Dynamic trace** — Run 0x0A1B5B with A='A' (0x41), reasonable font pointer in the expected register/RAM location (check D005E9 which session 282 identified as font ptr). Run 100 steps, log RAM writes to D5xxxx (VRAM region).

5. **Find all callers** of 0x0A1B5B — scan for `CD 5B 1B 0A` (CALL) and `C3 5B 1B 0A` (JP).
