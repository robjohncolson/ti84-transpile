# Auto-Session 363 P2: Investigate RAM Trampoline Stack Behavior

## Goal
Create a probe that specifically examines what the RAM trampoline does to SP and whether it's the source of the SP corruption into ROM space.

## Background
The RAM trampoline in `cpu-runtime.js` (lines 1146-1156) intercepts execution at RAM addresses >= 0xD00000 where no compiled block exists. It does a synthetic RET:
```javascript
const sp = cpu.sp & 0xFFFFFF;
const retAddr = cpu.mem[sp] | (cpu.mem[sp + 1] << 8) | (cpu.mem[sp + 2] << 16);
cpu.sp = (sp + 3) & 0xFFFFFF;
return retAddr;
```

The flash self-test at 0xD18C22 is copied from ROM 0x000EBB (90 bytes). The real flash self-test starts with `PUSH BC` and does complex flash operations before returning. The trampoline skips ALL of that and just does a RET.

Session 362 found that SP transitions from RAM (~0xD1A7E5 at step 2672) to ROM (~0x014C6F at step 2685). The question: does the trampoline's synthetic RET pop the correct return address, or does it pop garbage because the real function was supposed to manipulate the stack (PUSH/POP pairs) before returning?

The call chain: block 0x000D82 copies 90 bytes from ROM 0x000EBB to RAM 0xD18C22, then does `JP (IX)` to jump to 0xD18C22. The real function at 0x000EBB starts with PUSH BC. If the real function pushes N bytes onto the stack before returning, but the trampoline just does a plain RET (pops 3 bytes), then SP will be off by N bytes after the trampoline returns.

## What the probe must do
1. Boot from 0x000000 in z80 mode with timerInterrupt: false, max 5000 steps
2. Track when the RAM trampoline fires (missing block at addr >= 0xD00000)
3. For each trampoline activation, log:
   - The RAM address being trampolined
   - SP before the trampoline RET
   - The return address popped
   - SP after the trampoline RET
   - Full register dump
4. Disassemble the REAL ROM code that would have been executed at the source address (0x000EBB for 0xD18C22). Count how many PUSH/POP instructions the real code has. Determine what SP delta the real function would produce.
5. Compare: does the trampoline leave SP in the same state the real function would?
6. Specifically check: after each trampoline return, is SP still in RAM (>= 0xD00000)? If SP < 0x400000 after a trampoline return, that's the bug.

## Static analysis component
Also disassemble ROM bytes at 0x000EBB (the source of the flash self-test code copied to 0xD18C22). Decode all instructions for 90 bytes (the copied length). Count:
- How many PUSH instructions
- How many POP instructions  
- Net stack delta (each PUSH is -3 bytes in ADL mode or -2 in z80 mode, each POP is +3/+2)
- What does RET pop from the stack at the end?

The real function starts with PUSH BC. If it also does POP BC before RET, the net delta is 0 and the trampoline is correct. If it does PUSH BC but no POP BC, the trampoline's RET pops the wrong address (it pops the return address that was under the pushed BC).
