# Auto-Session 183 P1 — Trace ParseInp Error Handler Dispatch Chain

## Context
This is a TI-84 Plus CE ROM transpilation project. The ROM (eZ80 machine code) has been lifted to JavaScript. We're investigating why ParseInp (0x099914) fails with E_Undefined (errNo=0x8D) and jumps to 0x1BC300 (erased flash, all 0xFF bytes).

Session 182 RULED OUT the cxErrorEP hypothesis — patching cxErrorEP to 0x058BA9 does NOT change behavior. The error dispatch to erased flash uses a different mechanism.

## Task
Build a probe `TI-84_Plus_CE/probe-phase183-error-dispatch-trace.mjs` that traces the error handler dispatch chain step by step. Specifically:

1. Boot the ROM (cold boot + MEM_INIT as in existing probes)
2. Set up BufInsert tokens "2+3" at 0xD00A00 (tokens: 0x32, 0x70, 0x33)
3. Call ParseInp at 0x099914
4. **Instrument every block execution** to catch the exact moment errNo (at 0xD008DF) changes from 0x00 to 0x8D
5. Log the full block execution path from when errNo is first set, through the error handler dispatch, to the final JP 0x1BC300
6. For each block in the error dispatch chain, do a static disassembly (read ROM bytes, decode with ez80-decoder.js) to show what instructions execute
7. Specifically look for: any reads of the errSP (0xD008E0), any vector table reads in 0xD02500-0xD025FF range, any indirect JP that leads to 0x1BC300

## Key Addresses
- ParseInp entry: 0x099914
- errNo: 0xD008DF
- errSP: 0xD008E0 (3 bytes, 24-bit SP value)
- cxErrorEP: 0xD007D6 (3 bytes, 24-bit address — session 182 proved this is 0x000000 and irrelevant)
- appErr area: 0xD02500-0xD025FF (possible vector table — check if anything is populated)
- 0x1BC300: erased flash (all 0xFF) — this is where the error dispatch incorrectly jumps

## Output Format
Print structured JSON with:
- `errNoSetBlock`: the PC where errNo first becomes 0x8D

- `errSPValue`: the errSP value when errNo is set
