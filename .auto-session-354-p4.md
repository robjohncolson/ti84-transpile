# Auto-Session 354 — Priority 4: Trace Call Stack Through One Cycle

## Context
The TI-84 Plus CE boot reaches 270 unique blocks then loops in LCD init with a ~2174-step cycle period. The loop is at the CALL/RET level, not port-gated. We need to trace the subroutine call stack through one complete cycle to find which RET goes back to a caller that reinvokes the LCD init.

## Task
Create a probe `TI-84_Plus_CE/probe-phase354-call-stack-trace.mjs` that records all CALL and RET instructions through one full cycle.

### Approach
1. Boot the CPU for 3000 steps (past initial setup, into the cycling region)
2. For the next 3000 steps, record every instruction where the opcode is a CALL or RET variant:
   - CALL nn = CD nn nn (or with prefixes for eZ80 CALL nn,nn,nn)
   - CALL cc,nn = conditional calls (C4, CC, D4, DC, E4, EC, F4, FC)
   - RET = C9
   - RET cc = conditional returns (C0, C8, D0, D8, E0, E8, F0, F8)
   - RST n = restart calls (C7, CF, D7, DF, E7, EF, F7, FF)

For each CALL/RET event, record:
- Step number
- PC (address of the CALL/RET instruction)
- Type (CALL/RET/RST)
- Target address (for CALLs: the destination; for RETs: the return address from stack)
- Current stack pointer (SP)

3. Build a call tree showing the nesting structure
4. Identify which CALL-RET pair spans the cycle boundary (i.e., which function returns and then gets called again to start the next cycle)

### How to Detect CALL/RET
Read the opcode byte at cpu.pc before each step. The CPU memory can be read via the rom array for addresses < 0x400000. For RAM addresses >= 0xD00000, use cpu.mem (the full memory array).

```javascript
function getOpcode(cpu, rom) {
  const pc = cpu.pc;
  if (pc < 0x400000) return rom[pc];
  if (pc >= 0xD00000 && pc < 0x1000000) return cpu.mem[pc];
  return 0; // unmapped
}
```

Note: eZ80 has prefix bytes (0x40, 0x49, 0x52, 0x5B for .SIS/.SIL/.LIS/.LIL) that precede the actual opcode. If the first byte is one of these prefixes, the actual opcode is the NEXT byte. Also watch for DD/FD (IX/IY) prefixes and ED prefix (extended instructions).

For a simpler approach: just track SP changes. A CALL pushes the return address (SP decreases by 3 in ADL mode or 2 in z80 mode), and a RET pops it (SP increases). Track (step, pc, sp_before, sp_after) for every step where SP changes by exactly 2 or 3.
