# Task: Test D00080 Bit 4 Fix — Display Update Unlock

## Context
You are working on a TI-84 Plus CE ROM transpilation project. The OS has been lifted from eZ80 machine code to JavaScript. We've been tracing the OS event loop and discovered that display updates never fire during key processing because of a gate flag.

## Discovery from Session 473
The key handler chain at 0x02FE89 works like this:
- 0x02FE9D: SET 0,(IY+0x1D) = D0009D bit 0 (ALWAYS set for non-0xFF keys)
- 0x02FEA1: BIT 4,(IY+0x00) = D00080 bit 4 TEST
- 0x02FEA5: JR Z,0x02FEB7 (if D00080 bit 4 CLEAR → SKIP cursor update!)
- 0x02FEA7: RES 0,(IY+0x1D) = D0009D bit 0 (CLEAR — only if bit 4 was set!)
- 0x02FEAB: CALL 0x030300 (cursor/display prep — only if D0009D was cleared)
- 0x02FEAF: RES 4,(IY+0x00) = D00080 bit 4 (consumed)

Our probes have been setting D00080=0x08 (bit 3 only). Without bit 4, D0009D stays SET and ALL 0x030300 calls exit immediately via `BIT 0,(IY+0x1D); RET NZ`.

0x030300 body: BIT 0,(IY+0x1D); RET NZ → RES 3,(IY+0x08)=D00088 bit 3 → CALL 0x040D11 (cursor timing) → RET.

## Your Task
Create a probe file `TI-84_Plus_CE/probe-phase474-d00080-bit4-fix.mjs` that tests setting D00080=0x18 (bits 3 AND 4) instead of just 0x08.

## Probe Structure
Use `TI-84_Plus_CE/probe-phase473-enhanced-persistent.mjs` as a template. Key changes:

1. **3-stage boot** (same as template):
   - Stage 1: runFrom(0x000000, 'z80', maxSteps:20000, maxLoopIterations:32)
   - Stage 2: runFrom(0x08C331, 'adl', maxSteps:200000, maxLoopIterations:500)
   - Stage 3: runFrom(0x0802B2, 'adl', maxSteps:200000, maxLoopIterations:500)
   - Reset cpu/stack between stages as in template

2. **State setup AFTER boot**:
   - `mem[0xD00587] = 0x09;` (ENTER key scan code)
   - `mem[0xD00080] |= 0x18;` ← THE FIX: bits 3 AND 4 (was 0x08)
   - `mem[0xD14091] = 1;` (key processing enable gate)
   - `mem[0xD00824] = 0x48;` (mode = 'H' home screen)
   - `mem[0xD007E0] = 0x48;`
   - `mem[0xD000B4] |= 0x01;` (display path enable)
   - `mem[0xD000C6] |= 0x01;`
   - `mem[0xD177BA] = 0x7F;`
   - `mem[0xD177B7] = 0x00;`
   - `mem[0xD00088] |= 0x08;`

3. **Run from 0x02FDBE** with:
   - maxSteps: 500000
   - maxLoopIterations: 50000
   - diHaltBypass: true
   - Stack: write 0x02FDBE as return address at SP
   - onBlock callback that restores return address at RET points (0x02FE88, 0x02FDE5, 0x02FE22)

4. **Track these PCs** (hit counts + first 10 hits with step numbers):
   - 0x02FDBE, 0x02FE88, 0x03FA09, 0x02FDD8, 0x02FE89
   - 0x02FFAE, 0x02FFED, 0x030300, 0x040D11, 0x0059C6
   - 0x02FEA7 (D0009D RES — proves bit 4 worked!)
   - 0x02FEAB (CALL 0x030300 from key handler — proves display prep reached!)
   - 0x03FBDE (buffer-full guard)

5. **Second key injection**: On 0x03FA09 hit #2+, if D00587==0x00, inject key "1" (0x31) with D00080 |= 0x18

6. **Report**:
   - Hit counts for all tracked PCs
   - VRAM bytes changed (compare before/after, range 0xD40000-0xD65800)
   - D0009D value before and after run
   - D00080 value before and after run
   - D141B5 value after run
   - JSON summary at end
