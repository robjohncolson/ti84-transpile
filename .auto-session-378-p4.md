# Task: Investigate HALT at 0x0019B5 — Is It EI+HALT? Does Timer Unlock It?

## Context
Session 377 found that both GPIO-fixed key dispatch scenarios halt at 0x0019B5 after ~170K steps. This is the point where the OS stops after processing a key. Understanding this HALT is critical — if it's an EI+HALT waiting for a timer interrupt, enabling timerInterrupt:true should make execution continue.

From session 371: 0x0019B5 was previously seen as a halt point during standard boot. The question is whether this is the same HALT or a different one reached via the key dispatch path.

## Deliverable
Create `TI-84_Plus_CE/probe-phase378-halt-0019B5.mjs` that:

1. **Static disassembly of 0x0019B5 and surrounding context**: Read ROM bytes at 0x0019A0-0x0019D0 and disassemble. Determine:
   - Is 0x0019B5 a HALT instruction (opcode 0x76)?
   - What precedes it? EI (0xFB) before HALT means "wait for interrupt"
   - What follows it? After interrupt fires and returns, execution continues at PC+1
   - Is there a DI (0xF3) anywhere nearby?

2. **Test with timerInterrupt:true**: Boot through phases 1-3, inject ENTER key, but use `createPeripheralBus({ timerInterrupt: true })` for the event loop phase. Run from 0x003A73 with 500K steps. Compare:
   - Does execution continue past 0x0019B5?
   - How many additional blocks are reached?
   - Where does it halt/terminate next?
   - Does the event loop re-enter 0x003A73 (key scan loop)?

3. **Test with timerInterrupt:false (control)**: Same boot + key injection but `timerInterrupt: false`. Confirm halt at 0x0019B5 at ~170K steps.

4. **Report**:
   - The disassembly of 0x0019A0-0x0019D0
   - Whether EI precedes HALT
   - Timer-enabled: total steps, unique blocks, final PC, whether 0x003A73 is re-entered
   - Control: total steps, unique blocks, final PC
