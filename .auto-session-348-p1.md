# Auto-Session 348 — Priority 1: Fix 0x0008BB ROM Signature Check (Boot HALT Root Cause)

## Context

The TI-84 CE boot at address 0x00004F does `CALL 0x0008BB` then `JP NZ,0x0019B5`. If the call returns NZ (non-zero flag), boot diverts to a DI+HALT loop that freezes execution. 

The function at 0x0008BB does:
```
LD HL,(0x000100)   ; load 3 bytes from RAM address 0x000100
LD BC,0xA55A       ; magic constant
OR A               ; clear carry
SBC HL,BC          ; subtract: sets Z if HL == BC
RET                ; Z flag = pass, NZ = fail
```

It returns Z (pass) when `mem[0x000100..0x000102] == 0x00A55A` (little-endian: 0x5A at 0x000100, 0xA5 at 0x000101, 0x00 at 0x000102).

Currently the RAM at 0x000100 is uninitialized (all zeros), so the SBC returns NZ, causing boot to halt.

## Task

1. Modify `TI-84_Plus_CE/cpu-runtime.js` to initialize the ROM signature bytes at boot time. In the `createCPU()` function (or wherever the memory array is first set up), AFTER the memory is created but BEFORE execution begins, write:
   ```javascript
   mem[0x000100] = 0x5A;
   mem[0x000101] = 0xA5;
   mem[0x000102] = 0x00;
   ```
   
   Look for existing memory initialization patterns (there may already be seed writes for other addresses). Place this near them.

2. Write a probe `TI-84_Plus_CE/probe-phase348-rom-signature-fix.mjs` that:
   - Boots from 0x000000 with `timerInterrupt: false`
   - Traces execution for 5000 steps
   - Confirms that 0x0008BB is reached and returns with Z flag SET (not NZ)
   - Confirms that 0x0019B5 (the HALT stub) is NOT reached
   - Reports how far boot gets AFTER passing 0x00004F — what's the furthest PC reached?
   - Lists any `missing_block` terminations encountered
