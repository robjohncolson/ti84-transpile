# Auto-session 340 P1: Diagnose kernel init halt at 0x0019B5

## Context

The TI-84 Plus CE ROM transpiler boots the OS but kernel init halts after only 712 steps at address 0x0019B5. This is far too early — the OS never reaches CoorMon (0x08BF22), GetCSC (0x042366), or context dispatch (0x08C8B5). The cxMain pointer at 0xD007CA stays 0x000000 — never populated.

0x0019B5 is a known hardware halt stub (writes to port 0x00, then HALT instruction). The question is: what triggers the jump to 0x0019B5 during init?

## Task

Create a probe `TI-84_Plus_CE/probe-phase340-kernel-halt-trace.mjs` that:

1. Boots the OS the same way as existing probes (see `TI-84_Plus_CE/probe-phase339-extended-kernel-init.mjs` for reference — read it first)
2. Runs kernel init with per-STEP instruction logging for all 712 steps (not just per-block — we need every instruction)
3. For each step, log: `step#, PC, opcode bytes (first 4), mnemonic if available, any CALL/JP/JR targets`
4. Specifically watch for:
   - Any JP/CALL to 0x0019B5 (direct jump to halt)
   - Any JP/CALL to 0x000028 (rst 0x28 = FP EXIT chain that ends at 0x0019B5)
   - Any port IN/OUT instructions (which port, what value)
   - Any conditional jumps and whether they were taken
5. At the end, report: "Halt triggered by instruction at PC=0xNNNNNN (step N): <mnemonic>"

## Key Architecture

- Runtime: `import { createCPU } from './cpu-runtime.js'` and `import { createPeripheralBus } from './peripherals.js'`
- Boot: `const cpu = createCPU(rom); const bus = createPeripheralBus({ timerInterrupt: false }); cpu.setPeripheralBus(bus);`
- The CPU object has: `cpu.pc`, `cpu.step()` returns `{ pc, steps, term }`, `cpu.mem` is the memory array
- ROM is loaded from `./ROM.rom` via `fs.readFileSync`
- Use `cpu.step()` in a loop, checking `cpu.pc` after each step
- The CPU starts at PC=0x000000 (reset vector)
- To read ROM bytes at an address: `rom[addr]`, `rom[addr+1]`, etc.
- Timer IRQ MUST be disabled: `createPeripheralBus({ timerInterrupt: false })`
