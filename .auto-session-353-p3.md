# Task: Investigate Port 0xD018 (LCD Controller Status) Boot Gate

## Context
The TI-84 Plus CE ROM transpilation project boots the OS from 0x000000 in z80 mode. After session 352, boot reaches 270 unique blocks but enters a steady-state loop. Port 0xD018 is read 24 times during boot, always returning 0xFF (unhandled default). This port is in the LCD controller range (0xD000-0xDFFF). On real hardware, port 0xD018 may be an LCD status/busy register. The wrong return value may prevent boot from advancing past LCD initialization.

## What You Must Do
Create a probe `TI-84_Plus_CE/probe-phase353-portD018-analysis.mjs` that:

1. Boots from 0x000000 in z80 mode with `{ pllDelay: 2, timerInterrupt: false }` for 5000 steps
2. Intercepts ALL reads from port 0xD018 with context: PC address, step number, A register value
3. For each unique PC that reads port 0xD018, disassembles 20 bytes from that PC showing what the code does with the read value (BIT tests, AND masks, CP compares, conditional jumps)
4. Then runs THREE additional tests:
   - Port 0xD018 returns 0x00 (LCD idle/ready)
   - Port 0xD018 returns 0x04 (common LCD ready bit pattern)
   - Port 0xD018 returns 0x80 (busy bit in MSB)
   Compare unique block counts and whether the loop breaks.
5. Reports which return value (if any) advances boot past 270 blocks

## Technical Details

Port 0xD018 is NOT registered in peripherals.js. The default read handler at line 198 returns 0xFF. Related LCD ports that ARE registered:
- 0xD00C → returns 0x02 (SPI status, "idle")
- 0xD00D → returns 0x00
- 0xD008 → gets 788 writes during boot (SPI data out)

To register a test handler:
```javascript
const peripherals = createPeripheralBus({ pllDelay: 2, timerInterrupt: false });
peripherals.register(0xD018, { read() { return VALUE; }, write() {} });
```

Note: `register` takes raw port number. `normalizePort` does `Number(port) & 0xFFFF` so 0xD018 stays 0xD018.
