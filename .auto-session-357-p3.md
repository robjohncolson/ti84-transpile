# Task: Per-instruction port trace during NMI handler — read/write ordering

## Context
The TI-84 CE NMI handler both reads AND writes port 0x28 during each wake cycle. Session 356 found:
- Port reads: IN 0x28 → 0x04 (twice)
- Port writes: OUT 0x28 ← 0xD0

The PLL handler (port 0x28, peripherals.js) only resets the lock countdown when a DIFFERENT value is written than lastWrite. The NMI handler writes 0xD0 every cycle. If 0xD0 equals lastWrite, the write is a no-op — PLL stays locked, reads keep returning 0x04.

But there's a subtlety: does the WRITE happen BEFORE or AFTER the READS within a single NMI wake? If the write happens first with a new value, it would reset the PLL, and subsequent reads in that same handler invocation would return 0x00. But if reads come first (getting 0x04), and the write comes after (setting lastWrite=0xD0), then the next NMI's reads would still see locked=true because the write matched lastWrite.

## What to do
Create a probe file `TI-84_Plus_CE/probe-phase357-port-ordering.mjs` that:

1. Boots the ROM normally (timerInterrupt: false) for ~5000 steps to reach HALT at 0x0019B5
2. Wraps the peripheral bus port handlers to intercept ALL reads and writes, recording:
   - The current block address (from cpu.pc or the block being executed)
   - The step number within the NMI handler
   - Port number
   - Read vs Write
   - Value read or written
   - For port 0x28: the PLL state before AND after the operation (locked, remainingReads, lastWrite)
3. Triggers exactly 3 NMI wakes
4. For each NMI wake, prints a chronological table of ALL port operations:
   ```
   NMI #1:
     Step  Block     Op     Port  Value  PLL.locked  PLL.remainingReads  PLL.lastWrite
     1     0x000066  READ   0x3D  0x01   true        0                   0xD0
     2     0x000071  WRITE  0x3E  0x01   true        0                   0xD0
     ...
   ```

## How to intercept port operations
The peripheral bus in peripherals.js has read/write methods. You can either:
- Monkey-patch `cpu.in()` and `cpu.out()` (if those exist on the CPU object)
- Or wrap the bus's portIn/portOut functions
- Look at how `probe-phase356-nmi-handler-trace.mjs` captures port operations — it likely has a pattern you can extend

Check the cpu-runtime.js to see how port I/O is dispatched. The CPU object has `portIn(port)` and `portOut(port, value)` methods (or similar). Wrap these.

## Key implementation details
- Use `import { createCPU } from './cpu-runtime.js'` and `import { createPeripheralBus } from './peripherals.js'`
- Boot with `createPeripheralBus({ timerInterrupt: false })`
- Access PLL state via `bus.getState().pll`
- NMI trigger: `cpu.triggerNMI()` when execution HALTs
- Record the execution block (cpu.pc) at the time of each port operation
