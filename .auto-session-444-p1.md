# Task: Implement HALT-Wake in Workflow Probe

## Context
The file `TI-84_Plus_CE/probe-workflow-arithmetic.mjs` is a workflow probe that tests "1 + 1 ENTER → 2" by injecting keys into the OS event loop. Currently, after the first key '1' processes through the event loop at 0x003A73, the CPU hits DI+HALT at address 0x001942 (wrapper function at 0x001933). Subsequent keys only advance 1 step because they start from the HALT address.

## The Fix
The cpu-runtime.js already has a `diHaltBypass` mechanism (lines 1098-1100, 1322-1336). When `opts.diHaltBypass` is true, hitting DI+HALT redirects execution back to `diHaltBypassEntry` (defaults to 0x003A73 = `COLDBOOT_EVENT_LOOP_ENTRY`). The workflow probe currently does NOT pass this option.

## What To Do
Edit `TI-84_Plus_CE/probe-workflow-arithmetic.mjs`:

1. In the `pressKey` section (around line 130), add `diHaltBypass: true` to the runFrom options object:
```js
pressResult = executor.runFrom(currentPc, currentMode, {
  maxSteps: STEPS_PER_PRESS,
  maxLoopIterations: MAX_LOOPS,
  diHaltBypass: true,
});
```

2. Do the same for the `releaseKey` section (around line 145):
```js
releaseResult = executor.runFrom(currentPc, currentMode, {
  maxSteps: STEPS_AFTER_RELEASE,
  maxLoopIterations: MAX_LOOPS,
  diHaltBypass: true,
});
```

3. After each key press+release cycle, if the termination was 'halt' but diHaltBypass fired, the lastPc should now be back near the event loop. But as extra insurance, add logic after the release result to detect when lastPc lands at the DI+HALT wrapper (0x001933-0x001942) and reset it:
```js
// If we ended up at the HALT barrier again, reset to event loop entry
if (releaseResult.lastPc >= 0x001933 && releaseResult.lastPc <= 0x001942) {
  currentPc = EVENT_LOOP_ENTRY;
  currentMode = 'adl';
} else {
  currentPc = releaseResult.lastPc ?? currentPc;
  currentMode = releaseResult.lastMode ?? currentMode;
}
```
Remove the existing `currentPc = pressResult.lastPc` line at ~line 140 and move the PC update to AFTER the release phase (after the if-block above).

4. Update the `currentPc` tracking: After the press phase, set `currentPc = pressResult.lastPc ?? currentPc; currentMode = pressResult.lastMode ?? currentMode;` before the release call. Then the release call uses this updated PC. After the release, apply the HALT barrier check above.

5. Add an `onWake` callback to log when HALT-wake fires:
```js
onWake: (haltPc, newPc, newMode) => {
  console.log(`    HALT-wake: haltPc=${hex(haltPc)} → newPc=${hex(newPc)} mode=${newMode}`);
},
```

## Deliverables

- The probe should now show multiple keys each processing >1 step (not just the first key)

- Keep `timerInterrupt: false` — the diHaltBypass is the solution, not timer IRQs
