# Task: Wire Event Loop Entry into Workflow Arithmetic Probe

## Context
The TI-84 Plus CE ROM transpilation project has a workflow probe `TI-84_Plus_CE/probe-workflow-arithmetic.mjs` that boots to the home screen, then injects keystrokes `1 + 1 ENTER` and checks if VRAM changes. Currently it FAILS because after boot stages complete, `resumePc=0xffffff` (the stack is filled with 0xFF so RET goes to 0xFFFFFF). The key injection then tries to `runFrom(0xffffff, ...)` which immediately errors with 0 steps.

The fix: after boot completes, switch to the known OS event loop entry point `0x003A73` for key processing. This address is the proven event loop entry used by multiple other probes (e.g., `probe-phase370-keypress-event-loop.mjs` line 14, `probe-phase368-eventloop-200k.mjs` line 14).

## What to do

Modify `TI-84_Plus_CE/probe-workflow-arithmetic.mjs` to wire the event loop:

1. **Add constants** near the top (after the existing STAGE_ENTRIES line ~33):
   ```javascript
   const EVENT_LOOP_ENTRY = 0x003A73;
   ```

2. **In the `bootToHomeScreen` function** (around line 63-96): After the stage loop completes, instead of returning `lastResult.lastPc` directly, return `EVENT_LOOP_ENTRY` as the resumePc. Change the return to:
   ```javascript
   return { lastPc: EVENT_LOOP_ENTRY, lastMode: 'adl' };
   ```

3. **Before returning from bootToHomeScreen**, add CPU state setup for the event loop (matching the proven pattern from `probe-phase370-keypress-event-loop.mjs` line 84-92):
   ```javascript
   cpu.halted = false;
   cpu.iff1 = 0;
   cpu.iff2 = 0;
   cpu.f = 0x40;
   cpu._ix = 0xD1A860;
   cpu._iy = 0xD00080;
   cpu.sp = STACK_RESET_TOP - 12;
   mem.fill(0xFF, cpu.sp, cpu.sp + 12);
   ```
   This goes right before the `return` statement in `bootToHomeScreen`.

4. **In phase 2 (key injection loop)**, increase `maxLoopIterations` to allow the event loop to run. The current values are:
   ```javascript
   const STEPS_PER_PRESS = 200000;
   const STEPS_AFTER_RELEASE = 50000;
   const MAX_LOOPS = 5000;
   ```
   These should be fine. But the key issue is that `currentPc` and `currentMode` will now start at `0x003A73` / `'adl'` instead of `0xffffff`. Verify the key injection loop already uses `currentPc` from `bootState.lastPc` — it should work automatically.

5. **Do NOT change** the assertion logic at the bottom — the probe should still check for VRAM changes, step advancement, and "2" visibility. The assertions may still fail (the event loop may hit other missing pieces), but the diagnostic should now show steps > 0 and a valid PC trace.
