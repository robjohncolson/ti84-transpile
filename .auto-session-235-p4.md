# Task: Trace 0x000578 app-context check (ooo)

## Context
You are working on a TI-84 Plus CE ROM transpilation project. The ROM is lifted to JavaScript and executed via `cpu-runtime.js`.

**0x000578** is called by 0x02237E and 0x022346 to determine Z vs NZ (app context present or not). Session 234 confirmed: on the home screen, 0x000578 returns Z=1, causing early RET from 0x02237E/0x022346 — which means the descriptor builder at 0x0236F9 is NEVER reached. In APP mode, 0x000578 returns NZ, enabling the full descriptor pipeline.

We need to understand: What does 0x000578 actually check? What RAM location(s) determine Z vs NZ? How would an app register to receive key descriptors?

## What to do
Create a probe file `TI-84_Plus_CE/probe-phase235-000578-app-context.mjs` that:

1. Imports from `./cpu-runtime.js` and loads ROM from `./ROM.rom`
2. Standard setup: `{ timerInterrupt: false }`, `cpu.mbase = 0xD0`, IY = 0xD00080

### Part A: Static disassembly
Read ROM bytes at 0x000578 through 0x0005C0 (72 bytes). Print as hex dump. Manually decode the first ~10 instructions to understand the check.

The function should be short (it's called inline from 0x02237E which is itself small). Look for:
- What memory address it reads (LD A,(...) or BIT n,(HL) or similar)
- What comparison it makes (CP, OR A, AND, BIT)
- How it sets Z/NZ flag before RET

### Part B: Dynamic trace — home screen (Z path)
Start at 0x000578 with default RAM state (all zeros or post-boot state). Run up to 100 steps. Capture:
- Every block visited
- Total steps to RET
- Z flag state at return (check cpu.flags or equivalent)
- Which RAM address was the deciding factor

### Part C: Dynamic trace — simulated APP context (NZ path)
Based on Part A's findings, seed the RAM location that 0x000578 checks to simulate an app being active. Then re-run from 0x000578. Capture same data as Part B, confirming NZ is returned.

If Part A reveals that the check reads a specific address (e.g., a pointer table or app context pointer), test with different values to map the Z/NZ threshold.

### Part D: Cross-reference
Search ROM for all CALL/JP to 0x000578 — how many callers exist? List the first 20. This tells us how widely the app-context check is used across the OS.

Search pattern in ROM binary: `CD 78 05 00` (CALL 0x000578 in ADL mode, little-endian with 3-byte address). Also check `C3 78 05 00` (JP 0x000578).

### Part E: Find what SETS the app context
From Part A, once you know which RAM address 0x000578 reads, scan ROM for writes to that address. This reveals how apps register themselves.

## Key constraints
- Do NOT modify any file except the probe file
- Use `{ timerInterrupt: false }`, `cpu.mbase = 0xD0`, IY = 0xD00080
- ROM at `TI-84_Plus_CE/ROM.rom`
- ES module imports from `./cpu-runtime.js`

## Success criteria
- Probe runs: `node TI-84_Plus_CE/probe-phase235-000578-app-context.mjs`
- Identifies which RAM address(es) control the Z/NZ decision
- Shows block chain for both Z and NZ paths
- Lists callers of 0x000578
- Identifies how app context gets armed
