# Task: Trace 0x0302EB called at 0x02FF1B after 09F79B table lookup (jjj)

## Context
You are working on the TI-84 Plus CE ROM transpilation project. We are tracing the OS key-event dispatch pipeline.

Session 233 decoded the key classification at function 0x02FE89. For non-CLEAR/non-MODE keys, the path goes:
1. 0x02FF11: `LD DE,0x09F79B` (key code table base)
2. Table lookup via offset computation
3. 0x02FF1B: `CALL 0x0302EB` — **this is the target**

After the 09F79B table lookup produces a key code in DE (or HL), 0x0302EB is called. From the session 233 trace, after this call the path continues to CALL 0x022346 → 0x022359 → 0x0236F9 (descriptor pipeline). So 0x0302EB might be a pre-processing step that transforms or validates the table result before the descriptor is built.

**BUT** — re-reading session 233 more carefully: the actual flow after the table lookup at 0x02FF11 is:
- `LD HL,A+09F79B` at 0x02FF11 (A is the offset)
- Then CALL 0x022346 at some point
- 0x0302EB might be called BETWEEN the table lookup and the descriptor builder

We need to trace exactly what 0x0302EB does.

## What to do

Create a probe file `TI-84_Plus_CE/probe-phase234-0302eb-post-table.mjs` that:

1. **Disassembles 0x0302EB-0x030350** (at least 100 bytes) using the transpiled ROM blocks. List each instruction.

2. **Also disassemble 0x02FF11-0x02FF40** to see the exact instruction sequence between the table lookup and the call to 0x0302EB. This tells us what registers/flags are set when 0x0302EB is entered.

3. **Traces 0x0302EB dynamically**:
   - Full boot sequence (z80 boot → kernelInit → memInit → homescreen stages 1-4)
   - Disable timer IRQ: `createPeripheralBus({ timerInterrupt: false })`
   - IX = 0xD1A860 before each homescreen stage
   - After boot: simulate the table lookup result by setting registers to what 0x02FF11-0x02FF1A would produce for key code 0x8F (digit '1'), then call 0x0302EB
   - Trace 200 steps, recording blocks, register changes (especially A, HL, DE), IY flag changes, RAM writes

4. **Test with multiple key types**:
   - 0x8F (digit '1' — regular key code from table)
   - 0x80 ('+' operator)
   - A key that produces a special-path code (≥0xE2, if known from phase230-09f79b-full-table.json)

5. **Identify the function**: Does it validate the key code? Transform it? Set flags? Is it the gate for the 0xE2 threshold (session 229: "CP 0xE2 threshold → normal key codes written to D0058E")?
