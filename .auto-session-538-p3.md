# Task: DECODE 0x07FEE7 (string type handler in 0x07FEE1 region)

## Context
This is a TI-84 Plus CE ROM transpilation project. The ROM file is at `TI-84_Plus_CE/ROM.rom` (4 MB eZ80 binary, little-endian). We're manually decoding eZ80 functions by reading raw bytes from the ROM.

**What we know about 0x07FEE7:**
- Jumped to from 0x07FEF5 when type = 0x21 (string): `CP 0x21; JR Z,$07FEE7`
- Falls inside the 0x07FEE1 region (20B, 0x07FEE1-0x07FEF4), specifically at offset +6 from 0x07FEE1
- The full 0x07FEE1 function (session 536): `CALL 0x08021F (validator). JR C,0x07FEF5. PUSH AF. XOR A. CALL 0x07FEFC. POP AF. LD HL,D005F8. OR (HL). LD (HL),A. RET.`
- So 0x07FEE7 enters partway into 0x07FEE1 — after the CALL 0x08021F + JR C check, but the exact instruction it lands on depends on the encoding

**0x07FEE1 byte-level layout (from session 536 decode):**
- 0x07FEE1: CD 1F 02 08 = CALL 0x08021F (4 bytes)
- 0x07FEE5: 38 0E = JR C,$07FEF5 (2 bytes) → so 0x07FEE7 is immediately after this JR
- 0x07FEE7: This is where the string handler jumps to — it should be the PUSH AF instruction

Let me verify: if 0x07FEE7 is PUSH AF, then the string handler re-enters the "invalid type" path (PUSH AF, XOR A, CALL 0x07FEFC, POP AF, OR (HL), LD (HL),A, RET) — meaning strings get the same sub-transform as invalid types.

**eZ80 encoding reminders (ADL mode, 3-byte addresses):**
- CALL nn = CD nn nn nn (4 bytes)
- JR cc,e = 38/30/28/20 ee (2 bytes, signed offset from PC+2)
- PUSH AF = F5 (1 byte)
- POP AF = F1 (1 byte)
- XOR A = AF (1 byte)
- LD HL,nn = 21 nn nn nn (4 bytes)
- OR (HL) = B6 (1 byte)
- LD (HL),A = 77 (1 byte)
- RET = C9 (1 byte)
