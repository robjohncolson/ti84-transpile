# Auto-session 336 — Priority (d): Map the 0x09EFDE VRAM fill kernel

## Goal
Determine what the block at 0x09EFDE does — it wrote 26,112 bytes to VRAM (0xD40000-0xD44AFF) during the event loop. Is this a full-screen clear, a partial fill, or the LCD DMA transfer? Trace the entry conditions (register values that control fill range and color).

## Context (from session 335 display-refresh probe)
- During the event loop, only 3 blocks touch VRAM:
  - **0x09EFDE**: 26,112 writes to 0xD40000-0xD44AFF (the heavy hitter — this is our target)
  - 0x0A3408: 72 sparse writes to 0xD4114E-0xD422D7 (status bar)
  - 0x09EFEC: 24 sparse writes to 0xD40244-0xD41DC5 (cursor/UI element)
- TI-84 CE LCD is 320×240 at 16bpp = 153,600 bytes total VRAM
- 26,112 bytes = 13,056 pixels = about 8.5% of the screen (roughly 40 rows × 320 pixels)
- VRAM base: 0xD40000
- 0xD44AFF = 0xD40000 + 0x4AFF → offset 19,199 bytes → ~60 rows of 320 pixels at 2 bytes/pixel

## Existing probe to reference
Read `TI-84_Plus_CE/probe-phase335-display-refresh.mjs` — it traced VRAM writes during the event loop. Use its boilerplate for the boot harness.

## Deliverables
Create `TI-84_Plus_CE/probe-phase336-vram-fill.mjs` that:
1. Boots OS normally (boot → kernel init, timerInterrupt: false)
2. Disassembles the block at 0x09EFDE (read ROM bytes, use decodeInstruction to decode ~50 instructions from that address)
3. Sets up execution to call 0x09EFDE directly (after boot) and instruments memory writes to VRAM (0xD40000-0xD5FFFF range)
4. Reports:
   - Full disassembly of the 0x09EFDE block
   - What registers control the fill: start address (likely DE or HL), length (likely BC), fill value/color
   - Whether it's LDIR-based (block copy), a loop, or something else
   - The exact VRAM range filled and what value(s) are written
   - Whether this is a screen clear (all same value) or a copy from another buffer
5. Also disassembles the block at 0x09EFEC (the 24-write block) for comparison — is it the same kernel with different parameters?
