# Session 374 P4: Investigate Repeat-Key vs New-Key Path

## Context
The keyboard scan routine at 0x003C63 has two paths to reach the "store scan code" instruction at 0x003D4B:
1. **Repeat-key path** at 0x003C98: `JP 0x003D4B` — for when the same key is held
2. **New-key path** at 0x003C9C: `CALL 0x003D4B` — for a newly detected key

The repeat path checks a repeat counter at RAM address 0xD0058A (initialized to 0x34=52, decremented each scan call). When the counter reaches 0, it resets to 0x0A=10 and stores the key via the repeat path. This means: even if the multi-key detection rejects the key on each scan, after 52 calls through the repeat timer path, the key should eventually be accepted.

BUT: session 373's dynamic trace showed 90 calls to 0x003C63 over 200K steps with NONE reaching the store at 0x003D4B. Why isn't the repeat path triggering after 52+ calls?

## Key finding to investigate
The repeat counter at 0xD0058A should decrement each scan call. If it's NOT decrementing, the repeat logic is never entered. Possible reasons:
- The repeat check happens BEFORE the multi-key detection, and the multi-key detection at 0x003D2E aborts BEFORE the repeat counter is checked
- The repeat counter check happens in a different branch that requires the PREVIOUS scan to have found a valid key
- The counter is at a different address or the initialization value is wrong

## Setting keyboard matrix key
The keyboard matrix is internal to createPeripheralBus. To press ENTER in the matrix:
- ENTER = keyMatrix[1], bit 0 (per keyboard-matrix.md)
- Need to set keyMatrix[1] &= ~0x01 (clear bit 0 = key pressed, active low)
- If peripherals.setMatrixKey exists (may have been added by P2), use it
- If not, add it to peripherals.js minimally:
  After the keyboardState declaration (~line 483), and in the return object, add:
  ```javascript
  setMatrixKey(group, bit, pressed) {
    if (pressed) {
      keyboardState.keyMatrix[group] &= ~(1 << bit);
    } else {
      keyboardState.keyMatrix[group] |= (1 << bit);
    }
  }
  ```
