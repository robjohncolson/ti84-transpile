# Task: Trace 0x003D5A (_GetCSC keyboard scan function)

## Context
This is a TI-84 Plus CE ROM transpilation project. The ROM (eZ80 machine code) has been lifted to JavaScript. We're tracing the OS event loop to understand how keys get processed.

**Key finding from session 444**: The error handler at 0x003A05-0x003A8E calls 0x003D5A to poll the keyboard. This is the _GetCSC function — the TI-OS keyboard scan routine. It reads the keyboard matrix and returns a scan code in register A.

The TI-84 CE keyboard matrix (from keyboard-matrix.md): The keyboard has 8 groups (0-7). Each group has 8 bits (0-7). A key is identified by group and bit. The scan code format is `(group << 4) | bit` but the SDK maps groups as `keyMatrix[N] = SDK Group(7-N)`.

The keyboard MMIO ports are:
- Port 0xF50012 (or mapped address): keyboard group select
- Port 0xF50010 (or mapped address): keyboard data read

## Task
Write a probe script `TI-84_Plus_CE/probe-phase445-getCSC-trace.mjs` that:

1. Reads the ROM binary at `TI-84_Plus_CE/ROM.rom`
2. Disassembles the function at 0x003D5A and surrounding context (0x003D00-0x003E50) using raw byte decoding
3. For each instruction, decode the opcode and operands. Key eZ80 opcodes:
   - CALL nn (0xCD + 3-byte addr), JP nn (0xC3 + 3-byte addr)
   - JP cc,nn (0xC2/CA/D2/DA + 3-byte addr)
   - RET (0xC9), RET cc (0xC0/C8/D0/D8/E0/E8/F0/F8)
   - IN A,(n) (0xDB + 1-byte port) — but eZ80 uses IN0 A,(n) = 0xED 0x38 + 1-byte port for low ports
   - OUT (n),A (0xD3 + 1-byte port) — eZ80 uses OUT0 (n),A = 0xED 0x39 + 1-byte port
   - IN r,(C) = 0xED + reg-specific byte for port reads via BC
   - OUT (C),r = 0xED + reg-specific byte for port writes via BC
   - LD A,(nn) / LD (nn),A for RAM reads/writes
   - HALT (0x76), DI (0xF3), EI (0xFB)
   - JR e (0x18), JR cc,e (0x20/28/30/38)
   - CP n (0xFE), OR A (0xB7), AND n (0xE6)
   - BIT b,r (0xCB prefix)
   - SLA/SRL/RRA/RLA for shift operations
   - INC/DEC for counters
4. Identify:
   - How does _GetCSC read the keyboard matrix? (which ports, which groups)
   - What does it return in register A? (scan code format)
   - Does it write the scan code to a RAM location?
   - Does it debounce?
   - What's the calling convention? (does it preserve registers?)
5. Cross-reference with the known keyboard matrix layout

Also write a report file `TI-84_Plus_CE/phase445-getCSC-trace-report.md` with:
- Full disassembly of 0x003D00-0x003E50
- Analysis of the keyboard scanning algorithm
- Scan code encoding format
- RAM locations written (if any)
- Register usage and calling convention
