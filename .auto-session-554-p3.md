# Task: Trace Font Table 0x003D6E-0x005B6E — Verify Glyph Boundaries and Dump Characters

## Context
You are working on a TI-84 Plus CE ROM transpilation project. The ROM is at `TI-84_Plus_CE/ROM.rom` (4MB eZ80 binary).

Session 553 decoded the font system:
- 0x000380 is a JP vector → 0x003D85
- 0x003D85 does `LD HL,0x003D6E; RET` — returns the font table base address
- Font table base = 0x003D6E
- Each glyph = 28 bytes (14 rows × 2 bytes per row)
- 256 entries × 28 = 7168 bytes, so table spans 0x003D6E to 0x005B6E
- Format: 14 rows of 16-bit bitmaps, font is ~7px wide × 14px tall
- Verified: char 0x20 (space) = all zeros, char 0x41 ('A') has crossbar pattern

Session 551 found `BIT 1,(IY+0x14)` is the global font size switch (125 callers). When set, it may select a "small font" — possibly a different table entirely.

## Your task
1. Dump ALL 256 glyphs from the font table as ASCII art (using '#' for set bits, '.' for clear bits)
2. Verify that glyph boundaries are correct (char 0x20=space should be blank, printable ASCII 0x21-0x7E should look correct)
3. Check if the font is 7px wide or 8px wide (which bits in each 16-bit row are used?)
4. Look for a SECOND font table (small font). Search strategies:
   a. Look for other `LD HL,0x00XXXX; RET` patterns near 0x003D85 that could be alternate font base providers
   b. Search for other 28-byte-per-glyph tables (or possibly 14-byte tables for a half-height small font)
   c. Check if there are references to addresses in the range 0x005B6E-0x007000 that might be a second font

## How to render a glyph as ASCII art
```javascript
function renderGlyph(rom, tableBase, charCode) {
  const offset = tableBase + charCode * 28;
  const rows = [];
  for (let r = 0; r < 14; r++) {
    const lo = rom[offset + r * 2];
    const hi = rom[offset + r * 2 + 1];
    const word = (hi << 8) | lo;  // or maybe (lo << 8) | hi — check endianness
    let row = '';
    for (let bit = 15; bit >= 0; bit--) {
      row += (word >> bit) & 1 ? '#' : '.';
    }
    rows.push(row);
  }
  return rows;
}
```

Note: endianness matters. eZ80 is little-endian, so the first byte is the low byte. But the bit rendering order in the glyph may be MSB-first (leftmost pixel = highest bit). Try both orderings and see which produces recognizable characters.
