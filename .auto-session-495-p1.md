# Auto-Session 495 — P1: Decode BCALL Entry 833 (0x06118A)

## Context

You are working on a TI-84 Plus CE ROM transpilation project. The OS ROM is lifted to JavaScript and run in a CPU emulator. We are investigating the **cursor draw** mechanism.

**Session 494 found that BCALL entry 833 (target address 0x06118A) is the #1 cursor draw candidate.** Dynamic testing showed:
- 432 changed VRAM pixels at cursor position A (row=3, col=10)
- Bounding box 93×14 — **14 rows tall matches character cell height exactly**
- VRAM write position MOVES with cursor position (different bounding box at row=7, col=20)
- Hit 50K step limit both times (complex routine)
- Width inconsistency (93px vs 309px at different positions) needs explanation

The cursor ERASE function is at 0x061003 (BCALL entry 832). It clears from current row to screen bottom by writing 0xFF to VRAM. The DRAW companion writes non-white pixels. Entry 833 is adjacent in the BCALL table.

Key RAM addresses:
- D00595 = cursor row, D00596 = cursor column
- D00080 = IY base (OS system flags)
- D40000 = VRAM base (320×240, 16bpp, 153,600 bytes)
- 0x0059C6 = charRenderer function
- 0x005A48 = VRAM row calc function
- Cursor glyph codes: 0xE1 (insert block), 0xE2 (overwrite underline), 0xE3 (second cursor)

## Task

Create TWO probe files:

### Probe 1: `TI-84_Plus_CE/probe-phase495-decode-06118A.mjs`

Static disassembly of 0x06118A. Read the ROM bytes at that address and decode eZ80 instructions one by one (ADL mode, 24-bit addresses). Continue until you hit a RET (0xC9) or reach 200 instructions. For each instruction, print the address, hex bytes, and mnemonic.

Look for:
- References to D00595/D00596 (cursor position reads)
- CALL/JP targets (especially 0x0059C6 charRenderer, 0x005A48, 0x0A2A68, 0x0A1CEC, 0x0A22B1 — these are rendering pipeline functions)
- References to cursor glyph codes 0xE1/0xE2/0xE3
- Loop structures (DJNZ, JR NZ, conditional jumps back)
- VRAM address calculations (references to D40000 range)
- Comparisons with D02505 (screen bottom threshold)

Use the ROM.rom file directly: `fs.readFileSync(path.join(__dirname, 'ROM.rom'))`. The ROM is loaded at address 0x000000. To read the byte at address X, just index `romBytes[X]`.

eZ80 ADL mode decoding reference (24-bit):
- LD r, imm8: opcode then 1 byte
- LD rr, imm24: opcode then 3 bytes (little-endian)
- LD r, (IX/IY+d): DD/FD prefix + opcode + signed displacement byte
- CALL imm24: CD xx xx xx (3-byte address, little-endian)
- JP imm24: C3 xx xx xx
- JR e: 18/20/28/30/38 + signed offset byte
- DJNZ e: 10 + signed offset byte
- RET: C9
- Common prefixes: CB (bit ops), DD (IX), FD (IY), ED (extended)
- In ADL mode, all address operands are 3 bytes

Print a summary at the end: total byte span, key CALL targets, whether D00595/D00596 are referenced, whether cursor glyphs are referenced.
