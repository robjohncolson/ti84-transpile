# Auto-Session 204 P1: CoorMon Digit Key Classification

## Context
This is a TI-84 Plus CE ROM transpilation project. The ROM is lifted to JavaScript blocks. We need to understand how the OS event loop routes digit keypresses.

**Problem**: 0x09927F (token validator) CANNOT accept digit tokens — its first instruction is `CALL 0x082C50` which checks `CP 0x5D` and digits (0x30-0x39) always fail. Session 203 proved this conclusively. **Digits MUST bypass 0x058514 entirely** via a different code path.

**Question**: How does CoorMon (0x06EDFE) classify digit keys vs function keys BEFORE execution reaches 0x0584A7? Is there a branch in the home handler (0x0582B8-0x058700) that routes digits to a completely different handler that never touches 0x09927F?

## What to build
Create `TI-84_Plus_CE/probe-phase204-coormon-digit-classify.mjs`.

## Approach
1. **Static disassembly of 0x06EDFE** (CoorMon entry): Read ROM bytes and decode instructions. CoorMon is the OS monitor/event loop. Look for CP/SUB/AND instructions that distinguish key classes. Look for jump tables, indirect JP (HL), or conditional branches based on key code value.

2. **Trace the home handler entry from 0x0582B8 to 0x0584A7**: Session 182 disassembled this range (~280 instructions). The path includes:
   - 0x058467: sets cxErrorEP 
   - 0x058483: LCD stall skip
   - 0x0584A3: `LD HL,0xD0230E; CALL 0x07F9FB` (Copy9 TOKEN_STAGING→OP1)
   - 0x0584A7: `CALL 0x07F7BD` (KeyClassifier — reads OP1[0] & 0x3F)
   - 0x0584C1: `BIT 5,(IY+0x44)` — dispatch gate
   - 0x058514: `CALL 0x09927F` (token validator — BLOCKS digits)
   
   BUT there are branches BEFORE 0x0584A3. Look at 0x058460-0x0584A3 for any conditional that separates digit keys from other keys before Copy9 is called.

3. **Specifically investigate**: 
   - What code runs BETWEEN CoorMon dispatching a key and 0x0582B8 being entered?
   - Are there multiple home-context entry points depending on key type?
   - Does the home handler have a fast-path for digit insertion that goes directly to BufInsert (0x05E2A0) without going through 0x09927F?
   - Check the JP (HL) dispatch at 0x0585D3 — session 187 decoded the cxMain structure there (cxMain=0x0585E9, cxPPutaway=0x058B19, etc.). Different entry points might handle different key classes.

4. **Execution traces**: 
   - Use the standard probe pattern: `import { createCPU, createMemory, ... } from './cpu-runtime.js'`
   - Load ROM, run kernelInit + memInit
   - Pre-seed a digit key (scan code 0x92 for key '4', which ConvKeyToTok maps to token 0x34)
   - Trace from 0x0582B8 with the digit key in the appropriate register
   - Also trace from 0x06EDFE if feasible (may need MMIO stubs)

## Success criteria

- Identification of whether digits take a DIFFERENT path through the home handler than function keys
- If a digit bypass exists: the exact address where digit keys diverge from the 0x09927F path
- If no bypass exists at this level: document what CoorMon does with the key code and where the next investigation should look
