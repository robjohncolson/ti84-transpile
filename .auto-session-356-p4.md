# Task: Verify browser shell loads and renders after transpiler changes

## Context
TI-84 Plus CE ROM transpilation project. Session 355 made significant changes:
- Fixed RSMIX/STMIX opcode swap in `TI-84_Plus_CE/ez80-decoder.js`
- Removed mode-switch classification from STMIX/RSMIX
- Removed mode-switch block termination from transpiler
- Regenerated `TI-84_Plus_CE/ROM.transpiled.js.gz`
- Block count changed from 147,205 → 144,190

The browser shell at `TI-84_Plus_CE/browser-shell.html` loads the transpiled ROM and runs it with LCD rendering. We need to verify it still loads correctly.

## What to do

1. **Read `TI-84_Plus_CE/browser-shell.html`** and check for any hardcoded block counts or assumptions that might break with the new transpiler output.

2. **Check that `ROM.transpiled.js.gz` exists** and report its file size.

3. **Run a headless verification probe** `TI-84_Plus_CE/probe-phase356-browser-shell-verify.mjs` that:
   - Loads the same modules the browser shell uses (cpu-runtime.js, peripherals.js, the transpiled blocks)
   - Creates the executor with `createPeripheralBus({ pllDelay: 2, timerInterrupt: false })`
   - Boots from 0x000000, runs 2000 steps
   - Verifies: blocks load without error, executor creates without error, boot reaches at least 200 unique blocks
   - Checks VRAM region (0xD40000-0xD65800) for any non-zero pixels (indicating LCD init wrote something)
   - Reports: total blocks in transpiled module, blocks visited in 2000 steps, VRAM status

## Probe structure (MANDATORY)
Use the exact same boilerplate as `TI-84_Plus_CE/probe-phase355-rst38h-bypass.mjs`:
- Same imports, same `ensureTranspiledRom()`, same `createMemory()`, same module loading
- `createPeripheralBus({ pllDelay: 2, timerInterrupt: false })`
- Run via `executor.runFrom(cpu.pc, cpu.adl ? 'adl' : 'z80')`
- Initial: `cpu.pc = 0x000000`, `cpu.adl = false`
