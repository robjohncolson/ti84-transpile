# Auto-Session 607 — P3: TRACE KEY2 RUNAWAY AT 0x090927

## Goal
Trace key2's execution to understand why it gets stuck at 0x090927 after 500K steps. Session 606's wipe-hook probe showed key2 dispatches through cxMain successfully but enters the display rendering engine and never comes back. We need to find the exact divergence point between key1 (which completes) and key2 (which runs away).

## Background
- Session 606 showed key2 gets stuck at 0x090927 after 500K steps with 78 VRAM pixels. Key3 similarly gets stuck at 0x08F3DC.
- 0x090927 and 0x08F3DC are both in the 0x08xxxx-0x09xxxx range (display rendering engine).
- Key1 runs 332,856 steps and halts normally. Key2 and key3 have the post-paint snapshot restored (which is apparently insufficient).
- Session 606 also found key2 enters at block 0x03D058 (different from key1's 0x03F9B0) — this is the "skip init" fast path.
- Key2-only blocks include 0x08DD60-0x08DD9F (7 blocks) and 0x08E63E-0x08E775 (8 blocks in display branch).

## What to Build
Create `TI-84_Plus_CE/probe-phase607-key2-runaway.mjs`:

1. **Boot the OS** using the same init and post-paint snapshot as `probe-phase606-wipe-hook.mjs` (read that file for exact setup).

2. **Run key1 ('2', scan code 0x9A)** to completion (it halts normally). Note the step count and final state.

3. **Restore the post-paint snapshot** (same as 606 — this is the one that causes key2 to run away).

4. **Run key2 ('3', scan code 0x91)** with DETAILED TRACING:
   - Track ALL unique blocks visited, in order of first visit
   - Use onBlock for these milestone addresses:
     - 0x08C331 (CoorMon), 0x08C72F (cxMain dispatch), 0x0019B5 (halt)
     - 0x0018F8 (wipe), 0x03D058 (key2's entry), 0x03F9B0 (key1's entry)
     - 0x090927 (where key2 gets stuck), 0x08F3DC (where key3 gets stuck)
     - 0x08DD60, 0x08DD9F (key2-only cluster boundaries)
   - Every 50,000 steps, log: current PC, step count, VRAM pixel count, stack depth (read SP)
   - At step 450,000 (near the end), capture the last 100 unique blocks visited
   - At step 499,000, do a tight trace: log every block for the last 1000 steps to find the loop

5. **Report**:
   - Total unique blocks visited by key2
   - Milestone hit log (which milestones fired, at what step counts)
   - The block loop at the end (the repeating pattern of blocks after 499K steps)
   - Is key2 in a tight loop between a few addresses? If so, what addresses?
   - Comparison: which milestone addresses are hit by key2 but NOT by key1 (from session 606 data)?
