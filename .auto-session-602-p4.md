# Auto-Session 602 — Priority 4: FIND WHAT ZEROES VRAM AFTER THE PEAK

## Context

This is a TI-84 Plus CE ROM transpilation project. The lifted OS runs real eZ80 code as JavaScript.

Session 600 showed the VRAM lifecycle during key processing:
- 1,348 px (pre-key, status bar)
- 22 px (status bar clear at step 42K)
- 0 px (bulk wipe at step 86K via 0x0018F8)
- 3,040 px (body repaint at step 94K)
- 3,349 px (peak at step 270K with 4 text lines + entry line)
- **0 px at halt** (step 276K)

The bulk mem-clear at 0x0018F8 clears D00000-D13FD7 (82KB) — this does NOT include VRAM which starts at 0xD40000. So something ELSE zeroes VRAM between the peak (~step 270K) and halt (~step 276K).

The question: is the final VRAM=0 state the "real" display state (meaning the calculator screen would be blank after pressing '2'), or is it a teardown artifact (the OS clears VRAM as part of returning to idle, and the ISR/timer would repaint it)?

## Task

Write a probe that:
1. Boots the OS, paints status bar, presses '2', runs outer loop (use the standard recipe from probe-phase601-verify-2-glyph.mjs as reference)
2. Samples VRAM non-white pixel count at every 1000 steps from step 265K to step 280K (or halt, whichever comes first)
3. When VRAM transitions from non-zero to zero, record the EXACT step number and current PC
4. At that transition step, also record:
   - The current call stack (if accessible — check cpu.regs.sp and read the stack)
   - What block is executing
   - Whether D007CA is still zero
5. Check if the VRAM zeroing is done by:
   - A LDIR/LDIR-equivalent (bulk memory fill)
   - Individual writes (display clear function)
   - The same 0x0018F8 bulk init (check if 0x0018F8 runs a second time)
