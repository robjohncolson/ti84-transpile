### What we know about 0x096F67

From session 498 (probe-phase498-decode-096CCF.mjs):
- 0x096CCF (the cursor show/erase subroutine) calls 0x096F67 as its **FIRST** call:
  `CALL 0x096F67`
  `JP NZ to 0x097955 (early exit)`
- This means 0x096F67 runs BEFORE any row manipulation in 0x096CCF
- 0x096CCF does NOT directly call 0x061061 (cursor draw) or 0x061003 (cursor erase)
- Therefore 0x096F67 is likely where the actual draw/erase dispatch happens

### Call chain so far

```
cursor_blink_toggle (0x096BEE)
  → cursor_show_sub (0x096CCF)
      → 0x096F67  [FIRST CALL — this is what you're decoding]
          JP NZ → early exit (0x097955)
      → ... row manipulation
      → 0x096CC8
```

### Blink toggle logic (0x096BEE)

- Tests BIT 2,(IY+0x0D) (cursor-currently-drawn flag)
- If bit=0 (NOT drawn): JP to 0x096CCF to DRAW
- If bit=1 (IS drawn): RES bit 2, CALL 0x096CCF to ERASE, SET bit 2

### Known RAM addresses

- D008D2: VRAM base address (24-bit HL)
- D008D5: VRAM high byte
- D00595: cursor row (0-based)
- D00596: cursor col (0-based)
- D02505: cursor col duplicate
- D02575: cursor type/character code
- IY_BASE = 0xD00080
- (IY+0x0D) = D0008D = cursor flags (bit 2 = cursor drawn on screen)

### Known subroutines to annotate

- 0x061980: putchar
- 0x061003: cursor_erase
- 0x061061: cursor_draw
- 0x060EF5: cursor_blink_orchestrator
- 0x096BEE: cursor_blink_toggle

- 0x096CC8: unknown_096CC8 (short helper)
- 0x0A23E5: pixel_renderer (reads D008D2/D008D5)
