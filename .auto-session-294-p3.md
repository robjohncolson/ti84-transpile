# Auto-session 294 P3: Trace 0x096E22 (default key handler)

## Context
In the TI-84 Plus CE OS, the dispatcher at 0x0258DA handles recognized scan codes via CP cascades (GRAPH, MATH, STAT, etc.). Scan codes that don't match ANY CP comparison fall through to a default handler at 0x025A93 which does:
- CALL 0x096E22
- CALL 0x025CFC

Session 293 proved that CLEAR (scan code 0x28) does NOT have a dedicated handler in 0x0258DA — it falls through all comparisons to this default path. So 0x096E22 is where CLEAR and other unmatched scan codes get processed.

## Task
Create a probe file `TI-84_Plus_CE/probe-phase294-096e22-default-handler.mjs` that:

1. Reads `TI-84_Plus_CE/ROM.rom` directly (raw binary, 4MB)
2. Uses `TI-84_Plus_CE/ez80-decoder.js` to decode instructions starting at 0x096E22
3. Follows the linear instruction stream (stop at RET/JP unconditional)
4. For EACH instruction, check:
   - Does it read D0058C (raw scan code)?
   - Does it read D0058E (keyExtend)?
   - Does it use CP instructions? Log comparison values — these may form a secondary dispatch for CLEAR and other codes
   - Does it reference IY+offset (OS flags)?
   - Is it a CALL? Log target
   - Is it a conditional branch? Log condition and target
5. Also disassemble 0x025CFC (the second call from the default path) using the same approach
6. Build CP cascade maps for both functions
7. Report: instruction count, byte range, all CP values, all CALL targets, any reference to scan code 0x28 (CLEAR), IY flag accesses

## Reference

## Key technical details
- ROM file is raw binary, byte at file offset N = ROM address N
- ez80-decoder.js: `decodeInstruction(romBuffer, address)` returns instruction object
- Scan code 0x28 = CLEAR key in TI-84 keyboard matrix
- D0058C = raw scan code storage, D0058E = keyExtend
- IY typically points to OS flag area (IY+0x00 through IY+0x44 or so)
- The default handler may itself contain a CP cascade that handles CLEAR
