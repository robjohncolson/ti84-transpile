# Task: _GetCSC handler investigation — disassemble blocks and find missing CALL targets

## Context
The _GetCSC OS function (jump table entry at 0x020048, handler at 0x03D184) is supposed to scan the keyboard matrix and return a scan code. Currently:
- Handler chain runs only 4 blocks: 0x03D184 → 0x03D197 → 0x03D19C → 0x03D1BB
- Reads port 0x5016 (interrupt status) and 0x5006 (enable mask) but ZERO reads in 0xE00800-0xE00FFF keyboard MMIO range
- Returns A=0x04 for all keys (wrong — value comes from reset vector after stack corruption)
- Stack corruption: POP HL pops wrong value → falls to 0x000000 reset vector
- The direct scan function at 0x0159C0 works perfectly (Test 25, 9/9 PASS), so keyboard MMIO hardware is fine

The handler chain is too short to be a complete keyboard scan. It likely contains CALL or JP targets pointing to blocks that aren't transpiled yet, OR the calling convention expects a specific stack frame we're not providing.

## Deliverables

Build a probe file `TI-84_Plus_CE/probe-phase177-getCSC-disasm.mjs` that:

1. **Static disassembly**: Read raw ROM bytes from 0x03D180 to 0x03D200 (128 bytes covering the handler chain plus surrounding context). Use `ez80-decoder.js` to decode every instruction. Print each with address, hex bytes, and mnemonic. Flag all CALL/JP/JR targets.

2. **Check transpiled blocks**: For every CALL/JP target found in step 1, check if a block exists in PRELIFTED_BLOCKS at that address. Report which targets are present and which are MISSING.

3. **Trace with MBASE fix**: Run _GetCSC with `cpu.mbase = 0xD0` (the ISR gate fix from session 176) to see if the handler behaves differently when MBASE is correct. Set up the keyboard with ENTER pressed (`keyMatrix[1] = 0xFE`), set keyboard IRQ, then call 0x020048. Trace every block visited, every I/O access, and every MMIO read. Compare to the session 176 trace (which used MBASE=0).

4. **Stack frame analysis**: Before calling _GetCSC, dump the stack contents around SP. After the call, show where SP ended up and what values were popped. This will reveal if the POP HL stack corruption is due to missing setup.

5. **Check the _GetCSC jump table path**: The entry point 0x020048 is a jump table stub. Disassemble what's at 0x020048 to find the real handler address it dispatches to. Verify this matches 0x03D184.
