# Auto-Session 363 P3: Disassemble 0x014C63 and 0x014C6B

## Goal
Create a probe that disassembles and traces blocks 0x014C63 and 0x014C6B, which execute between steps 2673-2676 during boot. These are part of the call chain leading to SP corruption.

## Background
Session 362 established:
- At step 2672, SP is in RAM (~0xD1A7E5)
- Block 0x014C63 is called at step 2673
- Block 0x014C6B returns at some point
- By step 2685, SP is in ROM (~0x014C6F) — corrupted
- 0x014C63 calls 0x002197 which does JP (HL)
- 0x014C6B returns

We need to understand what these blocks do: what's in HL at the JP (HL)? What state do they leave? Are they the source of the corruption or just passing through?

## Deliverable
Create file: `TI-84_Plus_CE/probe-phase363-disasm-014C63.mjs`

## What the probe must do

### Part 1: Static disassembly
1. Load ROM.rom
2. Disassemble from 0x014C63 for ~64 bytes using ez80-decoder.js
3. Disassemble from 0x014C6B for ~32 bytes
4. Disassemble from 0x002197 for ~32 bytes (the JP (HL) target)
5. Print each instruction with address, hex bytes, mnemonic, operands
6. Annotate any PUSH, POP, LD SP, CALL, RET, JP instructions — these affect control flow and stack

### Part 2: Dynamic trace
1. Boot from 0x000000 in z80 mode, timerInterrupt: false, max 5000 steps
2. Log full register dumps (A, BC, DE, HL, IX, IY, SP, PC, flags, MBASE) when entering:
   - Block 0x014C63
   - Block 0x014C6B
   - Block 0x002197
   - Any block in range 0x014C00-0x014CFF
3. At block 0x002197, specifically log HL (the JP target)
4. Track SP changes in the window from step 2670 to step 2690

### Part 3: Caller trace
1. Track which block CALLs 0x014C63 (what is the caller at step 2672-2673?)
2. Track what block executes after 0x014C6B returns
3. Build a mini call-chain: ... → caller → 0x014C63 → 0x002197 → JP(HL) → ? → 0x014C6B → RET → ?
