# Session 374 P2: Investigate Keyboard Scan Multi-Key Rejection

## Context
The keyboard scan routine at 0x003C63 (called by _GetCSC at 0x003D5A) reads the CE keyboard controller ports 0xA000-0xA014 to detect pressed keys. Session 373 found that over 90 calls to 0x003C63 during 200K steps, the scan routine NEVER reaches the "store scan code" instruction at 0x003D4B. Instead, all calls exit via the carry-flag error path (0x003D47: SCF; LD A,0xFF; RET → caller stores 0xFF in 0xD00589).

The multi-key detection at 0x003D2E does `INC H; JR NZ,0x003D47` which triggers the error path when H is already non-zero (meaning a second group with activity was found). But the question is: WHY does the scan detect multiple groups?

Hypothesis: the emulated keyboard controller at ports 0xA000-0xA010 may be returning key data regardless of which group is selected. The real CE hardware only returns data for the group whose select line is active. Check whether:
1. The group-select write to 0xA000 correctly isolates which group's data is returned from 0xA008
2. When ENTER (group 1, bit 0) is the only key pressed, reading 0xA008 with group 0 selected returns 0xFF (no keys)

   - For each group select value (0xFE=group0, 0xFD=group1, 0xFB=group2, 0xF7=group3, 0xEF=group4, 0xDF=group5, 0xBF=group6, 0x7F=group7):
     - Write the group select to port 0xA000

2. **Dynamic trace during boot**: Boot through phases 1-3, then enter the event loop at 0x003A73 with ENTER pressed in the keyboard matrix (keyMatrix[1] &= ~0x01). Instrument port reads/writes:

3. **H-register tracking**: Instrument block 0x003D2E to log the H register value when the INC H instruction executes. This will show how many groups had activity before the multi-key detection triggers.

## Keyboard matrix reference
```
keyMatrix[0] = SDK Group 7 (arrows): B0:DOWN B1:LEFT B2:RIGHT B3:UP
keyMatrix[1] = SDK Group 6 (operators): B0:ENTER B1:+ B2:- B3:× B4:÷ B5:^ B6:CLEAR
```
ENTER = keyMatrix[1], bit 0. Pressed = bit CLEAR (0xFE). Group select for group 1 = 0xFD (bit 1 clear).
