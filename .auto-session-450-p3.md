# Task: Trace 0x0067F8 Execution — Map Call Tree to Crash at 0xD18C22

## Context
When the TI-84 OS processes a key, the event loop at 0x003A73 calls _GetCSC (0x003D5A), then 0x001713 (key dispatch), which calls 0x0008BB (ROM magic guard — returns Z), then 0x0067F8 (real key handler). 0x0067F8 is a C-compiled function (PUSH IX frame, args via stack) that processes the key and eventually crashes at PC=0xD18C22 after 170,329 steps through 405 unique blocks. VRAM changes during execution.

Session 449 already has a trace probe at `TI-84_Plus_CE/probe-phase449-0x0067F8-key-handler-trace.mjs` that collected the first 40 unique block PCs. The full list of 405 blocks was collected but only 40 are in the report.

## Your task
Create `TI-84_Plus_CE/probe-phase450-0x0067F8-calltree.mjs` that:

1. **Boots the OS** (standard sequence: BOOT_ENTRY → KERNEL_INIT → POST_INIT → 4 stages)
2. **Sets gates**: D14091=1, D177B7=0x55, D177BA=0
3. **Injects key "1"** (scan=0x12, idx=4, bit=1, D00587=0x12, IY+0 bit 3 set)
4. **Runs from EVENT_LOOP_ENTRY (0x003A73)** with maxSteps=200000, diHaltBypass:true
5. **Tracks ALL CALL/RET instructions** during execution to build a call tree

For tracking CALLs and RETs: The executor visits transpiled blocks. Each block starts at a PC. To detect CALL targets, look at the sequence of visited PCs. When a new PC is visited that doesn't follow sequentially from the previous block's expected end, it's likely a CALL target. When execution returns to a PC that was previously on the "stack", it's a RET.

A simpler approach: just collect ALL unique block PCs in execution order (all 405 of them), then for each PC, read 4-8 bytes from ROM to identify CALL instructions. Group the blocks into functions by looking for PUSH IX/PUSH IY prologues (0xDDE5 or 0xFDE5) and RET (0xC9) instructions.

6. **Identifies the last ~20 blocks before the crash** at 0xD18C22. This shows the call chain leading to the crash.

7. **Writes report** to `TI-84_Plus_CE/phase450-0x0067F8-calltree-report.md`
